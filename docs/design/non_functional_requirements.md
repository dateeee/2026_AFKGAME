## 1. 性能要件

個人運用のため対外的なSLAは掲げず、**プレイ体験が破綻しない上限**として定義する。数値は仮置き（負荷試験で計測して確定）。

| 対象 | 目標 p95（仮置き） | 根拠 |
|------|------------------|------|
| `GET /api/game/state` | 300ms | 起動時・復帰時の初期表示に直結する |
| `POST /api/battle/tick`（1〜100tick／正規シミュレーション） | 800ms | オンライン中のポーリングの体感即時性 |
| `POST /api/battle/tick`（101〜1,440tick／簡略計算） | 3,000ms | 24時間放置からの復帰が最悪ケース |
| 操作系（購入・装備変更・スキル習得など） | 300ms | 1セッション3〜5分の操作を妨げない |
| 認証系（login / register） | 1,000ms | パスワードハッシュ計算を含む |
| ランキング取得 | 500ms | 上位固定件数の取得 |
| フロント初期表示（LCP・モバイル回線） | 2,500ms | |

| 規模の前提 | 値 |
|-----------|-----|
| 登録ユーザー数 | 初期 1,000／上限想定 10,000 |
| 同時アクティブユーザー | 100（登録者の10%が同時接続する想定） |

- **tick処理時間が60秒（ポーリング周期）を超えないこと**は必須要件。超過すると次tickと重なり処理が破綻する
- 目標を超過した場合の対処順序は [tech_performance.md §10.4](../tech/tech_performance.md)。ただし **tick間隔の変更・報酬効率の低下をもって性能対策としてはならない**
- 計測・負荷試験は [development_process.md §3.6](../development_process.md) 結合テストの一部として実施する

## 2. 容量・データ保持要件

放置ゲームでは**時間に比例してデータが増え続ける**ため、上限または保持期間のないデータを持たない。

| 対象 | 上限 | 定義箇所 |
|------|------|---------|
| 戦闘ログ（DB保存） | ユーザーあたり100件 | [tech_battle.md §1](../tech/tech_battle.md) |
| 戦闘ログ（APIレスポンス） | 50件／回 | 同上 |
| オフライン報酬の蓄積 | 24時間分（1,440tick） | [systems/battle.md](systems/battle.md) |
| アイテム・装備の所持枠 | 倉庫LVによる上限あり | [systems/economy.md](systems/economy.md) |
| ポーション所持数 | 種類ごと99個 | [systems/battle.md](systems/battle.md) |
| リフレッシュトークン | 有効期限30日 | [tech_auth.md](../tech/tech_auth.md) |
| アプリケーションログ | 保持30日 | [tech_logging.md](../tech/tech_logging.md) |

- **上限のないデータを新設しない**。新しいテーブルには必ず「1プレイヤーあたりの上限」または「保持期間」を定義し、本表に追記する
- 1プレイヤーあたりのサイズ見積りとDB移行の判断ラインは [tech_performance.md §10.3](../tech/tech_performance.md)

## 3. 可用性

| 項目 | 目標 | 補足 |
|------|------|------|
| 稼働率 | 99%（月間ダウンタイム 約7時間まで許容） | 個人運用のためSLAとしては提示しない |
| RPO（復旧時点目標） | 24時間 | 日次バックアップ相当 |
| RTO（復旧時間目標） | 4時間 | 手動復旧を前提とする |
| 計画メンテナンスの停止時間 | **24時間未満**（必須制約） | 下記のとおり超過するとプレイヤーの報酬が失われるため |

- **停止中の経過分が復帰後に回収されること**は要件である。tick処理は経過時間から算出するものとし、サーバーの稼働時間の積算に依存してはならない
- 停止時間がオフライン上限（24時間）以内であれば報酬の損失は発生しない。超過した場合の補填は [operation_requirements.md §3](operation_requirements.md) に従う
- バックアップ・リストアの方式と検証頻度は [tech_operations.md §12.5](../tech/tech_operations.md)

## 4. セキュリティ・不正防止要件

「サーバー権威」（[tech_architecture.md](../tech/tech_architecture.md)）が具体的に**何を防ぐか**を定義する。実現方式は [tech_security.md §11](../tech/tech_security.md)。

| # | 脅威 | 守るべき要件 |
|---|------|------------|
| S-1 | 戦闘結果の偽装 | 戦闘計算・報酬確定はサーバーのみで行う。クライアントから受理するのは**入力値**（目標階・装備選択・設定値）のみとし、**結果値**（獲得ゴールド・EXP・HP）は受理しない |
| S-2 | **端末時計の改ざん** | 経過時間はサーバー時刻（UTC）と DB の `lastTickAt` のみから算出する。クライアントが送る時刻・経過秒数は**一切参照しない** |
| S-3 | tick連打・多重タブによる報酬の多重取得 | 同一ユーザーのtickが同時実行された場合でも、付与される報酬が経過時間ぶんを超えないこと |
| S-4 | 他ユーザーのデータ操作 | すべてのゲームAPIで認証を必須とし、対象リソースの所有者以外の操作を拒否すること |
| S-5 | 入力値の改ざん | 目標階・購入数量・装備IDは、サーバー側で範囲と所有権を再検証すること |
| S-6 | 認証情報への総当たり攻撃 | パスワードは復元不可能な形で保存し、認証系エンドポイントには試行回数の制限を設けること |
| S-7 | 秘密情報の露出 | 署名鍵・OAuthクレデンシャルは環境変数で管理し、**本番環境で既定値のまま起動できないこと** |
| S-8 | ログ・エラー経由の情報漏洩 | パスワード・トークン・メールアドレスをログおよびAPIレスポンスに出力しないこと |

- S-1〜S-3 は [product_requirements.md §5](product_requirements.md) の受入観点「公平性」の判定対象とする

## 5. データライフサイクル・プライバシー要件

| 項目 | 要件 |
|------|------|
| 取得する個人情報 | メールアドレス（メール登録時）、Googleアカウントのメール・ID（OAuth連携時）**のみ**。氏名・生年月日・位置情報等は取得しない |
| 公開される情報 | 表示名（`display_name`）とランキング記録のみ。メールアドレスは公開しない |
| 表示名の扱い | 本名・連絡先を入力しないよう注意喚起する。不適切な表示名は運営が変更できること |
| ゲストデータの消滅 | 最終アクセスから90日で自動削除される（[tech_auth.md](../tech/tech_auth.md)）。**事前告知の手段を持たない**ため、本登録を促す導線をUIに常設すること |
| データ復旧不可の明示 | ゲストのままリフレッシュトークンを失うと復旧できない。この制約を初回起動時と設定画面で明示すること |
| 退会（アカウント削除） | プレイヤーの要求により、アカウントと紐づく全ゲームデータを削除できること（**未実装** → [open_specs.md](../open_specs.md)） |
| 同時セッション | 同一アカウントの複数タブ・複数端末での同時プレイを許容する。報酬は多重化せず（§4 S-3）、画面間の不整合は次tickで解消されること |
| 対象年齢 | 全年齢。射幸性の高い課金要素を持たない（完全無料） |
| 規約類 | 公開時に利用規約・プライバシーポリシーを掲示すること（Google OAuth 利用の前提条件でもある → [open_specs.md](../open_specs.md)） |

- 削除ジョブの実行方式は [tech_operations.md §12.6](../tech/tech_operations.md)
