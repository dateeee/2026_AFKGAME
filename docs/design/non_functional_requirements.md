## 1. 性能要件

個人運用のため厳密なSLAは設けず、**プレイ体験が破綻しない上限**として定義する。数値は仮置き（結合テストで計測して確定）。

| 対象 | 目標（仮置き） | 備考 |
|------|--------------|------|
| `POST /api/battle/tick`（オンライン: 1〜数tick） | p95 300ms | 60秒ポーリングの体感即時性 |
| 同（オフライン復帰: 〜100tick／正規シミュレーション） | p95 1.0秒 | [tech_offline.md §2](../tech/tech_offline.md) |
| 同（オフライン復帰: 101〜1,440tick／簡略計算） | p95 3.0秒 | 24時間放置＝最大1,440tick |
| `GET /api/game/state` | p95 300ms | 起動時の初回ロード |
| 初期表示（LCP・モバイル回線） | 3秒以内 | |
| 初期JSバンドル | 500KB（gzip後）以内 | |
| 想定同時アクティブユーザー | 100 | 個人運用時の上限想定 |

- tick処理が目標を超える場合は、簡略計算への切替閾値（`FAST_CALC_THRESHOLD`、現在100）を下げて調整する
- 計測は結合テスト工程（[development_process.md §3.6](../development_process.md)）で行う

## 2. 容量・データ保持要件

放置ゲームでは**時間に比例してデータが増え続ける**ため、無制限に保持する対象を作らない。

| 対象 | 上限 | 正となる定義 |
|------|------|------------|
| 戦闘ログ（DB保存） | ユーザーあたり100件 | [tech_battle.md §1](../tech/tech_battle.md) |
| 戦闘ログ（APIレスポンス） | 50件／回 | 同上 |
| オフライン報酬の蓄積 | 24時間分（1,440tick） | [systems/battle.md](systems/battle.md) |
| アイテム・装備の所持数 | 倉庫LVによる上限あり | [systems/economy.md](systems/economy.md) |
| ポーション所持数 | 種類ごと99個 | [systems/battle.md](systems/battle.md) |
| アプリケーションログ保持 | 30日 | [tech_logging.md](../tech/tech_logging.md) |

## 3. 可用性

| 項目 | 要件 |
|------|------|
| 稼働目標 | ベストエフォート（SLAなし・個人運用） |
| 停止中の進行 | tickはサーバー時刻から算出するため、停止中の経過分は復帰後のオフライン計算で回収される（上限24時間を適用） |
| 通信断時のクライアント | 最大3回リトライ後に接続エラーバナー表示（[tech_architecture.md](../tech/tech_architecture.md)） |
| バックアップ | 日次取得。RPO 24時間／RTO ベストエフォート |

- 「停止中の経過分が回収される」ことは要件である。tick処理は**経過時間から算出**するものとし、サーバーの稼働時間の積算に依存してはならない
- 24時間を超える停止時の扱いは [operation_requirements.md §3](operation_requirements.md) を参照

## 4. セキュリティ・不正防止要件

「サーバー権威」（[tech_architecture.md](../tech/tech_architecture.md)）が具体的に**何を防ぐか**を要件として定義する。

| 脅威 | 要件 |
|------|------|
| 戦闘結果の偽装 | 戦闘計算・報酬確定はサーバーのみで行う。クライアントから受理するのは**入力値**（目標階・装備選択・設定値）のみとし、**結果値**（獲得ゴールド・EXP・HP）は受理しない |
| **端末時計の改ざん** | 経過時間はサーバー時刻（UTC）と DB の `lastTickAt` のみから算出する。クライアントが送る時刻・経過秒数は一切参照しない |
| tick連打・多重タブによる報酬の多重取得 | tickは `lastTickAt` の更新を伴う排他処理とし、同時実行時は後続が0tickとなること |
| API直接呼び出し | 全ゲームAPIでJWT必須。他ユーザーのリソース操作は403を返す |
| 入力値の改ざん | 目標階・購入数量・装備IDはサーバー側で範囲・所有権を再検証する |
| 認証情報への攻撃 | パスワードは bcrypt（cost 12）でハッシュ化。認証系エンドポイントにレート制限を設ける |
| 秘密情報の露出 | `JWT_SECRET` 等は環境変数で管理し、**本番で既定値のまま起動させない**（起動時チェック） |
| ログからの漏洩 | パスワード・トークン・メールアドレスはマスクする（[tech_logging.md](../tech/tech_logging.md)） |

## 5. データライフサイクル・プライバシー要件

| 項目 | 要件 |
|------|------|
| 取得する個人情報 | メールアドレス（メール登録時）、Googleアカウントのメール・ID（OAuth連携時）**のみ**。氏名・生年月日・位置情報等は取得しない |
| 公開される情報 | 表示名（`display_name`）とボスラッシュの記録のみ |
| 表示名の扱い | 本名・連絡先を入力しないよう注意喚起する。不適切な表示名は運営が変更できる |
| ゲストデータの消滅 | 90日アクセスなしで自動削除（[tech_auth.md](../tech/tech_auth.md)）。**事前通知の手段がない**ため、本登録を促す導線をUIに常設する |
| データ復旧不可の明示 | ゲストのままリフレッシュトークンを失うと復旧できない。この制約を初回起動時と設定画面で明示する |
| 退会（アカウント削除） | プレイヤーの要求により、アカウントと紐づく全ゲームデータを削除できること（**未実装** → [open_specs.md](../open_specs.md)） |
| 同時セッション | 同一アカウントの複数タブ・複数端末での同時プレイを許容する。サーバー権威により報酬は多重化せず、画面間の不整合は次tickで解消される |
| 対象年齢 | 全年齢。射幸性の高い課金要素を持たない（完全無料） |
| 規約類 | 公開時に利用規約・プライバシーポリシーを掲示する（Google OAuth 利用の前提条件でもある） |
