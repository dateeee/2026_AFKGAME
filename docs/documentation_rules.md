# AFK GAME — ドキュメント規約

> 本書は AFK GAME の Markdown ドキュメント（要件定義〜詳細設計の成果物）の記述規約を定める。
> プロジェクト概要は [README.md](../README.md)、工程定義は [development_process.md](development_process.md) を参照。

---

## 1. 目的

AIエージェント（Claude Code）と人間が共同で開発するため、ドキュメントは「人が読める」だけでなく **「AIが1回の読み込みで理解できる」** 必要がある。

- **コンテキスト効率**: 巨大ファイルは全文読込でコンテキストを圧迫し、他の必要情報を押し出す
- **参照精度**: 1ファイル1テーマなら、必要な箇所だけを正確に参照できる
- **編集の安全性**: 巨大ファイルの部分編集は前後の文脈欠落により矛盾を生みやすい
- **レビュー効率**: ファイルが小さいほど変更の影響範囲が明確になる

→ **「1ファイル = 1テーマ = 1回の読み込みで完結」** を原則とする。

## 2. 適用範囲

- 対象: リポジトリ内の全 `.md` ファイル
- 除外: `node_modules/`、`docs/reviews/`、`docs/changelog.md`（いずれも追記型アーカイブ。通常の作業では読み込まない）

## 3. 文字数上限

文字数は **UTF-8の文字数**（バイト数ではない）で数える。

| 区分 | 対象 | 推奨 | 上限 | 根拠 |
|------|------|------|------|------|
| **A. 常時読込** | `CLAUDE.md` | 2,500 | **3,000** | 全セッション・全ターンで読み込まれるため最も厳格 |
| **B. 索引** | `README.md`、`**/*_OVERVIEW.md` | 4,000 | **6,000** | 目次として全体を見渡す。詳細は持たない |
| **C. 仕様・設計・データ** | `docs/**`、`diagrams/**` | 6,000 | **8,000** | 1テーマを1回の読み込みで完結できる粒度 |
| **D. エージェント定義** | `.claude/skills/**`、`.claude/references/**`、`.claude/project/**` | 4,000 | **5,000** | スキル起動時に読み込まれる |
| **除外** | `docs/reviews/**`、`docs/changelog.md`、`node_modules/**` | — | — | 追記型アーカイブ（§5.1） |

### 上限8,000字の根拠

本プロジェクトで既に「1エンティティ = 1ファイル」に分割済みの `docs/data/towers/`（1,915〜7,808字）・`docs/data/skills/`（1,916〜3,906字）は、**全ファイルが8,000字未満**に収まっている。一方、未分割の `game_spec.md`（35,042字）・`tech_spec.md`（27,052字）は上限の3〜4倍。
適切に分割された「1テーマ」の自然なサイズが8,000字であることを、本リポジトリの実績が示している。

## 4. セクション粒度

| 対象 | 上限 | 超過時の対処 |
|------|------|-------------|
| H2（`##`）セクション | 2,000字 | H3へ分割、またはセクションごと子ファイルへ切り出す |
| H3（`###`）セクション | 1,000字 | 表への置き換え、または記述の圧縮 |

- 1ファイルの H2 は **7個以内**（多すぎる場合は複数テーマの混在を疑う）
- 見出し階層は **H3まで**。H4が必要になったら子ファイルへ分割する

## 5. 記述スタイル

文字数を増やさないための記述ルール。

- **表を優先**: 列挙的な情報（数値・パラメータ・API一覧）は散文ではなく表で書く
- **1行1事実**: 1つの箇条書きに複数の事実を詰め込まない
- **重複禁止**: 同じ数値・仕様を複数ファイルに書かない。正となるファイルを1つ決め、他はリンクする
- **前置き禁止**: 「〜について説明します」等の導入文を書かない
- **コード例は最小限**: 完全なコードではなく、構造が分かる最小の抜粋にする
- **変更履歴を各ファイルに書かない**: [changelog.md](changelog.md) へ集約する（§5.1）

### 5.1 変更履歴は1ファイルへ集約する

**個々のドキュメントに変更履歴セクションを置かない。** 改稿時は [changelog.md](changelog.md) の先頭（最新日付ブロック）へ `| ファイル | 内容 |` を1行追記する。

理由 — 変更履歴は**本文が増えなくても単調増加する**唯一の要素であり、文字数予算を静かに食い潰す。

| | 移行前 | 移行後 |
|---|-------|-------|
| `tech_spec.md` | 4,191字（履歴 **47%**） | 2,219字 |
| `game_spec.md` | 4,619字（履歴 **39%**） | 2,824字 |
| `open_specs.md` | 2,524字（履歴 **57%**） | 1,091字 |
| `CLAUDE.md` | 2,987字（上限3,000の**残99.6%消費**） | 2,520字 |

索引ファイルほど本文が短く、かつ§6の「履歴は親に集約」で子の履歴まで集まるため、**履歴が本文を上回る**状態に陥っていた。集約先の `changelog.md` は上限対象外（§2）とし、通常の作業では読み込まない。完全な履歴は Git（`git log -- <path>`）が持つため、changelog は人間向けの一覧に徹する。

## 6. 分割パターン

### 6.1 ハブ&スポーク（推奨・本プロジェクトの標準形）

親を索引（区分B）にし、詳細を子ファイル（区分C）へ移す。`docs/data/towers/` が既にこの形。

```
docs/data/towers/
├── TOWERS_OVERVIEW.md   # 索引: 全塔の一覧表・共通ルール
├── 001_ゴブリンの塔.md   # 詳細: 1塔 = 1ファイル
└── 002_森の塔.md
```

### 6.2 サブシステム分割

機能単位で切り出す。例: `game_spec.md` の §2.x（キャラクター・戦闘・装備…）を1機能1ファイルへ。

### 6.3 レイヤー分割

同一テーマを抽象度で分ける。例: `tech_spec.md` → データ設計 / API設計 / アーキテクチャ方針。

### 分割時の必須事項

1. 親ファイルに子ファイルへの**リンク表**を残す（リンク切れ = 情報の喪失）
2. 親から移した内容は親から**削除**する（重複させない）
3. **節番号は維持**する（`§2.4` を子ファイル側でも `2.4` のまま使う）。既存のリンク・アンカー・レビュー指摘の参照が生き残る
4. **変更履歴は親にも子にも置かない**（§5.1）。分割した旨は [changelog.md](changelog.md) へ1行記録する
5. 子ファイルのヘッダに **親へのリンク**と担当節を明記する
6. [README.md](../README.md) のドキュメント索引と、`.claude/project/**` の対象ファイル一覧を更新する
7. リンク切れがないことを確認する（相対パスは移動先を基準に張り直す）

## 7. 判定方法

```bash
python scripts/check_doc_size.py          # 判定（新規の上限超過があれば exit 1）
python scripts/check_doc_size.py --list   # 全ファイルの文字数一覧
python scripts/check_doc_size.py --sections  # H2セクションの文字数も表示
```

- ドキュメントの新規作成・改稿時に実行する
- `doc-review`・`diagrams-review` スキルの判定項目に含める
- 上限超過は **すべて ERROR**（exit 1）。既知超過を猶予する `KNOWN_OVERSIZED` は §8 の是正完了により空
- 変更履歴セクションの復活も **ERROR**（§5.1）。スクリプトが `## 変更履歴` 等の見出しを検出する

## 8. 分割実績（2026-08-02 完了）

制定時に上限を超えていた8ファイルは、すべて索引 + 個別ファイルへ分割済み。

| 元ファイル | 分割前 | 分割後（索引） | 子ファイル |
|-----------|-------|--------------|-----------|
| `docs/design/game_spec.md` | 35,042 | 4,242 | `design/systems/` 7件（3,235〜6,902） |
| `docs/tech/tech_spec.md` | 27,052 | 2,663 | `tech/tech_{data,structure,api,architecture,logging}.md` 5件（3,550〜6,774） |
| `diagrams/api_sequence.md` | 19,311 | 887 | `api_sequence/` 6件（2,101〜4,840） |
| `docs/data/master_data.md` | 19,273 | 3,470 | `data/master/` 5件（1,673〜5,302） |
| `diagrams/class_diagram.md` | 15,301 | 980 | `class_diagram/` 3件（4,302〜5,932） |
| `diagrams/battle_flow.md` | 11,592 | 641 | `battle_flow/` 4件（1,663〜5,522） |
| `diagrams/er_diagram.md` | 10,978 | 859 | `er_diagram/` 3件（2,528〜5,279） |
| `docs/tech/tech_battle_offline.md` | 8,445 | 5,529 | `tech_offline.md`（3,278）。オフライン計算を分離し `tech_battle.md` へ改名 |

- 全81ファイルが上限内（`python scripts/check_doc_size.py` が exit 0）
- 索引ファイル・子ファイルとも節番号を維持している（§6「分割時の必須事項」）

### 残課題

- H2セクションの2,000字上限（§4）を超える箇所が残る。Mermaid図1枚で構成されるセクション（`class_diagram/`・`er_diagram/` 等）は分割しても可読性が上がらないため許容し、`--sections` の WARN として扱う
- `docs/reviews/**` の過去レポートに、ディレクトリ再編前のリンク切れが残る（規約の適用対象外・追記型アーカイブのため修正しない）
