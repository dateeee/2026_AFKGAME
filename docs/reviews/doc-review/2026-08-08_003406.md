### ISSUE-1201: `potionThreshold` の入力検証範囲が `tech_security.md` だけ 0〜1 で、他5箇所の 0.1〜0.5 と食い違う

| 項目 | 値 |
|------|-----|
| カテゴリ | 整合性 |
| 重要度 | 中 |
| 関連ファイル | docs/tech/nonfunctional/tech_security.md, docs/tech/basic/tech_db/player.md, docs/tech/basic/tech_data.md, docs/glossary.md |
| 該当箇所 | tech_security.md §11.3 行59 / tech_db/player.md 行37 / tech_data.md 行47 / glossary.md 行83 |
| 検出可能工程 | 基本設計（DB設計セグメント2/3 の `player_settings` 確定時） |

**問題の説明:**

`tech_security.md` §11.3「入力バリデーション方針」の制約表は、`hpThreshold` と `potionThreshold` を同じ行にまとめて範囲を1つだけ与えている。

```
| `hpThreshold` / `potionThreshold` | 0〜1 の小数（刻みは仕様どおり） |
```

しかし `potionThreshold` の範囲は 0.1〜0.5 であり、次の4箇所が一致して 0.1〜0.5 を宣言している。

- `docs/tech/basic/tech_db/player.md:37` — `| `potion_threshold` | `FLOAT` | 不可 | `0.3` | ポーション使用HP閾値（0.1〜0.5） |`
- `docs/tech/basic/tech_data.md:47` — `"potionThreshold": 0.3,            // ポーション自動使用閾値（0.1〜0.5、0.1刻み。デフォルト0.3）`
- `docs/glossary.md:83` — `ポーション自動使用のトリガーHP%（10%〜50%、10%刻み。デフォルト30%）`
- `diagrams/er_diagram/player.md:86` — `float potion_threshold "0.1-0.5, default 0.3"`

`hpThreshold` 側は 0.0〜1.0（`tech_db/player.md:21`・`tech_data.md:18`・`tech_api.md:48`）で正しい。同§の冒頭が「**サーバー側の検証が唯一の防御線**」と宣言している表なので、この行をそのまま Pydantic の `Field(ge=, le=)` に落とすと `potionThreshold=0.9` が通り、DB定義書の範囲を破った値が保存される。括弧書きの「刻みは仕様どおり」は刻み幅だけを委譲しており、上下限までは委譲していない。

**修正案:**

- `docs/tech/nonfunctional/tech_security.md` §11.3 の表で当該行を2行へ分割する。

  ```
  | `hpThreshold` | 0.0〜1.0 の小数 |
  | `potionThreshold` | 0.1〜0.5 の小数（0.1刻み。正は [tech_db/player.md](../basic/tech_db/player.md) §2） |
  ```

- `docs/spec_ownership.md` §2 に「ポーション使用HP閾値の範囲・刻み」の正として `docs/tech/basic/tech_data.md` を登録し、`tech_security.md`・`tech_db/player.md`・`glossary.md` を従に列挙する（同じ範囲が4ファイルに散っており、`check_docs.py --owner` の検出対象に載っていない）。

### ISSUE-1204: 一意制約名 `uq_shop_daily_slot_index` が `tech_db.md` §2 の命名規約に反する

| 項目 | 値 |
|------|-----|
| カテゴリ | 規約 |
| 重要度 | 中 |
| 関連ファイル | docs/tech/basic/tech_db/item.md, docs/tech/basic/tech_db.md |
| 該当箇所 | tech_db/item.md §5 行89・§7 行115 / tech_db.md §2 行28 |
| 検出可能工程 | `python scripts/check_schema_triple.py --naming`（本レビューで検出済み。常設化済みのため再発は自動検出される） |

**問題の説明:**

`tech_db.md` §2 の命名規約は一意制約名を `uq_<テーブル名>_<列>_<列>` と定め、例に `uq_tower_clear_records_player_tower` を挙げている。テーブル名は複数形（同§）なので `shop_daily_slots` が入るべきだが、定義書の実際の宣言は単数形になっている。

```
一意制約: `uq_shop_daily_slot_index` = (`shop_daily_state_id`, `slot_index`)
```

`check_schema_triple.py --naming` が次を出力する。

```
ERROR docs/tech/basic/tech_db/item.md:69 `shop_daily_slots`: 一意制約名 `uq_shop_daily_slot_index` が命名規約に反する（tech_db.md §2: uq_<テーブル名>_<列>_<列> → `uq_shop_daily_slots_...` で始まる必要がある）
```

定義書内の他の一意制約はすべて規約どおり（`uq_tower_clear_records_player_tower`・`uq_party_members_player_slot`・`uq_learned_skills_character_skill`・`uq_active_skill_slots_character_slot`・`uq_inventory_items_player_item`・`uq_facilities_player_type`・`uq_boss_rush_milestones_state_wave`）で、本件のみが例外。定義書は例外である旨の注記も持たない（`battle_logs.timestamp` は §1 で `_at` 規約の例外と明記してある、という前例がある）。

**修正案:**

本テーブルは**実装済み**（`backend/app/models/shop.py` `ShopDailySlot`）のため、改名は models と SQLite の制約名変更（SQLite は制約の直接 RENAME ができずテーブル再構築が必要）を伴う。`fix-specs` で仕様書だけを書き換えると仕様↔コードの乖離が生じるため、**次のどちらかをユーザーが選ぶ**前提で修正する。

- **案A（規約へ揃える・推奨）**: `docs/tech/basic/tech_db/item.md:89` と `:115` を `uq_shop_daily_slots_state_slot` へ改名し、`docs/known_issues.md` §2 へ「`models/shop.py` の制約名を定義書へ追従させる（Alembic のテーブル再構築マイグレーションが必要）」を1行追加する。図（`diagrams/er_diagram/item.md`）に制約名の記載は無いため図の修正は不要。
- **案B（現名を正として例外化）**: `docs/tech/basic/tech_db/item.md:89` の直後に、`battle_logs.timestamp`（`tech_db/battle.md:18`）と同じ書き方で「一意制約名の複数形規約（親 §2）の**例外**で、実装済みのため現名を正とする」と注記する。あわせて `scripts/check_schema_triple.py` の `--naming` が本件を除外できるよう、例外リストの追加を検討する（現状は exit 1 のままになる）。
