### ISSUE-003: バックアップ方式が §12.1 と §12.5 で別のものになっている

| 項目 | 値 |
|------|-----|
| カテゴリ | 整合性 |
| 重要度 | 高 |

**問題の説明:**

`non_functional_requirements.md` §3 は正を1箇所に指名している。

```
- バックアップ・リストアの方式と検証頻度は [tech_operations.md §12.5](../tech/tech_operations.md)
```

その §12.5 は次のとおり。

```
| 方式 | SQLite: `VACUUM INTO` でのファイルコピー（稼働中でも整合が取れる）／PostgreSQL: `pg_dump` |
| 保管先 | アプリ稼働ノードとは別のストレージ |
```

一方、今回追加された §12.1「本番構成（AWS）」表は別方式を書いている。

```
| バックアップ | EBS の日次スナップショット。RPO 24時間を満たす |
```

EBS スナップショット（ボリューム単位）と `VACUUM INTO`（DBファイル単位）は別の手段であり、両立させるのか置き換えるのかが読み取れない。§12.5 が正と指名されている以上、§12.1 の記述が競合している。

**修正案:**

- `docs/tech/tech_operations.md` §12.1（28行目）のバックアップ行を、構成の所在のみに留める:
  `| バックアップ | EBS スナップショットの取得先として EC2 の EBS を使用する。取得方式・頻度・保持期間は §12.5 が正 |`
- そのうえで §12.5 の「方式」行に AWS 前提を反映し、二方式の関係を1箇所で確定させる。いずれかを選ぶ:
  - (a) `方式 | SQLite: `VACUUM INTO` でファイルへ書き出し、S3 へ転送／PostgreSQL: `pg_dump`` とし、EBS スナップショットは併用しない
  - (b) `方式 | EBS 日次スナップショット（ボリューム全体）。論理バックアップとして SQLite は `VACUUM INTO`、PostgreSQL は `pg_dump` を併用する` と明記する
- §12.5 の「保管先」行が「アプリ稼働ノードとは別のストレージ」のままで AWS 構成を満たすか確認し、満たすなら `（EBS スナップショットは S3 に保管されるため本要件を満たす）` と補足する

**問題の説明:**

正は `tech_auth.md` 34行目（`ゲストアカウントの有効期限: 90日`）で、`tech_operations.md` §12.6 は環境変数 `GUEST_ACCOUNT_EXPIRE_DAYS` とともに再掲している。これに加えて要件側にも実数値が2箇所ある。

```
（non_functional_requirements.md 92行目） | ゲストデータの消滅 | 最終アクセスから90日で自動削除される（[tech_auth.md](...)）… |
（operation_requirements.md 62行目）      - ゲスト削除の事前告知には使えない（90日間アクセスのないプレイヤーには届かないため）…
```

`operation_requirements.md` 62行目はリンクを伴わずに数値だけを再掲しており、`.claude/project/requirements.md` §3 の観点4「数値の一意性（正を1つ決めて他はリンク）」に反する。期限値を変更した際の追随漏れになる。

**修正案:**

- `docs/design/operation_requirements.md` 62行目から実数値を外す:
  `- ゲスト削除の事前告知には使えない（**一定期間アクセスのないプレイヤー**には届かないため。期限は [tech_auth.md](../tech/tech_auth.md) が正）。緩和策は [non_functional_requirements.md](non_functional_requirements.md) §5 が正`
