### ISSUE-101: 戦闘ログのキーが snake_case で、APIボディの camelCase 規約と乖離

| 項目 | 値 |
|------|-----|
| カテゴリ | フロント・バック統合整合性 |
| 重要度 | 中 |
| 関連ファイル | backend/app/services/battle_service.py, frontend/src/types/game.ts, docs/tech/tech_api.md |
| 該当箇所 | battle_service.py 行261・411 / game.ts 行86〜105 / tech_api.md 行12 |
| 検出可能工程 | 本レビュー（常設スクリプト化を提案。「プロセスへの還元」参照） |

**問題の説明:**

`tech_api.md` はレスポンスボディのキー命名を例外なく camelCase と定めている。

> | ボディのキー | **camelCase**（バックエンドは `CamelModel` で snake_case ↔ camelCase を自動変換） |

しかし戦闘ログは `CamelModel` ではなく素の dict で組み立てられており、snake_case のまま返却されている。

```python
# backend/app/services/battle_service.py 行257〜261
"actor": character.name,
...
"target_hp": player.current_enemy_hp,
```

フロント側も snake_case を受ける型定義になっており、両側で辻褄は合っているが規約からは外れている。同一 interface 内に camelCase と snake_case が混在する。

```typescript
// frontend/src/types/game.ts 行82〜105
 * NOTE: battle_logsはCamelModel変換対象外。バックエンドからsnake_caseのまま返却される
export interface BattleLogEntry {
  type: string
  actor?: string
  max_hp?: number      // ← snake_case
  enemy_hp?: number    // ← snake_case
  exp_lost?: number    // ← snake_case
  target_hp?: number   // ← snake_case
```

**通信は失敗しない**（両側が snake_case で一致しているため）が、`tech_api.md` の規約に例外が明記されていないため、規約どおり camelCase を期待する実装を後から足すと壊れる。

**修正案:**

方針の判断が必要（**勝手に決めず、以下の判断材料で選択する**）。

- **案A（実装を仕様へ合わせる）**: 戦闘ログエントリを `BattleLogEntry(CamelModel)` としてスキーマ化し、`battle_service.py` の dict 生成を置き換える。フロントは `types/game.ts` の `max_hp` / `enemy_hp` / `exp_lost` / `gold_lost` / `target_hp` を camelCase へ、`GameView.vue:122` の `entry.target_hp` 参照も追随。ログはDBにJSONで保存されるため**既存保存データのキー移行が必要**（マイグレーションか読み出し時の互換処理）
- **案B（仕様書を実装に合わせる）**: `tech_api.md` 行12 の表に「例外: `battleLogs` の各エントリは snake_case（DB保存形式をそのまま返すため）」を追記する。移行コストはゼロだが、規約に例外が1件増える

案Bが低コストだが、`tech_data.md` の `GameStateResponse` 構造とも突き合わせたうえで決めること。

### ISSUE-102: 必要EXPの計算式がフロントエンドに再実装されている

| 項目 | 値 |
|------|-----|
| カテゴリ | フロント・バック統合整合性 |
| 重要度 | 中 |
| 関連ファイル | frontend/src/views/GameView.vue, backend/app/master_data/characters.py, backend/app/schemas/player.py, docs/data/master/character.md |
| 該当箇所 | GameView.vue 行66 / characters.py 行26〜28 / player.py 行14〜25 |
| 検出可能工程 | 本レビュー（常設スクリプト化を提案。「プロセスへの還元」参照） |

**問題の説明:**

必要EXPの計算式が**フロントとバックの両方に**書かれている。正は `docs/data/master/character.md` 行72。

> 計算式: `required_exp = 100 * (level ^ 1.5)`

```python
# backend/app/master_data/characters.py 行26〜28
def required_exp(level: int) -> int:
    return int(100 * (level ** 1.5))
```

```typescript
// frontend/src/views/GameView.vue 行66
const expRequired = computed(() => hero.value ? Math.floor(100 * Math.pow(hero.value.level, 1.5)) : 100)
```

`CharacterResponse`（`schemas/player.py` 行14〜25）に必要EXPを返すフィールドが無いため、フロントはEXPバーを描くために式を再実装せざるを得ない状態にある。

これは以下に抵触する。

- **不変条件6「データ駆動」**（[profile.md](../../../.claude/project/profile.md) §5）: マスターデータの数値 `100` `1.5` がフロントのコードに直接埋まっている
- **観点12**（[review-fullstack.md](../../../.claude/project/review-fullstack.md) §3）: フロントがビジネスロジックを持たない。例外は `useBattleLocal.ts` のみ

現時点では `int()` と `Math.floor()` が正の値に対して同一結果を返すため**表示は正しい**。ただしバランス調整で式を変えると、バックエンドのレベルアップ判定とフロントのEXPバー表示が無言で食い違う。

**修正案:**

- **バックエンド**: `schemas/player.py` の `CharacterResponse` に `exp_to_next: int` を追加し、`services/game_state_builder.py` で `required_exp(character.level)` の結果を詰める
- **フロントエンド**: `types/game.ts` の `Character` に `expToNext: number` を追加。`GameView.vue` 行66 の `expRequired` を `hero.value?.expToNext ?? 100` へ置き換え、`Math.pow` の式を削除する
- **仕様書**: `tech_data.md` の `GameStateResponse` 構造へ `expToNext` を追記する

### ISSUE-111: `tech_polling.md` §6 の是正対象5件が未着手のまま Phase 2 製造完了と判定されている

|-------------|---------|
| in-flightフラグなし（再入可能） | `inFlight` / `isTicking` 等の該当ゼロ。`setInterval(tick, …)` と `handleVisibilityChange` の `tick()` が排他なしで重なりうる |

これは**不変条件2「ハイブリッドtick制」の実装水準**に関わる。特に多重タブは、2タブ開くと両方が毎分tickを投げ、サーバー側排他（`tech_tick.md` §3）により一方が `503 BATTLE_TICK_BUSY` を受けて**接続エラーバナーが出る**。`tech_polling.md` §5 分岐一覧 #1・#3・#4・#5 は現状の実装では満たせない。

にもかかわらず `development_process.md` §5 は Phase 2 製造を「完了」、§4 製造完了ゲートも通過済みとしている。§6 が「製造工程の是正対象」と明記している以上、**5件が残る状態で製造完了と判定したのは矛盾**。さらにこれらは `known_issues.md` §2 にも登録されていないため、**どの管理台帳からも追跡されていない**。

**修正案:**

- **管理**: `tech_polling.md` §6 の5件を `known_issues.md` §2 へ登録し、対応Phaseを明示する（仕様書側に是正対象表を置くと完了判定から漏れるため、台帳へ移す）
- **フロントエンド（優先度順）**:
  1. in-flightフラグ: `usePolling` に `let inFlight = false` を持ち、`tick()` の冒頭で真なら即return、`finally` で解放する（§2）
  2. `lastTickAt` を保持し、`visible` から5秒以内の即時tickを抑止する（§2）。ISSUE-106 のカウントダウンと同じ値を使う
  3. `window.addEventListener('focus', …)` を追加し、直近tickから60秒以上経過していれば即時tickする（§3）
  4. `updatedState` の必須フィールドを検証し、欠落時はどのストアも更新せずエラー扱いにする（§4）
  5. 多重タブのリーダー選出（`BroadcastChannel('afkgame')` + `localStorage` フォールバック、リース90秒）を実装する（§2.1）。最も規模が大きいため、1〜4とは分けて着手する
- **プロセス**: `development_process.md` §5 の Phase 2 製造の記述に、未着手の是正対象がある旨を反映する（または5件を解消してから「完了」とする。**どちらを取るかの判断が必要**）
