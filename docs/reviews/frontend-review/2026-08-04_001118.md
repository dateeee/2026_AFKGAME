### ISSUE-801: 設定「戦闘ログ表示件数」が表示に反映されない

| 項目 | 値 |
|------|-----|
| カテゴリ | エラーハンドリング・UX |
| 重要度 | 高 |
| 関連ファイル | frontend/src/views/GameView.vue, frontend/src/stores/battleStore.ts, frontend/src/views/SettingsView.vue |
| 該当箇所 | GameView.vue 行77 / battleStore.ts 行6 |
| 検出可能工程 | 本レビュー |

**問題の説明:**
SettingsView は `battleLogCount`（20/50/100件）を保存し、サーバーにも永続化されるが、表示側はこの値を一切参照していない。GameView.vue 行77 は

```ts
const visibleLogs = computed(() => battleStore.battleLogs.slice(-10))
```

と固定10 tick分のみを表示し、battleStore の保持上限も `MAX_FRONTEND_LOGS = 100`（tick数）で固定。設定を変更しても画面の表示件数は変わらず、設定UIが機能していない（grep で `battleLogCount` の参照は保存系のみ）。

**修正案:**
- GameView.vue の `visibleLogs` を `battleStore.battleLogs.slice(-gameStore.settings.battleLogCount)` のように設定値参照へ変更する（「件」の単位が tick 群か行かは ui.md の定義に合わせる。行単位なら flatten 後に slice する）

### ISSUE-803: セッション失効（リフレッシュ不能）後も認証状態が残り、ログイン画面へ誘導されない

| 項目 | 値 |
|------|-----|
| カテゴリ | 状態管理 |
| 重要度 | 中 |
| 関連ファイル | frontend/src/api/client.ts, frontend/src/stores/authStore.ts, frontend/src/composables/usePolling.ts |
| 該当箇所 | client.ts 行110〜119（sendWithAuth）・行68〜90（tryRefresh） / usePolling.ts 行47〜49 |
| 検出可能工程 | 本レビュー |

**問題の説明:**
リフレッシュトークンが失効・無効化された場合、`tryRefresh` は `clearTokens()` するが `authStore.user` はリセットされず、`sendWithAuth` は `ApiError('認証に失敗しました', 'AUTH_REFRESH_FAILED', 401)` を投げる。usePolling はこれを `setConnectionError` で通信断バナーとして表示するだけでポーリングを止めず、以後60秒ごとに失敗リクエストと赤バナーが続く。router guard は `user` が残っているため通過し、ページをリロードするまでログイン画面へ誘導されない。

**修正案:**
- usePolling / gameStore で `error.code === 'AUTH_REFRESH_FAILED'` を判別し、`authStore.logout()`（ローカルクリアのみ）→ `router.push({ name: 'login' })` を実行する。あわせて sendWithAuth 失敗時にポーリングを停止する

### ISSUE-804: 塔一覧（targetFloorCap・最高到達階）がマウント時のまま更新されない

**問題の説明:**
`gameStore.loadTowers()` は GameView の `onMounted` で1回だけ呼ばれ、`towers[].targetFloorCap` はその時点の値で固定される。攻略中に最高到達階が伸びても（`towersCleared` はポーリングで更新される）、塔選択UIに戻ったときの目標階上限 `targetFloorCap` は古いままで、実際には選べるはずの階が NumberStepper の max 制限（行310）により選択できない。ページリロードまで回復しない。

### ISSUE-806: ポーリング tick に多重実行ガードがない

| 項目 | 値 |
|------|-----|
| カテゴリ | パフォーマンス |
| 重要度 | 低 |
| 関連ファイル | frontend/src/composables/usePolling.ts |
| 該当箇所 | usePolling.ts 行30〜50・行52〜56 |
| 検出可能工程 | 本レビュー |

**問題の説明:**
`setInterval(tick, 60_000)` は前回の tick 応答を待たずに次を発火する。応答が60秒を超えて遅延した場合（オフライン復帰直後の大量tick処理等）、`POST /api/battle/tick` が並行実行され、応答順によっては新しい状態が古い応答で上書きされうる。

**修正案:**
- `let inFlight = false` を導入し、tick 実行中は次の発火をスキップする（または直列化する）

### ISSUE-807: ShopView のエラーハンドリングが他画面と不統一（通信断がバナーに出ない）

| 該当箇所 | ShopView.vue 行67〜76・行88〜112 |

**問題の説明:**
他画面（GameView / EquipmentView / SettingsView）は `gameStore.reportActionFailure` で通信断→ConnectionBanner、業務エラー→インライン表示に振り分けるが、ShopView は独自の `message` にすべて格納する。通信断でもバナーが出ず、成功フラッシュ（`flash()`）と同じ場所・見た目（`role="status"`）で表示されるため、エラーの扱いが画面間で食い違う。

### ISSUE-808: 型の緩み（TowerMode を string で受け渡し）とマスターデータIDのハードコード

| 項目 | 値 |
|------|-----|
| カテゴリ | コード品質 |

| 該当箇所 | client.ts 行182・行197 / gameStore.ts 行20 / GameView.vue 行22 |
| 検出可能工程 | 本レビュー |

**問題の説明:**
`Player.towerMode` は `'auto_repeat' | 'stop_on_clear'` のユニオン型が定義済み（types/game.ts 行8）だが、`postTowerSelect(..., mode: string)`・`putTowerMode(mode: string)`・`gameStore.towerMode = ref<string>` は素の string で受けており、タイポをコンパイル時に検出できない。また GameView.vue 行22 の `selectedTowerId = ref('goblin_tower')` は塔IDのハードコードで、初期選択が towers 一覧から導出されていない。
