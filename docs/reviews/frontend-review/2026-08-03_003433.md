### ISSUE-001: fetchWithRetry がエラー種別を問わず3回リトライし、エラー表示の遅延と非冪等POSTの二重実行リスクを生む

| 項目 | 値 |
|------|-----|
| カテゴリ | エラーハンドリング・UX |
| 重要度 | 高 |
| 関連ファイル | frontend/src/api/client.ts |
| 該当箇所 | client.ts 行89〜117 |
| 検出可能工程 | 本レビュー |

**問題の説明:**

```ts
if (!response.ok) {
  throw new Error(`サーバーエラー (${response.status})`)
}
...
} catch (error) {
  lastError = error as Error
  if (attempt < MAX_RETRIES - 1) {
    await new Promise(resolve => setTimeout(resolve, BASE_DELAY_MS * Math.pow(2, attempt)))
  }
}
```

`!response.ok` の throw が catch に拾われ、**4xx の業務エラーも指数バックオフ（1秒+2秒）で3回再送**される。影響:

1. ゴールド不足・売り切れ等の応答が確定しているのに、ユーザーへのエラー表示が約3秒遅れる
2. `POST /shop/buy`・`/equipment/sell`・`/battle/tick` は非冪等。ネットワーク断で「サーバー側は成功・応答だけ喪失」の場合に再送され、**二重購入・二重売却**が起こりうる
3. 401 でリフレッシュ失敗時の `throw new Error('認証に失敗しました')`（行103）も catch に拾われ、無意味に2回リトライされる

**修正案:**

- `response.ok === false` の場合はリトライせず即時 throw する（リトライ対象は fetch 自体の失敗 = ネットワークエラーのみに限定）
- 非冪等な POST/PUT はネットワークエラーでも自動再送しない（GET のみリトライ可とするか、呼び出し側でオプトイン）
- 行103 の認証失敗 throw はループ外へ出して即時失敗させる

### ISSUE-002: エラーレスポンスの解析がバックエンドの統一形式 `{error: {code, message}}` と不一致で、業務メッセージがユーザーに届かない

| 項目 | 値 |
|------|-----|
| カテゴリ | エラーハンドリング・UX |
| 重要度 | 高 |
| 関連ファイル | frontend/src/api/client.ts, frontend/src/api/auth.ts |
| 該当箇所 | client.ts 行106〜108 / auth.ts 行16〜19 |
| 検出可能工程 | 結合テスト（L2 にエラーパスのシナリオがあれば検出できた） |

**問題の説明:**

バックエンドは全例外を `{"error": {"code": ..., "message": ...}}` に統一している（backend/app/exceptions.py）。しかしフロントは:

```ts
// client.ts — bodyを読まない
throw new Error(`サーバーエラー (${response.status})`)
// auth.ts — 存在しないキーを参照（FastAPI素のdetail形式を想定）
throw new Error(body.detail || `HTTP ${response.status}`)
```

結果、ログイン失敗は「HTTP 401」、登録済みメールは「HTTP 409」、日替わりショップの売り切れ（`SHOP_ITEM_SOLD_OUT`「この商品は売り切れです」）は「サーバーエラー (400)」と表示され、**サーバーが用意した日本語メッセージとエラーコードが一切使われない**。LoginView の `authStore.error` 表示・ShopView の `message` 表示の両方に波及する。

**修正案:**

- 両ファイルで `const body = await response.json().catch(() => null)` を読み、`body?.error?.message`（表示用）と `body?.error?.code`（分岐用）を持つエラー型（例: `ApiError extends Error { code: string }`）を throw する
- 呼び出し側（ShopView 等）は code で分岐できるようにする（ISSUE-001 の修正と同時に行う）

### ISSUE-003: ログアウトがどのUIからも呼ばれず、実行時のクリーンアップ（ポーリング停止・ストアリセット）も無い

### ISSUE-004: タブ復帰時の visibilitychange 処理が認証状態・従前の稼働状態を無視して tick と polling を開始する

| 項目 | 値 |
|------|-----|
| カテゴリ | パフォーマンス |
| 重要度 | 中 |
| 関連ファイル | frontend/src/composables/usePolling.ts |
| 該当箇所 | usePolling.ts 行50〜59 |
| 検出可能工程 | 本レビュー |

**問題の説明:**

```ts
function handleVisibilityChange() {
  if (document.hidden) {
    stop()
  } else {
    tick()
    start()
  }
}
```

usePolling は App.vue（useGameLoop 経由）で常時インスタンス化されるため、**未認証でログイン画面を開いたままタブを切り替えて戻るだけで** `tick()` が実行され、401 → 「認証に失敗しました」の赤バナーが表示され、さらに 60秒ポーリングが開始される。また一時停止前に polling が動いていなかった場合（初期化前）でも復帰時に無条件で開始される。

**修正案:**

- 復帰時は「非表示になる前に稼働していた場合のみ」再開する: `stop()` の前に `wasActive = isActive.value` を保存し、復帰側は `if (!wasActive) return` でガード
- あわせて `useAuthStore().isAuthenticated` が false なら何もしない

### ISSUE-005: 設定更新・装備売却に try/catch がなく、API失敗が未処理Promise拒否になる（フィードバック・ロールバックなし）

| 項目 | 値 |
|------|-----|
| カテゴリ | エラーハンドリング・UX |
| 重要度 | 中 |
| 関連ファイル | frontend/src/views/SettingsView.vue, frontend/src/components/equipment/EquipmentInventory.vue |
| 該当箇所 | SettingsView.vue 行38〜64 / EquipmentInventory.vue 行70〜77 |
| 検出可能工程 | 本レビュー |

**問題の説明:**

SettingsView の更新4関数は先にストアを楽観更新してから `await putSettings(...)` するが try/catch がない。API 失敗時（ISSUE-001 のリトライ後 throw）は unhandled rejection となり、画面には何も表示されず、ストアはサーバーと不一致のまま残る。EquipmentInventory の `sellSelected` も同様で、売却失敗時にエラー表示がない（観点8: APIエラー時のフィードバック）。

**修正案:**

- 各関数を try/catch で包み、失敗時は (1) ストア値を元に戻す、(2) ユーザーへエラーを表示する（`gameStore.setConnectionError` か、ISSUE-011 の業務エラー表示手段）
- `sellSelected` は失敗時に選択状態を保持したままエラーを表示する

### ISSUE-006: 装備の装着がローカルの equipped のみ更新し、サーバー側の連動解除（両手武器→盾）が最大60秒反映されない

| 項目 | 値 |
|------|-----|
| カテゴリ | 状態管理 |
| 重要度 | 中 |
| 関連ファイル | frontend/src/stores/equipmentStore.ts, frontend/src/views/EquipmentView.vue |
| 該当箇所 | equipmentStore.ts 行75〜78 |
| 検出可能工程 | 本レビュー |

**問題の説明:**

```ts
async function equipItem(characterId, slot, equipmentId) {
  await postEquip(characterId, slot, equipmentId)
  equipped.value[slot] = equipmentId   // 対象スロットのみ更新
}
```

サーバー側 `equip_item` は両手武器の装着時に盾スロットを自動解除するが、レスポンスは `{status: "ok"}` のみでフロントは対象スロットしか更新しない。大剣を装備した直後、盾は装備中のまま表示され、装備一覧からも消えたままになる。次の tick（最大60秒後）の `updated_state` でようやく一致する。

**修正案:**

- `equipItem` 成功後に `getGameState()` を再取得して `loadFromState` する（GameView の `enterTower` と同じ既存パターン。塔進入時と同頻度の操作なのでコストは許容範囲）
- 恒久策として equip API のレスポンスに更新後の `equipped` マップを含める案は API 変更を伴うため full-review で扱う
