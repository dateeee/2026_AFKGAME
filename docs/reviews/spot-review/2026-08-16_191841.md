## 指摘一覧

### ISSUE-1401: Phase 1〜2 における計画メンテナンスの告知手段が定義されていない

| 項目 | 値 |
|------|-----|
| カテゴリ | 網羅性 |
| 重要度 | 中（確度: 要検討） |
| 関連ファイル | docs/design/requirements/operation_requirements.md, docs/design/requirements/non_functional_requirements.md |
| 該当箇所 | operation_requirements.md §3「障害・メンテナンス時の扱い」表・§3.1「ゲーム内お知らせ要件」, non_functional_requirements.md §3「可用性」表 |
| 検出可能工程 | 要件定義（Phaseをまたぐ運用要件の突合。常設スクリプトでは検出できない） |

**問題の説明:**

`operation_requirements.md` §3 は計画メンテナンスの告知手段をPhaseの限定なしに定めている。

> | 計画メンテナンス | 事前にゲーム内お知らせで告知する。停止時間分の進行は復帰後のオフライン計算で回収される（`non_functional_requirements.md` §3） |

一方その告知手段そのものは §3.1 で Phase 3 の機能とされている。

> 告知手段として **Phase 3** で実装する。

§3.1 末尾の但し書きは、告知手段が無い期間の制約を**下方修正だけ**に限っている。

> - Phase 3 の実装完了までは告知手段を持たないため、**下方修正を伴う改定は行わない**

計画メンテナンスには触れていない。`non_functional_requirements.md` §3 は「計画メンテナンスの停止時間」を **24時間未満（必須制約）** として定義しており、メンテナンス自体は Phase 1〜2 でも発生しうる前提になっている。また `operation_requirements.md` §2 の「Phase進行によるスキーマ拡張」は Phase 1 → 2 の移行時にも生じるため、告知手段を持たない期間に計画停止が起きる経路が実在する。結果として、Phase 1〜2 で計画メンテナンスを行う場合の告知手段が要件のどこにも定義されていない。

**修正案:**

- `docs/design/requirements/operation_requirements.md` §3.1 末尾の箇条書き（「Phase 3 の実装完了までは告知手段を持たないため、下方修正を伴う改定は行わない」の行）へ、計画メンテナンスの扱いを1行追加する。次のいずれかを選ぶ:
  - **案A（告知手段を定める）**: `- Phase 1〜2 の計画メンテナンスは、ログイン画面への静的な告知文（デプロイで更新）で事前に掲示する`
  - **案B（実施しないと定める）**: `- Phase 1〜2 は告知手段を持たないため、計画メンテナンスを行わない（停止を伴う変更は Phase 3 の告知実装後に回す）`
- どちらの案も `docs/**` への1行追記のみで、`check_docs.py` / `check_doc_size.py` の判定に影響しない（`operation_requirements.md` は 3,286字・§3 は 1,191字で、いずれも上限に対して余裕がある）。案Aを採る場合は掲示先が `systems/ui/onboarding.md`「ログイン画面」の記載と矛盾しないことを併せて確認する。

> **反証の結果（確度: 要検討）**: 文書内の緊張（§3 の一般規定 vs §3.1 の Phase 3 実装）は原文で確認できたが、`operation_requirements.md` 冒頭が「実現方式は持たない。ジョブ・移行手順は `tech_maintenance.md`（§12.4〜§12.7）が正」と委譲しているため、**`docs/tech/nonfunctional/tech_maintenance.md` が Phase 1〜2 の暫定的な告知手段を定義している可能性を排除できていない**。修正の適用前に同ファイル §12.4〜§12.7 を確認すること。定義済みであれば、本指摘は「要件側からその手段への参照が無い」という参照漏れに縮小する。
