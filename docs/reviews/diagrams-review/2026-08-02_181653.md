### ISSUE-301: ログアウト導線が画面遷移図に存在しない

| 項目 | 値 |
|------|-----|
| カテゴリ | コードとの整合性 |
| 重要度 | 高 |
| 関連ファイル | diagrams/screen_transition/main_nav.md, diagrams/api_sequence/auth.md, frontend/src/stores/authStore.ts, backend/app/routers/auth.py |
| 該当箇所 | main_nav.md 98〜109行（`state 設定画面`）, api_sequence/auth.md 68〜74行 |

**問題の説明:**

APIシーケンス図に「ログアウト」フローが追加され、最終ステップを

```
B->>B: 保持中のトークンを破棄<br/>ログイン画面へ遷移
```

としている。実装側にも `POST /api/auth/logout`（`backend/app/routers/auth.py`）と `authStore.logout()`（`frontend/src/stores/authStore.ts:92`）が存在し、`tech_api.md:58` にもエンドポイントが定義されている。

しかし画面遷移図 `main_nav.md` の `state 設定画面` は

```
アカウント管理 : ゲスト→本登録バナー
...
退会 : 最下部に分離配置 (Phase 2~)
```

までで、**ログアウト項目も `設定画面 --> ログイン画面` の遷移も描かれていない**。`diagrams/` 全体を grep しても「ログアウト」は `api_sequence/auth.md` の2箇所のみで、遷移図側にどこからログアウトを実行するかの導線がない。

**修正案:**

- `diagrams/screen_transition/main_nav.md` の `state 設定画面` に、`退会` の直前へ1行追加する。

  ```
            ログアウト : 認証ユーザーのみ表示 (Phase 2~)
  ```

- 同ファイルの図の下の箇条書きに、退会の行（162行）と並べて追加する。

  ```markdown
  - ログアウト実行後も、退会と同様に認証フロー（[auth.md](auth.md)）のログイン画面へ戻る
  ```

- 参考: 仕様側（`docs/design/systems/ui.md`「アカウント欄（Phase 2〜）」）にもログアウト項目が無い。**仕様書のみの記載漏れは `doc-review` の担当**のため本レビューでは指摘として立てない（言及に留める）。

### ISSUE-302: `GET /api/abyss/ranking` を担当するルーターがどこにも定義されていない

| 項目 | 値 |
|------|-----|
| カテゴリ | 網羅性 |
| 重要度 | 中 |
| 関連ファイル | docs/tech/tech_structure.md, diagrams/system_architecture/application.md, diagrams/api_sequence/endgame.md |
| 該当箇所 | tech_structure.md 84〜95行（`routers/`）, application.md 73〜85行（`subgraph Routers`）, endgame.md 57〜73行（§11.7） |

**問題の説明:**

`tech_api.md:129` と APIシーケンス図 §11.7 は `GET /api/abyss/ranking` を定義しているが、`tech_structure.md` §2 の `routers/` 一覧にも、システム構成図の `Routers` サブグラフにも、このパスを持つルーターが無い。

- `boss_rush.py # ボスラッシュ・ランキング（Phase 5〜）` は `POST /api/boss-rush/start` / `retire` / `GET /api/boss-rush/ranking` を担当（application.md 83行）。FastAPI の `APIRouter(prefix=...)` は `/api/boss-rush` になるため `/api/abyss/ranking` は載らない
- `tower.py` は `/api/tower/*` のみ（application.md 77行）。深淵の塔の入塔は `/api/tower/*` を流用する仕様（endgame.md 59行）だが、ランキングだけプレフィックスが異なる

結果として「実装配置が未定のエンドポイント」が1件残っている。

**修正案:**

- `docs/tech/tech_structure.md` §2 の `routers/` に1行追加する（`boss_rush.py` の直後、`prestige.py` の前）。

  ```
  │   │   │   ├── abyss.py           # 深淵の塔ランキング（Phase 5〜）
  ```

- `diagrams/system_architecture/application.md` の `subgraph Routers` に、`bossRushRouter` の直後へノードを追加する。

  ```
            abyssRouter["abyss.py Phase5~\nGET /api/abyss/ranking"]
  ```

- `diagrams/api_sequence/endgame.md` §11.7 の冒頭引用に「ランキング取得のみ `abyss.py` が担当する」旨を追記する。

### ISSUE-304: システム構成図の Schemas に `SettingsResponse` が無い

| 項目 | 値 |
|------|-----|
| カテゴリ | 設計図間の整合性 |
| 重要度 | 低 |
| 関連ファイル | diagrams/system_architecture/application.md, diagrams/api_sequence/core.md, backend/app/schemas/player.py |
| 該当箇所 | application.md 107行, core.md 151行 |

**問題の説明:**

APIシーケンス図 §3.5 は `PUT /api/game/settings` の応答を

```
API-->>B: SettingsResponse<br/>(更新後の全設定値)
```

と明示している。実装も `@router.put("/settings", response_model=SettingsResponse)`（`backend/app/routers/game.py:32`）で、`backend/app/schemas/player.py:45` に `class SettingsResponse` が存在する。

一方システム構成図の `playerSchema` は

```
player.py\nPlayerResponse\nCharacterResponse\nGameStateResponse\nSettingsUpdate
```

で、リクエスト側の `SettingsUpdate` のみを挙げ、レスポンス側の `SettingsResponse` が抜けている。他の要素はすべてリクエスト／レスポンスの対で書かれているため、この箇所だけ非対称。

**修正案:**

- `diagrams/system_architecture/application.md` 107行の `playerSchema` ラベルに `SettingsResponse` を追加する。

  ```
            playerSchema["player.py\nPlayerResponse\nCharacterResponse\nGameStateResponse\nSettingsUpdate / SettingsResponse"]
  ```
