### ISSUE-601: ER図の一意制約の表現が3通りに分かれ、5テーブルで完全に欠落している

| 項目 | 値 |
|------|-----|
| カテゴリ | 仕様書との整合性 |
| 重要度 | 中 |
| 関連ファイル | diagrams/er_diagram/player.md, diagrams/er_diagram/item.md, diagrams/er_diagram/battle.md, docs/tech/basic/tech_db/player.md, docs/tech/basic/tech_db/item.md, docs/tech/basic/tech_db/battle.md |
| 該当箇所 | er_diagram/player.md 112・125〜127・147〜148・155〜156行、er_diagram/item.md 72〜73・88〜89行、er_diagram/battle.md 25・36〜37行 |

**問題の説明:**

定義書で宣言している一意制約9件に対し、ER図の `UK` タグの付け方が**3通りに分かれている**。

| # | テーブル | 定義書の一意制約 | ER図の `UK` |
|---|---------|----------------|------------|
| 1 | `tower_clear_records` | `uq_tower_clear_records_player_tower` = (`player_id`, `tower_id`) | **両列に付与** |
| 2 | `inventory_items` | `uq_inventory_items_player_item` = (`player_id`, `item_id`) | **両列に付与** |
| 3 | `party_members` | `uq_party_members_player_slot` = (`player_id`, `slot_index`) / `uq_party_members_player_character` = (`player_id`, `character_id`) | 先頭列のみ |
| 4 | `learned_skills` | `uq_learned_skills_character_skill` = (`character_id`, `skill_id`) | 先頭列のみ |
| 5 | `active_skill_slots` | `uq_active_skill_slots_character_slot` = (`character_id`, `slot_index`) | 先頭列のみ |
| 6 | `shop_daily_slots` | `uq_shop_daily_slot_index` = (`shop_daily_state_id`, `slot_index`) | **どちらにも無し** |
| 7 | `facilities` | `uq_facilities_player_type` = (`player_id`, `facility_type`) | **どちらにも無し** |
| 8 | `boss_rush_milestones` | `uq_boss_rush_milestones_state_wave` = (`boss_rush_state_id`, `wave`) | **どちらにも無し** |

さらに、定義書が列の備考欄で宣言している**単一列 UNIQUE 2件が ER図に反映されていない**。

- `tech_db/battle.md` `boss_rush_states.player_id`: 「FK → `players.id`、**UNIQUE**（1プレイヤーにつき1行）」
  → er_diagram/battle.md 25行: `uuid player_id FK "references Player.id"`（`UK` 無し）
- `tech_db/player.md` `prestige_bonuses.character_id`: 「FK → `characters.id`、**UNIQUE**（1キャラ1レコード）」
  → er_diagram/player.md 112行: `uuid character_id FK "references Character.id"`（`UK` 無し）

同じ 1:0..1 の関係でも `player_settings.player_id`（player.md 85行 `uuid player_id FK, UK`）は `UK` を付けており、表現が揃っていない。#6〜#8 は複合一意の存在自体が図から読み取れず、Phase 4〜5 の製造時に一意制約の実装漏れを招く。

**修正案:**

ER図の記法を「**複合一意は構成列すべてに `UK` を付け、先頭列のコメントに相手列を併記する**」（= #1・#2 の書き方）へ統一する。

- `diagrams/er_diagram/player.md`
  - 126行 `int slot_index "0-3 パーティ内位置"` → `int slot_index UK "0-3 パーティ内位置"`
  - 127行 `uuid character_id FK "references Character.id"` → `uuid character_id FK, UK "references Character.id"`
  - 148行 `string skill_id "マスター参照 SkillMaster.id（DB外部キーなし）"` → `string skill_id UK "マスター参照 SkillMaster.id（DB外部キーなし）"`
  - 156行 `int slot_index "0-1 セット枠番号"` → `int slot_index UK "0-1 セット枠番号"`
  - 112行 `uuid character_id FK "references Character.id"` → `uuid character_id FK, UK "references Character.id（1キャラ1レコード）"`
- `diagrams/er_diagram/item.md`
  - 72行 → `uuid shop_daily_state_id FK, UK "references ShopDailyState.id（slot_index と複合一意）"`
  - 73行 → `int slot_index UK "0-4 枠番号"`
  - 88行 → `uuid player_id FK, UK "references Player.id（facility_type と複合一意）"`
  - 89行 → `enum facility_type UK "tavern/forge/training_ground/warehouse/market"`
- `diagrams/er_diagram/battle.md`

### ISSUE-602: `inventory_items.item_id` が ER図でのみ `FK` タグを持つ（定義書・models は「FKなし」）

| 項目 | 値 |
|------|-----|
| カテゴリ | 仕様書との整合性 |
| 重要度 | 中 |
| 関連ファイル | diagrams/er_diagram/item.md, docs/tech/basic/tech_db/item.md, docs/tech/basic/tech_db.md, backend/app/models/item.py |
| 該当箇所 | er_diagram/item.md 36行 |
| 検出可能工程 | 基本設計 [basic-design.md](../../../.claude/project/basic-design.md) §4「DBスキーマ三者一致」（PK/FK/UK タグが照合対象外） |

**問題の説明:**

`tech_db.md` §4-6 は「マスターデータ（塔・敵・スキル・装備ベース）は…それらを指す列（`current_tower_id` `tower_id` `skill_id` 等）は**DB外部キーを張らず**、値の妥当性はサービス層が検証する」と定めている。`tech_db/item.md` の `inventory_items.item_id` も備考が「アイテムマスターの ID。**FKなし（親 §4-6）**」であり、`backend/app/models/item.py` も FK を張っていない。

```python
item_id: Mapped[str] = mapped_column(String(50), nullable=False)   # ForeignKey なし
```

しかし ER図だけが `FK` タグを付けている。

```
er_diagram/item.md 36行:
        string item_id FK, UK "references ItemMaster.id"
```

同じ「マスター参照だがFKを張らない」列は、ER図の他の6箇所ではすべて `FK` タグを外し `（DB外部キーなし）` と明記しており、本行だけが例外になっている。

| 列 | ER図の記述 |
|----|-----------|
| `players.current_tower_id` | `string current_tower_id "nullable, マスター参照 Tower.id（DB外部キーなし）"` |
| `tower_clear_records.tower_id` | `string tower_id UK "マスター参照 Tower.id（DB外部キーなし）"` |
| `learned_skills.skill_id` | `string skill_id "マスター参照 SkillMaster.id（DB外部キーなし）"` |
| `active_skill_slots.skill_id` | `string skill_id "マスター参照 SkillMaster.id（DB外部キーなし）"` |
| `equipment.base_id` / `shop_daily_slots.base_id` | `string base_id "装備マスターID"` |
| **`inventory_items.item_id`** | **`string item_id FK, UK "references ItemMaster.id"`** ← 例外 |

`ItemMaster` はDBテーブルを持たない（`tech_db.md` §1「ダンジョン・塔・敵・スキル・装備ベースはコード上のマスターデータでありDBテーブルを持たない」）ため、`FK` 表記のままだと存在しないテーブルへの外部キー実装を誘発する。なお `InventoryItem }o--|| ItemMaster : "references"` のリレーション線自体は他のマスター参照（`LearnedSkill }o--|| SkillMaster` 等）と同じ扱いで、変更不要。

**修正案:**

- `diagrams/er_diagram/item.md` 36行を、他のマスター参照列と同じ記法へ揃える。
  - 変更前: `        string item_id FK, UK "references ItemMaster.id"`
  - 変更後: `        string item_id UK "マスター参照 ItemMaster.id（DB外部キーなし・player_id と複合一意）"`
  - （`UK` は ISSUE-601 の複合一意表現として維持する）

## プロセスへの還元

**検出可能工程の集計**: 4件中3件（ISSUE-601・602・604）が「基本設計 §4 DBスキーマ三者一致」に集中している。現在この検証は**列名と並び順しか照合しておらず**、PK/FK/UK タグ・一意制約・nullable が対象外であるため、今回の指摘はすべてその穴から漏れたもの。

**改善案**: 候補キュー4「DBスキーマ三者一致チェックの常設化（`scripts/check_schema_triple.py`）」を実施する際、照合項目に以下を追加することを推奨する。今回の使い捨てスクリプトは4本目（セグメント1〜3 + 本レビュー）であり、[review-procedure.md](../../../.claude/references/review-procedure.md) §5 の「同種の使い捨てを繰り返し書いているなら常設スクリプトへ昇格」に該当する。

| 追加する照合 | 判定内容 |
|------------|---------|
| PK/FK/UK タグ | ER図のタグ ↔ 定義書の「制約・備考」欄（`PK` / `FK →` / `UNIQUE`）・`models` の `primary_key` / `ForeignKey` / `unique` |
| 一意制約 | 定義書の `uq_*` 宣言 ↔ ER図の `UK` 構成列 ↔ models の `UniqueConstraint`。**構成列すべてに `UK` があるか**を判定（ISSUE-601 が該当） |
| FKなし宣言 | 定義書が「FKなし（親 §4-6）」の列に ER図・models が FK を持たないこと（ISSUE-602 が該当） |
| nullable | 定義書の NULL 欄「可」 ↔ ER図注記の `nullable` ↔ models の `Mapped[T \| None]`（ISSUE-604 が該当） |
| 一意制約の命名規約 | `uq_<テーブル名>_<列>_<列>` に適合するか（上記「担当範囲外の言及」が該当） |
| ER索引の整合 | `er_diagram.md` 索引の列挙エンティティ ↔ 各子ファイルの実在エンティティ（ISSUE-603 が該当。`check_docs.py --reach` の拡張でも可） |
