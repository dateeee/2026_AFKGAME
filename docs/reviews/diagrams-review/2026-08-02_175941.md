### ISSUE-201: システム構成図の Schemas が実装・`tech_structure.md` と一致していない

| 項目 | 値 |
|------|-----|
| カテゴリ | コードとの整合性 |
| 重要度 | 高 |
| 関連ファイル | diagrams/system_architecture/application.md, docs/tech/tech_structure.md, backend/app/schemas/ |
| 該当箇所 | application.md 106〜111行（`subgraph Schemas`）、tech_structure.md 76〜83行 |

**問題の説明:**

前回の ISSUE-101 は Models / Services の不一致を修正したが、**同じ図の Schemas サブグラフは修正されていない**。

application.md 106〜111行:

```
subgraph Schemas["Schemas (Pydantic v2)"]
    playerSchema["player.py\nPlayerResponse\nSettingsUpdate"]
    charSchema["character.py\nCharacterResponse\nPartyEdit"]
    battleSchema["battle.py\nTickResponse\nBattleLogEntry\nOfflineSummary"]
    authSchema["auth.py Phase2~\nLoginRequest\nTokenResponse"]
end
```

実装は `backend/app/schemas/` に `__init__.py` / `auth.py` / `battle.py` / `equipment.py` / `player.py` / `shop.py` / `tower.py` の7ファイルで、**`character.py` は存在しない**。`CharacterResponse` は `schemas/player.py:9` に定義されている。`tech_structure.md` 76〜83行の一覧も `player.py` / `battle.py` / `equipment.py` / `shop.py` / `tower.py` / `auth.py` であり、`character.py` を含まない。

つまり図は「実在しないファイルを描き（`character.py`）、実装済みの3ファイル（`equipment.py`・`shop.py`・`tower.py`）を描いていない」状態で、ISSUE-101 と同じ誤りが Schemas に残っている。

なお `charSchema` の `PartyEdit` は Phase 3〜の想定だが、他の Phase 依存ノード（`authSchema` の `Phase2~`）と違い Phase 注記が無いため、実装済みと誤読される。

**修正案:**

- `diagrams/system_architecture/application.md` 106〜111行の `subgraph Schemas` を実装配置に合わせて置き換える。

```
subgraph Schemas["Schemas (Pydantic v2)"]
    playerSchema["player.py\nPlayerResponse\nCharacterResponse\nGameStateResponse\nSettingsUpdate"]
    battleSchema["battle.py\nTickResponse\nOfflineSummary"]
    towerSchema["tower.py\nTowerSelectRequest\nTowerInfo"]
    equipSchema["equipment.py Phase2~\nEquipmentResponse\nEquipRequest"]
    shopSchema["shop.py\nShopLineupResponse\nShopDailyItemResponse"]
    authSchema["auth.py Phase2~\nLoginRequest\nAuthResponse"]
end
```

- あわせて `battleSchema` の `BattleLogEntry` は `schemas/battle.py` に存在しない（`OfflineSummary` / `TickResponse` のみ）ため削除する。`authSchema` の `TokenResponse` も実装名は `AuthResponse`（`schemas/auth.py:14`）のため合わせる。
- `PartyEdit` は Phase 3〜 の未実装スキーマのため、図に残す場合は `Phase3~` の注記を付けたノードとして分離する（`player.py` 内へ置かない）。

### ISSUE-204: 画面遷移図の分割で、`ログイン画面` がメインナビの子として描画される

| 項目 | 値 |
|------|-----|
| カテゴリ | 設計図間の整合性 |
| 重要度 | 低 |
| 関連ファイル | diagrams/screen_transition/main_nav.md, diagrams/screen_transition/auth.md |
| 該当箇所 | main_nav.md 143行 |

**問題の説明:**

main_nav.md 143行は、`state メインナビ { ... }` ブロックの**内側**で未定義の状態を参照している。

```
        退会確認 --> ログイン画面 : 削除実行
```

`ログイン画面` は `screen_transition/auth.md` 19〜37行で定義された別図の状態で、main_nav.md では宣言されていない。stateDiagram-v2 は未宣言の状態を暗黙に生成するため、`ログイン画面` が **`メインナビ` の子状態として描画される**。実際はメインナビの外側（認証フロー）にある画面であり、分割前は1つの図に両方が存在したため生じなかった副作用。

auth.md 側にも `ホーム` への遷移（12〜17行・39〜43行）があるが、こちらはトップレベルの状態として置かれるため誤読につながらない。

**修正案:**

- `diagrams/screen_transition/main_nav.md` 143行を `メインナビ` ブロックの外へ出し、遷移先が別図であることを注記する。

```
    }

    退会確認 --> ログイン画面 : 削除実行（[auth.md] の認証フローへ）
```

- または 143行を削除し、図の下の箇条書きへ「退会の削除実行後は認証フロー（[auth.md](auth.md)）のログイン画面へ戻る」と記述する（auth.md 47行に対応する記述が既にあるため、こちらのほうが重複が少ない）。
