### ISSUE-101: 撃破済みの敵が同一ターン内に反撃する（階クリア後のstale敵攻撃）

| 項目 | 値 |
|------|-----|
| カテゴリ | コード品質 |
| 重要度 | 高 |
| 関連ファイル | backend/app/services/battle_service.py |
| 該当箇所 | battle_service.py 行248〜249・行398〜412 |
| 検出可能工程 | 本レビュー（分岐一覧に「撃破後の敵アクター打ち切り」の分岐が無く、単体テストでも検出されていない） |

**問題の説明:**
アクター順が `["player", "enemy"]`（プレイヤー先行）で、プレイヤーが敵を撃破すると、階クリア処理（行398〜400）で `player.current_enemy_id = None` / `player.current_enemy_hp = None` にリセットされる。続く敵アクターの打ち切り判定は

```python
if character.hp <= 0 or (player.current_enemy_hp is not None and player.current_enemy_hp <= 0):
    break
```

であり、`current_enemy_hp` が **None のときは成立しない**。その結果、敵アクターの処理（行402〜412）が撃破済みの `enemy_data` を使って実行され、**倒したはずの敵から1回攻撃を受ける**。この余分な被弾は毎階クリア時（プレイヤー先行時）に発生し、HP閾値撤退や全滅判定（行415〜438）まで到達しうる。目標到達+auto_repeat（行363〜368: break なし）、HP閾値撤退+auto_repeat（行390: `continue` で敵アクターへ進む）でも同じ経路を通る。stop_on_clear の塔退出（行378）と全滅（行438）のみ `break` で回避されている。

**修正案:**
- 行249の判定に敵不在を追加する: `if character.hp <= 0 or player.current_enemy_id is None or (player.current_enemy_hp is not None and player.current_enemy_hp <= 0): break`（または敵撃破処理の末尾で明示的に `break` し、ターンを終了させる）
- あわせて単体テストに「プレイヤー先行で敵撃破後、同ターンの敵攻撃が発生しない」ケースを追加し、詳細設計の分岐一覧（tech_battle.md）にもこの分岐を追記する

### ISSUE-102: tick処理で経過時間の余りが切り捨てられ、tick間隔が実質60秒超になる

| 項目 | 値 |
|------|-----|
| カテゴリ | コード品質 |
| 重要度 | 中 |
| 関連ファイル | backend/app/routers/battle.py |
| 該当箇所 | battle.py 行33〜42・行68 |
| 検出可能工程 | 本レビュー |

**問題の説明:**
`tick_endpoint` は `elapsed // TICK_INTERVAL_SECONDS` でtick数を算出した後、`player.last_tick_at = now`（行68）としており、**60秒未満の余り時間が毎回破棄される**。例: 前回tickから100秒経過 → 1tick処理 → 残り40秒分が消失。ポーリング間隔にジッタがあるほど累積し、「60秒固定間隔」（アーキテクチャ不変条件2）から実質的に乖離する。

**修正案:**
- `player.last_tick_at = last_tick + timedelta(seconds=pending_ticks * TICK_INTERVAL_SECONDS)` へ変更し、余り時間を次回へ持ち越す（MAX_OFFLINE_HOURS で切り詰めた場合はその時点を基準にする）

- 15件すべて「本レビュー」検出。特に ISSUE-101（撃破済みの敵の反撃）は C1 100% のテストが存在しても挙動として検出されておらず、**分岐一覧（詳細設計）に「敵撃破後の同ターン内の敵アクター打ち切り」という分岐自体が存在しない**ことが原因。カバレッジ100%は分岐一覧の網羅性までは保証しないため、詳細設計スキルの分岐一覧作成時に「状態をリセットする処理の直後に、リセット前の状態を前提とする処理が続かないか」の観点を追加することを提案する
- ISSUE-105〜109 は「片側の機能では対策済み・もう片側では未適用」という非対称パターン。fix-specs / dev での修正時に、同種パターンの横展開確認（本レポートの指摘箇所以外）を推奨する
