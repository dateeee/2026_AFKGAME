### ISSUE-901: 再設定トークンの「使用済み」判定が check-then-act で、同時実行では1回限りのトークンを2回使える

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 中 |
| 関連ファイル | backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthServiceImpl.java, backend/afkgame-domain/src/main/resources/com/afkgame/domain/repository/EmailVerificationTokenRepository.xml, backend/afkgame-domain/src/main/java/com/afkgame/domain/repository/EmailVerificationTokenRepository.java |
| 該当箇所 | AuthServiceImpl.java 行468〜472・行489, EmailVerificationTokenRepository.xml 行29〜33, EmailVerificationTokenRepository.java 行45 |
| 検出可能工程 | 詳細設計（password_reset.md §25 の分岐一覧に「同時実行で使用済み判定を通り抜ける」行が無い） |

**問題の説明:**

`resetPassword` は「読んで判定 → 更新」の順で、更新側に条件が無い。

```java
// AuthServiceImpl.java 行468〜472
if (resetToken.isUsed()) {
    logger.warn("パスワード再設定失敗").reason(LogReason.RESET_USED)
            .with(LogKey.USER_ID, resetToken.getUserId()).log();
    throw resetTokenInvalid();
}
...
// AuthServiceImpl.java 行489
emailVerificationTokenRepository.updateUsedById(resetToken.getId());
```

```xml
<!-- EmailVerificationTokenRepository.xml 行29〜33 -->
<update id="updateUsedById">
  UPDATE email_verification_tokens
     SET used = TRUE
   WHERE id = #{id}
</update>
```

同じトークンで2本のリクエストが並走すると、READ COMMITTED では両方が 行468 の判定を通過し、両方がパスワードを書き換えて 200 を返す。仕様（§24 手順4）は「メール確認と違い冪等にしない。認めると漏れたメールから何度でもパスワードを書き換えられる」ことを根拠に非冪等と決めているので、その担保が同時実行では効かないことになる。

**同一クラスの `refresh` は同じ問題を正しく処理している**。行144〜148 は更新件数で判定し直しており、コメントもその理由を明示している。

```java
// AuthServiceImpl.java 行144〜148
// 失効させられるのは未失効の1本だけ。0件なら同じトークンで並走した他のリクエストが
// 先にローテーションを済ませており、READ COMMITTED では上の失効判定を通り抜けている
if (refreshTokenRepository.updateRevokedById(stored.getId()) == 0) {
    throw detectReuse(stored.getUserId());
}
```

実害は「同時に2回書き換えられる」までで、時間差での再利用は現在の実装でも防げている（`used` は最初のコミットで立つ）。ただし2本が別々の新パスワードを送った場合、どちらが最終値になるかは不定であり、非冪等という設計判断が守られていない点は変わらない。

**修正案:**

`refresh` と同じ形（更新件数での判定）へそろえる。

- `backend/afkgame-domain/src/main/resources/com/afkgame/domain/repository/EmailVerificationTokenRepository.xml` 行29〜33 — 未使用のものだけを更新する。

  ```xml
  <update id="updateUsedById">
    UPDATE email_verification_tokens
       SET used = TRUE
     WHERE id = #{id}
       AND used = FALSE
  </update>
  ```

- `backend/afkgame-domain/src/main/java/com/afkgame/domain/repository/EmailVerificationTokenRepository.java` 行45 — 戻り値を `int` にし、`@return 更新件数（既に使用済みなら 0）` を Javadoc へ足す。

- `backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthServiceImpl.java` 行489 — 0件なら使用済みとして弾く。

  ```java
  if (emailVerificationTokenRepository.updateUsedById(resetToken.getId()) == 0) {
      logger.warn("パスワード再設定失敗").reason(LogReason.RESET_USED)
              .with(LogKey.USER_ID, resetToken.getUserId()).log();
      throw resetTokenInvalid();
  }
  ```

  この位置は `updatePasswordHash`（行488）の**後**なので、順序を入れ替えて「使用済み化 → 成功したらパスワード更新」にする。例外は `@Transactional` の既定でロールバックするため入れ替えなくても最終状態は同じだが、無駄な bcrypt 計算を避けられる。

- `verifyEmail`（行399）も同じメソッドを呼ぶが、**戻り値を見ない**まま据え置く。使用済みなら 行377 で早期 return するので 0件にはならず、同時実行で 0件になっても冪等が正（§20 手順4）のため扱いを変える必要がない。

**既存テストへの影響**（確認済み）: `AuthServiceImplTest` は `updateUsedById` を `verify(...)` でのみ検証しており（行1495・1645・1665・1683 ほか）、戻り値のスタブを持たない。`int` 化すると Mockito の既定値 0 が返るため、**再設定成功系のテストに `when(...).thenReturn(1)` の追加が必要**。あわせて 0件経路が新しい分岐として増えるため、C1 100% を保つにはテスト1件の追加が要る。

### ISSUE-903: `googleAuthCode` が境界ログへ生値で出る（固定表にも判定12 の語表にも無い）

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 中 |
| 関連ファイル | backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthService.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthServiceImpl.java, backend/afkgame-env/src/main/java/com/afkgame/env/logging/LayerLoggingInterceptor.java |
| 該当箇所 | AuthService.java 行119, AuthServiceImpl.java 行299, LayerLoggingInterceptor.java 行32〜34 |
| 検出可能工程 | 製造（`scripts/check_java_conventions.py` 判定12。`SECRET_WORDS` に認可コード系の語が無く素通りする） |

**問題の説明:**

`linkAccount` は Google の認可コードを `String` で受ける。

```java
// AuthService.java 行119
AuthResult linkAccount(User user, String email, String rawPassword, String googleAuthCode);
```

`AuthServiceImpl` は `com.afkgame.domain.service.*` のポイントカット配下にあるため、AOP が START ログへ全引数を出す。マスクは名前一致だけで決まる。

```java
// LayerLoggingInterceptor.java 行32〜34
private static final Set<String> MASKED_PARAM_NAMES = Set.of(
        "password", "rawPassword", "newPassword", "token", "accessToken", "refreshToken",
        "secret", "credential");
```

`googleAuthCode` はこの固定表に無く、判定12 の `SECRET_WORDS`（`raw` / `token` / `password` / `secret` / `credential`）にも一致しない（camelCase を割ると `google` / `Auth` / `Code`）。したがって**スクリプトは違反を出さず、値はそのままログへ出る**。認可コードはアクセストークンと交換できる一回限りの資格情報なので、`refreshToken` を伏せている基準と食い違う。

現時点では Google連携が 501 で止まる（行309〜311）ため実被害は無いが、**START ログはサービス本体より前に出る**ので、値を載せたリクエストが来た時点でログに残る。

**修正案:**

3か所を同時に直す（固定表の正は規約側）。

- `docs/process/coding_standards_backend/logging/application.md` §3.1 規約1 の固定表へ `googleAuthCode` を追加する。
- `backend/afkgame-env/src/main/java/com/afkgame/env/logging/LayerLoggingInterceptor.java` 行32〜34 — `MASKED_PARAM_NAMES` へ `"googleAuthCode"` を追加する。
- `scripts/check_java_conventions.py` — `MASKED_PARAMS` へ `googleAuthCode` を、`SECRET_WORDS` へ `authcode`（camelCase 分割後は `auth` + `code` になるため、語の追加ではなく**連続2語の判定**か `code` 単独の追加が要る）を反映する。`code` 単独の追加は `errorCode`・`statusCode` を巻き込むので、**`auth` の直後に `code` が続く場合だけ機密とみなす**判定にする。

  ```python
  # 例: 語の並びで見る
  def is_secret_name(name: str) -> bool:
      words = [w.lower() for w in CAMEL_WORD.findall(name)]
      if any(w in SECRET_WORDS for w in words):
          return True
      return any(a == "auth" and b == "code" for a, b in zip(words, words[1:]))
  ```

  この変更で `scripts/tests`（403件）の期待値追加が要る。既存の判定12 のテストは `errorCode` を違反にしない前提を持つため、その前提が保たれることも1件で固定する。

**問題の説明:**


- `backend/afkgame-domain/src/main/java/com/afkgame/domain/service/VerificationMailSenderImpl.java` 行195 の直後へ1行足す。

### ISSUE-909: bcrypt ハッシュが境界ログへ出る（規約例外で抑止しているが、出す必要が無い）

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 低 |
| 関連ファイル | backend/afkgame-domain/src/main/java/com/afkgame/domain/repository/UserRepository.java, backend/afkgame-env/src/main/java/com/afkgame/env/logging/LayerLoggingInterceptor.java |
| 該当箇所 | UserRepository.java 行81〜82, LayerLoggingInterceptor.java 行32〜34 |
| 検出可能工程 | 本レビュー（規約例外コメントで判定12 を抑止しているため、機械判定では出ない） |

**問題の説明:**

```java
// UserRepository.java 行81〜82
// 規約例外: 受け取るのは bcrypt ハッシュであり、境界ログに出ても生パスワードは復元できない
void updatePasswordHash(@Param("id") String id, @Param("passwordHash") String passwordHash);
```

「生パスワードは復元できない」は正しく、`findByTokenHash` の SHA-256 と同じ理屈が成り立つ。ただし SHA-256 のトークンハッシュと違い、**bcrypt ハッシュはオフラインでの総当たりの入力になる**（トークンハッシュは 48バイト乱数由来なので総当たりが成立しないのに対し、パスワードは辞書攻撃が成立する）。ログが流出した場合の意味が両者で異なるので、同じ「規約例外」で並べるのは過剰に緩い。

この値をログへ出して得られる運用上の情報も無い（更新できたかは END の有無で分かる）。

**修正案:**

- `docs/process/coding_standards_backend/logging/application.md` §3.1 規約1 の固定表へ `passwordHash` を追加する。
- `backend/afkgame-env/src/main/java/com/afkgame/env/logging/LayerLoggingInterceptor.java` 行32〜34 — `MASKED_PARAM_NAMES` へ `"passwordHash"` を追加する。
- `scripts/check_java_conventions.py` の `MASKED_PARAMS` へ `passwordHash` を追加する。`is_secret_name("passwordHash")` は `password` で既に真になるため、固定表へ入れるだけで違反が消え、**`UserRepository.java` 行81 の規約例外コメントは削除できる**。
- `tokenHash`（`RefreshTokenRepository` 行19・`EmailVerificationTokenRepository` 行32）の規約例外は**そのまま残す**（上記のとおり総当たりが成立しないため）。

### 2. 詳細設計の分岐一覧に「同時実行」の行が無い

ISSUE-901・902 は**同じ根**（check-then-act を単一 UPDATE の条件で締めていない）で、同じクラスの `refresh`（AuthServiceImpl 行144〜148）だけが正しく実装されている。差は「`refresh` の詳細設計（tech_auth.md §4）は再利用検知を仕様として持ち、`link` §19・`password_reset` §25 は同時実行の行を持たない」点にある。

分岐一覧に**「同時実行で判定を通り抜けた場合」の行を、更新を伴う手順ごとに必ず立てる**運用にすると、テストリスト工程で自然に拾える（分岐として立てば `check_branch_list.py` の突合対象にもなる）。C1 の網では拾えない（同時実行の分岐は行としてそもそも存在しない）ため、工程側で持たせるほうが確実。

### 3. 「規約例外」コメントのレビュー観点化

ISSUE-909 は、機械判定を抑止する `// 規約例外:` コメントが**判定の外側**にあることで生まれた。抑止そのものは必要な仕組みだが、抑止した箇所は目視レビューでしか再点検されない。`check_java_conventions.py` へ `--suppressed` のような一覧出力（抑止コメントの箇所と理由を並べるだけ）を足すと、レビュー時に「今も妥当か」を数行で確認できる。
