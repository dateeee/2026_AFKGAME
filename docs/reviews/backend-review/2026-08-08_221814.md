### ISSUE-601: `local` プロファイルの既定 JWT 署名鍵が、`APP_ENV` 未設定のまま本番起動すると有効になる

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 高 |
| 関連ファイル | backend/afkgame-env/src/main/resources/application-local.yml, backend/afkgame-env/src/main/resources/application.yml, backend/afkgame-env/src/main/resources/application-production.yml |
| 該当箇所 | application-local.yml 行14, application.yml 行12・行53 |
| 検出可能工程 | 基本設計 `tech_operations.md` §12.2（起動時バリデーションの設計） |

**問題の説明:**

`application-local.yml` 行13〜14 が JWT 署名鍵の既定値をリポジトリに持っている。

```yaml
    # HS256 の鍵長は32バイト以上が必要（RFC 7518 §3.2）
    secret: ${JWT_SECRET:afkgame-dev-secret-change-in-production}
```

一方 `application.yml` 行12 は、有効プロファイルを **`local` 既定**で決めている。

```yaml
    active: ${APP_ENV:local}
```

`application.yml` 行53 の `secret: ${JWT_SECRET}` は既定値を持たないため、`APP_ENV=production` なら `JWT_SECRET` 未設定で起動が止まる設計になっている（行52 のコメントどおり）。しかしこの防御は **`APP_ENV` が設定されていること自体に依存**している。`APP_ENV` を設定し忘れた場合は `production` の設定が読まれず `local` として起動し、**リポジトリに載っている既知の鍵で HS256 の署名が行われる**。起動は成功し、ログにも警告が出ないため気づく手がかりがない。

署名鍵が既知であれば任意の `sub` でアクセストークンを偽造でき、`JwtAuthenticationFilter` はそれを正当なユーザーとして通す（`JwtService` 行75〜79 は署名検証のみで発行元を区別しない）。**認証の全面バイパスに相当する**。

なお `DATABASE_URL`・`DATABASE_USER`・`DATABASE_PASSWORD` は `application-production.yml` に既定値なしで再宣言されているため、`APP_ENV` を取り違えても `local` の DB を向くだけで、鍵ほどの影響はない。**署名鍵だけがこの穴を持つ**。

**修正案:**

いずれかを採る。1が最も影響範囲が小さい。

- **案1（推奨）**: `backend/afkgame-env/src/main/resources/application-production.yml` に、DataSource と同じ流儀で署名鍵を既定値なしで再宣言する。`APP_ENV=production` 時に `JWT_SECRET` 未設定なら起動が止まる点は現状と変わらないが、**「本番の必須変数は production プロファイルに列挙されている」という読み方が成立する**ようになる。ただし `APP_ENV` 自体の設定漏れは防げないため、案3と併用する
  ```yaml
  afkgame:
    auth:
      secret: ${JWT_SECRET}
  ```
- **案2**: `application-local.yml` の既定鍵を廃し、`JWT_SECRET` 未設定時は起動ごとにランダム生成する（`JwtService` のコンストラクタで `authProperties.secret()` が空なら `Keys.secretKeyFor(Jwts.SIG.HS256)`）。開発時は再起動でトークンが無効になるが、**リポジトリから既知の鍵が消える**のが利点。`AuthProperties.secret` を nullable にする変更が要る
- **案3**: `application.yml` 行12 の既定値 `local` を外して `active: ${APP_ENV}` にし、`APP_ENV` の設定を必須にする。設定漏れが起動失敗として即座に出る。開発者が `APP_ENV=local` を常に設定する必要が生じるため、`docker-compose.yml`・README の起動手順・`.env.example` の同時更新が要る

案1・案3を採った場合も既存テストは `@SpringBootTest` が明示的にプロファイルを与えているため影響を受けない。案2は `JwtServiceTest` が固定鍵を渡しているため同様に影響しない。

### ISSUE-604: `handleExceptionInternal` が例外メッセージをそのままクライアントへ返す

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 中 |
| 関連ファイル | backend/afkgame-web/src/main/java/com/afkgame/web/filter/ApiExceptionHandler.java |
| 該当箇所 | ApiExceptionHandler.java 行81〜87 |
| 検出可能工程 | 本レビュー |

**問題の説明:**

`handleExceptionInternal`（行83〜87）が `ex.getMessage()` を無加工でレスポンスボディへ載せている。

```java
    protected ResponseEntity<Object> handleExceptionInternal(Exception ex, Object body,
            HttpHeaders headers, HttpStatusCode statusCode, WebRequest request) {
        return new ResponseEntity<>(
                ErrorResource.of("HTTP_" + statusCode.value(), ex.getMessage()), headers, statusCode);
    }
```

これは同クラスの Javadoc 行23〜24 の方針、および規約 §4-4「応答に内部情報（SQL・スタックトレース・スキーマ）を載せない」と食い違う。

```java
 * 未捕捉例外は ERROR ログにスタックトレースを残し、クライアントには 500 と
 * {@code INTERNAL_UNEXPECTED_ERROR} のみを返す（内部情報を漏らさない）。
```

`handleExceptionInternal` は `ResponseEntityExceptionHandler` の全標準例外の共通出口で、404・405・415 のように無害なものだけが来るわけではない。`ConversionNotSupportedException` と `HttpMessageNotWritableException` は **HTTP 500 でここを通り**、`getMessage()` に内部のクラス名・パッケージ名が入る（例: `Could not write JSON: ... com.afkgame.domain.model.Player ...`）。`TypeMismatchException` も変換先の Java 型名を含む。つまり **500 系の応答経路にだけ内部型情報の露出が残っている**。

`@ExceptionHandler(Exception.class)`（行60〜65）が定型文で返しているのと、同じクラス内で扱いが割れている点も一貫していない。

**修正案:**

- `backend/afkgame-web/src/main/java/com/afkgame/web/filter/ApiExceptionHandler.java` 行82〜87 を、5xx はログのみに残して定型文へ寄せ、4xx（クライアント起因で、内容が本人の送ったリクエストに閉じる）だけメッセージを返す形にする
  ```java
      /** 上記以外の Spring MVC 標準例外。コードは {@code HTTP_<status>} とする。 */
      @Override
      protected ResponseEntity<Object> handleExceptionInternal(Exception ex, Object body,
              HttpHeaders headers, HttpStatusCode statusCode, WebRequest request) {
          // 5xx はフレームワーク内部の型名・変換先を含みうるため、応答へ載せずログにのみ残す
          if (statusCode.is5xxServerError()) {
              middlewareLogger.error("フレームワーク内部エラー status={}", statusCode.value(), ex);
              return new ResponseEntity<>(
                      ErrorResource.of("INTERNAL_UNEXPECTED_ERROR", "サーバー内部エラーが発生しました"),
                      headers, statusCode);
          }
          return new ResponseEntity<>(
                  ErrorResource.of("HTTP_" + statusCode.value(), ex.getMessage()), headers, statusCode);
      }
  ```
- 既存の `ApiExceptionHandlerTest` 行127〜130 は 400（`HTTP_400`）を検証しており 4xx 経路のため影響を受けない。5xx 経路のケースを1件足すと分岐が埋まる

### ISSUE-605: 現在時刻をサービス内部で `Instant.now()` から取得している（規約 §2）

| 項目 | 値 |
|------|-----|
| カテゴリ | コード品質 |
| 重要度 | 中 |
| 関連ファイル | backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthService.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/service/PlayerInitializationService.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/service/JwtService.java |
| 該当箇所 | AuthService.java 行75・116・154・156, PlayerInitializationService.java 行91, JwtService.java 行53 |
| 検出可能工程 | 本レビュー（機械判定可能 — 末尾「プロセスへの還元」で常設化を提案） |

**問題の説明:**

規約 §2「現在時刻・乱数は**外から受ける**（引数・注入）。静的な共有インスタンスを持たない」に対し、ドメインサービス3クラス6箇所が `Instant.now()` を直接呼んでいる。

`PlayerInitializationService` 行91 は既存 `AuthService` の流儀に合わせた結果であり（規約 §1「規約に無い判断は近傍の既存コードに倣う」に沿う）、**新サービス単体の逸脱ではなく、STEP 2-B から続く既存の流儀そのものが規約と食い違っている**。したがって新サービスだけを直しても揃わない。

実害が出ている箇所が1つある。`AuthService.issueTokens()` が同一レコードの2列を別々の呼び出しで埋めている。

```java
        record.setExpiresAt(Instant.now().plus(refreshTokenExpire));   // 行154
        record.setRevoked(false);
        record.setCreatedAt(Instant.now());                             // 行156
```

`expires_at` と `created_at` の差が厳密に `refreshTokenExpire` にならない（2回の `now()` の間隔ぶんずれる）。差分から有効期限を逆算する監査・調査で誤差の原因になる。

テスト面では、期限切れ・境界時刻の検証が実時間に依存するため、`AuthServiceTest` は期限切れトークンを「過去の `Instant` を持つレコード」を用意する形でしか書けず、`JwtService` の期限切れ検証は実際に 30 分待てないため到達させられない。

**修正案:**

規約側の判断を先に決める。**規約 §2 を維持するなら案A、既存流儀を追認するなら案B**。中途半端に新サービスだけ変えると流儀が2つに割れるため避ける。

- **案A（規約 §2 を維持・推奨）**: `java.time.Clock` を Bean として定義し、3サービスへコンストラクタ注入する。`Instant.now()` を `clock.instant()` に置き換え、`issueTokens()` は先頭で `Instant now = clock.instant();` を1回だけ取って両列に使う
  ```java
  // afkgame-env の設定クラスへ
  @Bean
  Clock clock() {
      return Clock.systemUTC();
  }
  ```
  影響範囲は `AuthService`・`PlayerInitializationService`・`JwtService` のコンストラクタと、それらの単体テスト4件（`Clock.fixed(...)` を渡す形へ変更）。テスト側は固定時刻で期限切れ分岐を直接書けるようになり、`JwtServiceTest` の期限切れケースが実時間依存でなくなる利点がある
- **案B（既存流儀を追認）**: `docs/process/coding_standards_backend.md` §2 の当該行に「認証・監査で使う発行時刻など、外部から与える意味が無い時刻は `Instant.now()` を直接使ってよい」の例外を明記し、各サービスのクラス Javadoc にその旨を1行書く。コード変更は `issueTokens()` の `now()` 二重呼び出しの解消のみ
  ```java
      private AuthResult issueTokens(User user) {
          Instant now = Instant.now();
          ...
          record.setExpiresAt(now.plus(refreshTokenExpire));
          record.setRevoked(false);
  ```
