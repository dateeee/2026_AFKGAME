|------|-----|
| カテゴリ | セキュリティ |

| 関連ファイル | backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthService.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthServiceImpl.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/service/VerificationMailSender.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/service/VerificationMailSenderImpl.java |

| 検出可能工程 | 製造（`coding_standards_backend/logging/application.md` §3.1 規約1 の固定表と、実際のパラメータ名の突合） |

**問題の説明:**

`LayerLoggingInterceptor` は引数を**パラメータ名の完全一致**でしかマスクしない。

```java
private static final Set<String> MASKED_PARAM_NAMES = Set.of(
        "password", "rawPassword", "newPassword", "token", "accessToken", "refreshToken",
        "secret", "credential");                                        // 行32〜34
...
private static String formatArg(String paramName, Object value) {
    if (MASKED_PARAM_NAMES.contains(paramName)) {                       // 行88
        return FULL_MASK;
    }
    ...
    return formatValue(value);                                          // 行94 = 生値をそのまま
}
```

この固定表は `application.md` §3.1 規約1 と**一字一句一致しており、実装は規約どおり**である。問題は、**認証サービス側のパラメータ名がどれにも一致しないこと**にある。

| メソッド | パラメータ名 | 固定表との一致 | 出力される値 |
|---------|------------|--------------|-------------|
| `AuthService#refresh(String rawRefreshToken)` | `rawRefreshToken` | **なし** | リフレッシュトークンの生値（64文字） |
| `AuthService#logout(String userId, String rawRefreshToken)` | `rawRefreshToken` | **なし** | 同上 |
| `VerificationMailSender#send(User user, String rawToken)` | `rawToken` | **なし** | 確認トークンの生値（64文字） |
| `AuthService#register(String, String rawPassword)` | `rawPassword` | あり | `****`（正常） |

3経路とも `afkgame.properties` 50行のポイントカット `execution(public * com.afkgame.domain.service.*.*(..))` に一致し、`ApplicationContextConfig` 39行の `@EnableAspectJAutoProxy` で実際にプロキシが張られる。出力は `LoggerName.LAYER`（`afkgame.layer`）→ `logback.xml` 25行の `afkgame` ロガー（INFO）→ root の `APPLICATION` appender、すなわち `application.log` である。値は200文字打ち切りにかからない（生トークンは64文字）ため、**全文がそのまま残る**。

```
[2026-08-10 01:00:00] INFO     afkgame.layer: START signature=AuthServiceImpl#refresh args=[nX7k...（生トークン64文字）] request_id=...
```

これは `tech_auth/account.md` §9「ログ」の **「パスワードとトークン生値は出力しない」** に反する。ログ閲覧権限があれば、有効期限30日のリフレッシュトークンをそのまま再利用できる（ISSUE-701 で塞いだ再利用検知は、正規クライアントより先に使われた場合には被害の検知しかできない）。

なお本件は `docs/backlog/carryover_notes.md` §3 に「固定表を拡張するかパラメータ名を揃えるかは規約側の決定が要る」として記録されているが、**`known_issues.md` には未登録**で、実装は既に main にある。後述のとおりパラメータ名を揃えるだけで閉じるため、規約側の決定は不要である。

**修正案:**

固定表に既に `refreshToken` と `token` があるので、**パラメータ名をそちらへ揃える**（規約の改訂を伴わない・`application.md` §3.1 の固定表は無変更）。

  ...
  void logout(String userId, String refreshToken);
  ```

- `backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthServiceImpl.java` 行117・行263 — 実装側も同じ名前にする（`proxyTargetClass = true` へ切り替わった場合に CGLIB が実装メソッドを渡すため。ISSUE-805 と同じ理由）。

  ```

### ISSUE-802: パスワード長 8/128 が `RegisterResource` のリテラルと設定値に二重定義され、設定側は誰も読んでいない

| 項目 | 値 |

**問題の説明:**

セグメントC で `RegisterResource` を仕様どおりの入力長へ直したのは正しい修正だが、同じ数値が2か所に存在する状態になった。

```java
// RegisterResource.java 行17〜18
@NotBlank @Email @Size(max = 254) String email,
@NotBlank @Size(min = 8, max = 128) String password) {
```

```properties
# afkgame.properties 行27〜28
afkgame.auth.password.min.length=8
afkgame.auth.password.max.length=128
```

設定側は `AfkgameSettingsConfig` 107〜108行で読まれ `AuthSettings` へ載るが、**`passwordMinLength()` / `passwordMaxLength()` を呼ぶコードは本番・テストを通じて0件**（Grep 済み。`AuthSettings` の定義と `AfkgameSettingsConfig` の組み立て以外に出現しない）。実際に効いているのは `@Size` のリテラルだけで、設定ファイルの値を変えても挙動は一切変わらない。

これは前回 ISSUE-705 で指摘した「用意したが使っていない部品」と同じ型の問題であり、`profile.md` §5 不変条件6「マスターデータの数値をコードにハードコードしない」の趣旨（値の正を1か所に置く）とも噛み合わない。`tech_security.md` §11.3 のパスワード長を変更した際、properties だけ直して `@Size` を直し忘れる事故が起きる。

**修正案:**

Bean Validation の `@Size` はコンパイル時定数しか取れないため、プロパティ値を直接注入することはできない。次のどちらかを採る。

- **案A（推奨・コードだけで閉じる）** — `@Size` のリテラルは残し、**設定値と一致していることを検証するテストを1本置く**。`backend/afkgame-web/src/test/java/com/afkgame/web/resource/RegisterResourceTest.java`（新設）へ:

  ```java
  @Test
  void test_パスワード長の制約は設定値と一致する() throws Exception {
      Size size = RegisterResource.class.getRecordComponents()[1]
              .getAccessor().getAnnotation(Size.class);
      assertThat(size.min()).isEqualTo(8);    // afkgame.auth.password.min.length
      assertThat(size.max()).isEqualTo(128);  // afkgame.auth.password.max.length
  }
  ```

  さらに強くするなら統合テスト側で `AuthSettings` を注入して突き合わせる。案A では properties のキーが残るため、`tech_backend.md` §4.2・`tech_operations.md` §12.2 のキー一覧に手を入れる必要がない（`check_docs.py` は exit 0 のまま）。

- **案B（設定キーを削除）** — `afkgame.auth.password.{min,max}.length` と `AuthSettings` の2フィールド・`AfkgameSettingsConfig` の2引数を削除し、正を `RegisterResource` へ一本化する。**この案は `tech_backend.md` §4.2 の設定キー一覧と `tech_operations.md` §12.2 からの削除を伴い、`check_docs.py` を通すには仕様書側の改稿が必要**（`fix-specs` の担当）。コードだけの適用では文書と実装が食い違う。

  案Aのほうが手戻りが小さい。

### ISSUE-805: `@MaskReturnValue` がインタフェース側にしか無く、プロキシ方式が変わると黙って効かなくなる

| 項目 | 値 |
|------|-----|
| カテゴリ | コード品質 |
| 重要度 | 低 |
| 関連ファイル | backend/afkgame-domain/src/main/java/com/afkgame/domain/service/JwtService.java, backend/afkgame-env/src/main/java/com/afkgame/env/logging/LayerLoggingInterceptor.java |
| 該当箇所 | JwtService.java 行33, LayerLoggingInterceptor.java 行101 |
| 検出可能工程 | 製造（AOP のプロキシ方式と注釈の探索範囲の突合） |

**問題の説明:**

`LayerLoggingInterceptor` は戻り値のマスク判定を、渡された `Method` オブジェクトの注釈だけで行う。

```java
if (method.isAnnotationPresent(MaskReturnValue.class)) {   // 行101
    return FULL_MASK;
}
```

`invocation.getMethod()` が返すのは、**JDK 動的プロキシならインタフェースのメソッド、CGLIB なら実装クラスのメソッド**である。Java はインタフェースのメソッド注釈を実装メソッドへ継承しないため、`@MaskReturnValue` が `JwtService`（インタフェース）にしか無い現状は、**JDK 動的プロキシであることに依存して成立している**。

現時点では成立している（`proxyTargetClass` の指定は backend 全体で0件＝既定 `false`、かつ `JwtServiceImpl implements JwtService` なので JDK 動的プロキシ）。しかし次のいずれかが起きた瞬間、生の JWT が `application.log` の `result` へ出る。**失敗しても例外にならず、テストも赤くならない**（`LayerLoggingInterceptorTest` の `Sample` はインタフェース + `SampleImpl` の組で、注釈もインタフェース側にしか無いため、この経路を通らない）。

1. どこかで `@EnableAspectJAutoProxy(proxyTargetClass = true)` を指定する（Spring Boot 系の設定を持ち込むと既定でこうなる）
2. `@MaskReturnValue` を、インタフェースを持たない `@Service` クラスのメソッドへ付ける（3-A-3 以降で追加されうる）

**修正案:**

- `backend/afkgame-env/src/main/java/com/afkgame/env/logging/LayerLoggingInterceptor.java` 行97〜105 — 実装メソッドで見つからなければ、宣言クラスのインタフェース側も探す。プロキシ方式に依存しなくなる。

  ```java
  private static String formatResult(Method method, Object result) {
      if (method.getReturnType() == void.class) {
          return null;
      }
      if (isMaskedReturn(method)) {
          return FULL_MASK;
      }
      return formatValue(result);
  }

  /** CGLIB では実装メソッドが渡るため、インタフェース側の宣言も探す（注釈は継承されない）。 */
  private static boolean isMaskedReturn(Method method) {
      if (method.isAnnotationPresent(MaskReturnValue.class)) {
          return true;
      }
      for (Class<?> type : method.getDeclaringClass().getInterfaces()) {
          try {
              if (type.getMethod(method.getName(), method.getParameterTypes())
                      .isAnnotationPresent(MaskReturnValue.class)) {
                  return true;
              }
          } catch (NoSuchMethodException e) {
              // このインタフェースは同じシグネチャを宣言していない
          }
      }
      return false;
  }
  ```

- `backend/afkgame-env/src/test/java/com/afkgame/env/logging/LayerLoggingInterceptorTest.java` の `TestMasking` へ「注釈がインタフェース側だけにあり、実装クラスをそのまま進行させた場合も伏せる」を1件足す（`SampleImpl#secret()` の `Method` を直接渡す形）。

- 簡易案として「インタフェースと実装の両方へ付ける」を `application.md` §3.1 規約3 へ1行加える手もあるが、**付け忘れが静かに漏洩になる**ため、共通部品側で閉じる上記を推奨する（規約の改訂も不要）。

## プロセスへの還元

### 1. `check_java_conventions.py` へ「機密名の固定表とパラメータ名の突合」を足す（効果が最も大きい）

ISSUE-801 は、規約どおりに実装された共通部品と、規約の想定外だった呼び出し側の命名が噛み合わなかったことで生まれた。**どちらのファイルを単体で読んでも見つからない**種類の問題で、目視レビューに頼ると再発する。一方で判定は完全に機械化できる。

```
対象: com.afkgame.domain.service.* / com.afkgame.domain.repository.* の public メソッド（= ポイントカットに一致する範囲）
違反: パラメータ名が固定表（application.md §3.1 規約1）のいずれでもなく、かつ
      raw / token / password / secret / credential を含む
```

前回の還元#2（「MDC キーは `LogKey` に定義されたものだけ」）と同じ枠で追加できる。3-A-3 で `link-account` / `verify-email` / `password-reset` が入ると、`rawVerificationToken`・`rawResetToken` のような名前が新たに増えるため、**その製造より前に入れると効果が大きい**。

### 2. 「用意したが使っていない部品」の検出が2回連続で人手頼りになっている

前回の還元#4 が挙げた問題（`LogKey.EMAIL` が未使用）が、今回 ISSUE-802（`passwordMinLength` / `passwordMaxLength`）・ISSUE-803（`MailSettings` 全体・`passwordResetTokenExpire`）として再発した。2回続けて同種の指摘が出ているので、使い捨てではなく常設化を提案する。

```
対象: com.afkgame.env.config の record アクセサ、LogKey / LogReason / LoggerName の enum 値
判定: src/main（config パッケージ自身を除く）からの参照が0件なら WARN
```

意図的な先行投入（`MailSettings`）は WARN のまま許容し、**件数の増減だけを見る**運用でよい。ゼロを強制すると 3-A-3 の受け皿が作れなくなる。
