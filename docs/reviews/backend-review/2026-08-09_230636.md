### ISSUE-701: リフレッシュトークンのローテーションが同時実行で二重発行され、再利用検知をすり抜ける

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 中 |
| 関連ファイル | backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthServiceImpl.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/repository/RefreshTokenRepository.java, backend/afkgame-domain/src/main/resources/com/afkgame/domain/repository/RefreshTokenRepository.xml |
| 該当箇所 | AuthServiceImpl.java 行114〜137, RefreshTokenRepository.java 行33, RefreshTokenRepository.xml 行26〜30 |
| 検出可能工程 | 詳細設計（`tech_auth.md` §4 の分岐一覧に「同一トークンの同時使用」の分岐が無い） |

**問題の説明:**

`refresh` は「読んで判定してから更新する」形になっており、失効の更新件数を捨てている。

```java
RefreshToken stored = refreshTokenRepository.findByTokenHash(hashToken(rawRefreshToken));
...
if (stored.isRevoked()) {                                     // 行120
    ...
    refreshTokenRepository.updateRevokedByUserId(...);
    throw refreshInvalid("Refresh token reuse detected");
}
...
refreshTokenRepository.updateRevokedById(stored.getId());     // 行130
```

`updateRevokedById` の SQL は無条件更新で、インタフェースの戻り値も `void`（更新件数を受け取らない）。

```xml
<update id="updateRevokedById">
  UPDATE refresh_tokens
     SET revoked = TRUE
   WHERE id = #{id}
</update>
```

READ COMMITTED（PostgreSQL 既定）では、同じ生トークンで2本のリクエストが並走すると**両方が行120の `isRevoked()` を false で通過**し、両方が新しいトークンペアを発行できる。`tech_auth.md` §4 が求める「窃取されたトークンの再利用を検知して全失効させる」動作は、攻撃者が正規クライアントと同時にリフレッシュした場合に働かない。ISSUE-702 と違い、これは仮実装ではなく現行コードで再現する。

なお `logout`（行244〜262）も同じ read-then-update だが、冪等な操作であり二重実行しても結果が変わらないため対象外。

**修正案:**

- `backend/afkgame-domain/src/main/resources/com/afkgame/domain/repository/RefreshTokenRepository.xml` 行26〜30 — 失効を条件付きにして、勝者を1本に絞る。

  ```xml
  <update id="updateRevokedById">
    UPDATE refresh_tokens
       SET revoked = TRUE
     WHERE id = #{id}
       AND revoked = FALSE
  </update>
  ```

- `backend/afkgame-domain/src/main/java/com/afkgame/domain/repository/RefreshTokenRepository.java` 行33 — 更新件数を返す。

  ```java
  int updateRevokedById(Integer id);
  ```

- `backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthServiceImpl.java` 行130 — 0件なら「他のリクエストが先に失効させた＝再利用」として、行120と同じ全失効経路へ寄せる。

  ```java
  if (refreshTokenRepository.updateRevokedById(stored.getId()) == 0) {
      logger.warn("不正リフレッシュトークン検知").reason(LogReason.REFRESH_REUSED)
              .with(LogKey.USER_ID, stored.getUserId()).log();
      refreshTokenRepository.updateRevokedByUserId(stored.getUserId());
      throw refreshInvalid("Refresh token reuse detected");
  }
  ```

  `@Transactional(noRollbackFor = AppException.class)` は既に付いているため、この経路でも全失効は確定する（行113）。
- `AuthServiceImplTest` へ「更新件数0なら全失効して401」のテストを1件足す（既存の `test_revoked済みの再利用は全トークンを失効させる` と対になる）。

### ISSUE-702: 確認メールが「コミット後・トランザクションの外」で送られない（Javadoc の宣言に実体が無い）

| 項目 | 値 |
|------|-----|
| カテゴリ | 一貫性 |
| 重要度 | 中 |
| 関連ファイル | backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthServiceImpl.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/service/VerificationMailSender.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/service/VerificationMailSenderImpl.java |
| 該当箇所 | AuthServiceImpl.java 行157〜159・行199〜202・行264〜276, VerificationMailSenderImpl.java 行25〜29 |
| 検出可能工程 | 詳細設計（`tech_auth/account.md` §11 の分岐一覧が #12・#13 で送信の成否しか持たず、「送信がコミット後か」の分岐が無い） |

**問題の説明:**

`AuthServiceImpl` は自クラスの Javadoc で、送信タイミングの担保を送信側へ委ねると宣言している。

```java
 * <p>重複確認からトークン発行までを本メソッドの境界で1つにまとめる
 * （tech_auth/account.md §10 手順8）。確認メールの送信要求だけは境界の外へ出さず、
 * 送信側（{@link VerificationMailSender}）が「コミット後」の扱いを持つ。   // 行157〜159
```

しかし `VerificationMailSenderImpl` は WARN ログを1行出すだけで、遅延実行の仕組みを一切持たない。

```java
@Override
public void send(User user, String rawToken) {
    logger.warn("確認メールは未送信（送信手段は移行 STEP 3-A-3 で実装）")
            .with(LogKey.USER_ID, user.getId())
            .log();
}
```

backend 全体を grep しても `TransactionSynchronization` / `@TransactionalEventListener` / `afterCommit` は**1件も存在しない**。したがって現状 `sendVerificationMail`（行270）は `@Transactional public AuthResult register(...)` の**内側**、コミット前に同期実行される。

現時点は仮実装のため実害はないが、STEP 3-A-3 で実 SMTP へ差し替えた瞬間に「コミット前に確認メールを送る」実装になる。手順9 の「コミット後に送信を要求する。送信はトランザクションの外」（`tech_auth/account.md` 行33）に反し、コミットが失敗した場合に**存在しないアカウント宛の確認リンク**が届く。担保がクラスのコメントにしか無いため、3-A-3 の実装者がこの制約に気づかない可能性が高い。

**修正案:** 次のいずれかを取り、コメントと実体を一致させる。どちらでも `check_java_conventions.py` は exit 0 のまま（本スクリプトは呼び出し位置を見ない）。

- **案A（宣言どおり送信側で担保・推奨）** — `backend/afkgame-domain/src/main/java/com/afkgame/domain/service/VerificationMailSenderImpl.java` の `send` を、トランザクション参加中なら after-commit へ、そうでなければ即時へ振り分ける。

  ```java
  @Override
  public void send(User user, String rawToken) {
      if (TransactionSynchronizationManager.isSynchronizationActive()) {
          TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
              @Override
              public void afterCommit() {
                  doSend(user, rawToken);
              }
          });
          return;
      }
      doSend(user, rawToken);
  }
  ```

  この場合 `AuthServiceImpl` 行157〜159 のコメントはそのままで正しくなる。ただし `AuthServiceImplTest` の `test_確認メールの送信に失敗しても登録は成功する`（行512〜523）は after-commit 化すると送信例外が `register` へ伝わらなくなるため、**例外を握る責務が `AuthServiceImpl#sendVerificationMail` から送信側へ移る**ことを合わせて設計する（テスト1件の付け替えが要る）。
- **案B（呼び出しを境界の外へ出す）** — `register` から送信呼び出しを取り除き、`AuthApi#register` がサービス呼び出しの後で送信する。`AuthResult` に生の確認トークンを載せる必要があり、Web層へトークンが漏れるため案Aより劣る。
- いずれの案を採るにせよ、`tech_auth/account.md` §11 の分岐一覧へ「送信がコミット後に行われる」分岐を追加するかは `detail-design` の担当（本レビューでは扱わない）。

### ISSUE-703: メールアドレスの大文字小文字が正規化されず、同一アドレスで複数アカウントを作れる

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 中 |
| 関連ファイル | backend/afkgame-domain/src/main/java/com/afkgame/domain/service/AuthServiceImpl.java, backend/afkgame-domain/src/main/java/com/afkgame/domain/repository/UserRepository.java, backend/afkgame-initdb/src/main/resources/db/migration/V1__initial_schema.sql |
| 該当箇所 | AuthServiceImpl.java 行164・行173・行213, UserRepository.xml 行27〜32, V1__initial_schema.sql 行24・33 |
| 検出可能工程 | 詳細設計（`tech_auth/account.md` §10 手順2・§12 手順2 にメールの正規化規約が無い） |

**問題の説明:**

登録の重複確認もログインの検索も、受け取った `email` をそのまま等価比較している。

```java
if (userRepository.findByEmail(email) != null) {   // 行164（register）
...
user.setEmail(email);                              // 行173（正規化せず保存）
...
User user = userRepository.findByEmail(email);     // 行213（login）
```

```xml
<select id="findByEmail" resultMap="userResultMap">
  ... WHERE email = #{email}
</select>
```

PostgreSQL の `varchar` 等価比較と `uq_users_email`（`V1__initial_schema.sql` 行33）はいずれも大文字小文字を区別するため、次が成立する。

1. `User@Example.com` で登録 → 成功
2. `user@example.com` で登録 → 手順2の検索に一致せず、`uq_users_email` にも触れず**2件目のアカウントが作られる**
3. 1で登録した利用者が `user@example.com` でログイン → `AUTH_INVALID_CREDENTIALS`（401）

メールのドメイン部は RFC 上大文字小文字を区別しないため、利用者から見れば「登録できたのにログインできない」「同じアドレスで2アカウント持てる」という挙動になる。確認メールの再送・パスワード再設定（STEP 3-A-3）でも同じ経路を使うため、先に決めておかないと影響範囲が広がる。

`tech_auth/account.md` §10 手順2・§12 手順2 と `tech_db/auth.md` のいずれにも正規化の規約が無く（`正規化` / `小文字` / `lower` を grep して0件）、**実装だけで決められない仕様欠落**である。`docs/backlog/known_issues.md` へ登録した。

**修正案:** 方針決定の後に適用する。

- **案A（アプリ層で正規化・推奨）** — `AuthServiceImpl#register` / `#login` の入口で `email.toLowerCase(Locale.ROOT)` を1回だけ適用し、保存も検索も正規化後の値で行う。既存行が無い現段階（Phase 1〜3 はどの言語でも未実装）なので移行データの手当てが不要。`tech_auth/account.md` §9 の共通規約へ「メールは小文字へ正規化して保存・検索する」の1行を足す必要がある（`fix-specs` または `detail-design` の担当）。
- **案B（DB層で担保）** — `email` を `citext` にするか `CREATE UNIQUE INDEX ... ON users (lower(email))` へ置き換える。`V1__initial_schema.sql` の改変になり、`scripts/check_schema_triple.py` の照合対象（DDL ↔ 仕様 ↔ Entity）へ波及する。案Aのほうが影響が小さい。
- どちらの案でも `check_java_conventions.py` は exit 0 のまま（本スクリプトは文字列正規化を見ない）。

### ISSUE-704: `UserIdMDCPutFilter` が体系外の MDC キー `USER` へ意味を成さない値を出力する

| 項目 | 値 |
|------|-----|
| カテゴリ | 一貫性 |
| 重要度 | 中 |
| 関連ファイル | backend/afkgame-web/src/main/java/com/afkgame/web/config/app/SpringSecurityConfig.java, backend/afkgame-web/src/main/java/com/afkgame/web/filter/JwtAuthenticationFilter.java, backend/afkgame-env/src/main/java/com/afkgame/env/logging/LogKey.java |
| 該当箇所 | SpringSecurityConfig.java 行75・行114〜121, JwtAuthenticationFilter.java 行84〜86, LogKey.java 行15〜48 |
| 検出可能工程 | 本レビュー（`check_java_conventions.py` はロガー名を見るが、MDC キーは見ない） |

**問題の説明:**

雛形由来の `UserIdMDCPutFilter` が Security フィルタチェーンへ載ったまま残っている。

```java
http.addFilterAfter(userIdMDCPutFilter(), AnonymousAuthenticationFilter.class);   // 行75
```

このフィルタの実体を jar（`terasoluna-gfw-security-web-5.11.0.RELEASE.jar`）の定数プールで確認すると、MDC キーは文字列 `USER`、値は `Authentication#getPrincipal()` が `UserDetails` なら `getUsername()`、そうでなければ `toString()` である（`USER` / `UserDetails` / `getUsername` / `toString` の各定数を確認）。

本アプリの principal は `JwtAuthenticationFilter` が置く `com.afkgame.domain.model.User` で、`UserDetails` を実装せず `toString()` も定義していない。

```java
SecurityContextHolder.getContext().setAuthentication(
        new UsernamePasswordAuthenticationToken(user, null, List.of()));   // 行85〜86
```

したがって出力される値は `com.afkgame.domain.model.User@1a2b3c4d`（`AbstractMDCPutFilter` の `maxMDCValueLength` で切り詰め）になる。認証不要な `/api/auth/guest` などでは `AnonymousAuthenticationFilter` の principal が入るため `anonymousUser` が出る。

`logback-encoder-text.xml` 行15 の `%mdc` と `JsonLogFormatter` 行64（MDC 全件を同じ階層へ展開）はいずれも MDC を選別しないため、**この値は認証を通る全リクエストのログ行に載る**。

問題は3点。

1. キー `USER` は `LogKey` に存在せず、「項目名は snake_case」（`LogKey` 行10）という体系を破る
2. 値がオブジェクトの `toString()` で、ログとしての情報量がゼロ
3. 認証済みユーザーIDは既に `JwtAuthenticationFilter` 行84 が `player_id` として載せており、役割が重複している

`known_issues.md` #20 が「雛形の gfw ロギング部品が残っている」として3件（`exceptionLoggingFilter`・`traceLoggingInterceptor`・`handlerExceptionResolverLoggingInterceptor`）を挙げているが、**`userIdMDCPutFilter` は列挙から漏れている**。同 #20 へ追記した。

**修正案:**

- `backend/afkgame-web/src/main/java/com/afkgame/web/config/app/SpringSecurityConfig.java` — 行75 の `addFilterAfter` と行114〜121 の `userIdMDCPutFilter()` Bean 定義、行3〜16 の `AnonymousAuthenticationFilter`・`UserIdMDCPutFilter` の import を削除する。認証済みユーザーIDのログ出力は `JwtAuthenticationFilter` 行84 が担うため、削除しても失われる情報は無い。
- 影響範囲を Grep で確認済み: `UserIdMDCPutFilter` / `userIdMDCPutFilter` を参照するのは `SpringSecurityConfig` の6か所のみで、**MDC キー `USER` を検証しているテストは存在しない**（`RequestLogFilterTest` は `request_id`・`method`・`path`・`client_ip`、`JwtAuthenticationFilterTest` は `player_id` のみを見る）。テストの修正は不要。
- 本件は `known_issues.md` #20 の「雛形の gfw ロギング部品除去」と同じ作業単位のため、**#20 の修正時にまとめて適用する**のが手戻りが少ない。

## プロセスへの還元

各指摘の「検出可能工程」を集計すると、**本レビュー 6件 / 詳細設計 3件 / 結合テスト 1件 / テストリスト作成 1件**。詳細設計に3件（ISSUE-701・702・703）が集まっており、分岐一覧の観点に共通の穴がある。

### 1. 分岐一覧へ「トランザクション境界」と「同時実行」の観点を足す（効果が最も大きい）

ISSUE-701（同時リフレッシュ）・ISSUE-702（送信がコミット前）はどちらも、分岐一覧が**単一リクエストの逐次実行だけを列挙している**ことから生まれている。`tech_auth/account.md` §11 は #10・#11 でトランザクションの成功／失敗を持つが、「どの処理が境界の内側か外側か」「同じ資源へ同時に到達したらどうなるか」の行を持たない。

`detail-design` のプロファイルにある分岐一覧の必須観点へ、次の2行を追加することを提案する。

- **境界の内外**: 外部I/O（メール送信・外部API）を伴う手順は、トランザクションの内側・外側のどちらで実行するかを分岐一覧に1行として書く
- **同時実行**: 同一レコードを読んでから更新する手順は、同じレコードへ2本のリクエストが同時到達した場合の期待動作を1行として書く

### 2. `check_java_conventions.py` へ「MDC キーは `LogKey` に定義されたものだけ」を足す

ISSUE-704 は、`LogKey` を経由しない MDC 書き込み（`UserIdMDCPutFilter` の `USER`）が体系を破っていた事例。ロガー名は既に機械判定できている（[ログ] OK）ので、同じスクリプトへ「`MDC.put(` の第1引数は `LogKey.*.field()` の形であること」を1ルール足せば、以後この種の混入は目視なしで落とせる。現状 `MDC.put` を直接書いているのは `RequestLogFilter`（6か所）・`JwtAuthenticationFilter`（1か所）・`LogEntry`（内部実装）で、いずれも `LogKey` 経由のため**追加しても既存コードは全件 OK になる**（Grep で確認済み）。

### 3. 結合テストの必須シナリオへ「新規エンドポイントは永続化まで1本」を足す

ISSUE-707 は、単体テスト（モック）が分岐一覧を完全に覆っていたために、統合テストの空白が見えにくくなっていた事例。`integration-test` のプロファイルにある必須シナリオへ「移行 STEP で追加したエンドポイントは、実DBの行を検証するテストを最低1本持つ」を加えると、STEP 3-A-3 以降で同じ抜けが起きない。

### 4. `LogKey.EMAIL` のような「用意したが使っていない部品」を拾う手立てが無い

ISSUE-705 は、マスク規則まで実装・テスト済みの `LogKey.EMAIL` が本番コードから1度も呼ばれていなかった事例。テストが参照しているためカバレッジでは検出できず（C1 100% でも緑）、`check_java_conventions.py` の対象でもない。enum 定数の「テストからのみ参照」を検出する使い捨てスクリプトを1本書いて、`LoggerName`・`LogReason`・`LogKey` の3 enum に対して回すだけでも棚卸しになる。繰り返すなら常設化を検討する。
