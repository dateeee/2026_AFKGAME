### ISSUE-001: SettingsUpdate に値域バリデーションがなく任意値がDBへ保存される

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 中 |
| 関連ファイル | backend/app/schemas/player.py, backend/app/routers/game.py |
| 該当箇所 | player.py 行52〜56 / game.py 行45〜54 |
| 検出可能工程 | 本レビュー |

**問題の説明:**

`PUT /api/game/settings` の入力に値域検証がどこにもない。

```python
class SettingsUpdate(CamelModel):
    potion_threshold: float | None = None   # ge/le なし
    battle_log_count: int | None = None     # 範囲なし
    auto_sell_rarity: str | None = None     # 任意文字列
```

`potion_threshold=100` や負値がそのまま保存され、`battle_service.py:214` の `character.hp <= effective_max_hp * threshold` の係数として使われる。`hp_threshold`（tower.py 行142）は手書きで範囲検証しているのと非対称。`auto_sell_rarity` は不正値でも 200 が返り、`try_drop` 側で黙って無視される（設定したつもりが効かない）。

**修正案:**

- `schemas/player.py` の `SettingsUpdate` に制約を付ける: `potion_threshold: float | None = Field(default=None, ge=0.0, le=1.0)`、`battle_log_count: int | None = Field(default=None, ge=1, le=100)`（上限値の正は tech_state.md / ui.md と突合）、`auto_sell_rarity: Literal["common","uncommon","rare","epic","legendary"] | None = None`（空文字リセット仕様があるため `""` を許すなら validator で正規化）
- 反映後、境界値テストを test-list の分岐一覧へ追加する

### ISSUE-003: JWT_SECRET の開発デフォルトが31バイトで推奨未満・本番未設定でも起動する

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 中 |
| 関連ファイル | backend/app/config.py |
| 該当箇所 | config.py 行35 |
| 検出可能工程 | 単体テスト（pytest 警告に顕在。警告を fail 扱いにしていれば検出できた） |

**問題の説明:**

```python
JWT_SECRET = os.environ.get("JWT_SECRET", "dev-secret-change-in-production")
```

デフォルト値が31バイトで RFC 7518 §3.2 の HS256 最低推奨（32バイト）未満。pytest 実行時に `InsecureKeyLengthWarning` が繰り返し出ている（362警告の主因）。また本番で `JWT_SECRET` を設定し忘れても公開リポジトリに載っている既知の値で署名されたまま起動する。

**修正案:**

- デフォルトを32バイト以上へ変更（警告解消）
- 本番判定（例: `ENV=production` 環境変数）を config.py に導入し、本番でデフォルト値のままなら起動時に例外で落とす（fail-fast）。秘密情報管理の正は tech_security.md に従う

### ISSUE-004: メール確認トークンとパスワードリセットトークンが用途未分離

| 項目 | 値 |
|------|-----|
| カテゴリ | セキュリティ |
| 重要度 | 中 |
| 関連ファイル | backend/app/routers/auth.py, backend/app/services/auth_service.py, backend/app/models/user.py |
| 該当箇所 | auth.py 行319・343 / auth_service.py 行123〜162 / user.py 行54〜62 |
| 検出可能工程 | 本レビュー |

**問題の説明:**

パスワードリセット要求（auth.py 行319）が `create_email_verification_token` を流用し、確認も同じ `verify_email_token` を使う。結果:

1. **登録時のメール確認トークンでパスワードリセットが実行できる**（`password_reset_confirm` は同テーブルの未使用トークンなら何でも受理する）
2. リセット確認の副作用で `user.email_verified = True` が立つ（verify_email_token 内、auth_service.py 行161）
3. 逆に `GET /verify-email` にリセットトークンを渡してもメール確認として消費される

どちらのトークンも同一メール所有の証明ではあるため直ちに権限昇格にはならないが、有効期限も用途も異なるべきトークンが相互流用できるのは設計欠陥。

**修正案:**

- `EmailVerificationToken` に `purpose: Mapped[str]`（`"verify_email"` / `"password_reset"`）を追加し（Alembic マイグレーション込み）、発行・検証の両方で用途一致を要求する
- `password_reset_confirm` からは email_verified を立てない（用途分離後は自然に解消）
- tech_auth.md にパスワードリセットのトークン仕様の記載が見当たらないため、仕様側への追記は doc-review / requirements の管轄（下記「担当範囲外の言及」参照）

### ISSUE-005: ログ extra のホワイトリスト欠落により主要キーが出力されない（開発用トークン出力も機能していない）

| 項目 | 値 |
|------|-----|

| 該当箇所 | logging_config.py 行35〜37・56〜59 / auth.py 行146〜149・320〜323 |
| 検出可能工程 | 本レビュー |

**問題の説明:**

TextFormatter / JsonFormatter は既知キーの列挙方式だが、実際に `extra=` で渡しているキーの多くが列挙にない: `user_id`（認証系ログ全部）、`verification_token`・`reset_token`（「開発用ログ出力」が前提のメール確認・リセットフロー）、`email`、`highest_floor`・`slot_index`・`base_id`（日替わりショップ）、`slot`・`items_sold`・`gold_earned`（装備）。

- 恒久策としてはホワイトリスト方式をやめ、`record.__dict__` から標準属性を除いた残りを出力する方式も検討（キー追加漏れの再発防止）

### ISSUE-012: SQLAlchemy 旧API `Query.get()` の使用と冗長な装備取得フォールバック
