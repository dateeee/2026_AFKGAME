# AFK GAME — 酒場スカウト処理

> Phase 4。`POST /api/base/scout` の排出設定の解決・抽選・重複判定・キャラ生成を定める。
> **数値の正**: 排出率は [CHARACTERS_OVERVIEW.md §4.1](../../data/characters/CHARACTERS_OVERVIEW.md)、ガチャプールのキャラ定義は [characters/](../../data/characters/) のタイプ別ファイル §3、スカウト費用と酒場のしきい値は [economy.md §2.9](../../design/systems/economy.md)。本書は**処理**のみを持つ。
> 建設・レベルアップと施設効果の解決規則は [tech_base.md](tech_base.md)。

## 1. 適用範囲と方針

| 項目 | 内容 |
|------|------|
| 対象 | `POST /api/base/scout`（酒場でのキャラクター1体獲得） |
| 施設 | `tavern` のみ。LV0（未建設）では実行不可 |
| 回数 | 1リクエスト＝**1体**（連続ガチャ・複数抽選は持たない） |
| 進行状態 | 全状態で許可（[tech_state.md §4](tech_state.md) の `POST /api/base/*` 行） |
| 乱数 | [tech_rng.md §1](tech_rng.md) #14「累積確率・レアリティ順」。RNGは §2 のとおりメソッド引数で受け取る |
| 永続化 | `characters` へ1行追加（[tech_db/player.md §4](../basic/tech_db/player.md)）。ゴールド減算と同一トランザクション |
| エラーコード | 新設しない。`BASE_NOT_BUILT`・`BASE_INSUFFICIENT_GOLD` は `tech_base.md` §6 が正 |

- リクエストボディを持たないため、Bean Validation による `422` は発生しない
- 未認証は共通の `401`（[tech_api/common.md](../basic/tech_api/common.md)）。本書の分岐一覧では扱わない

## 2. 排出設定の解決（酒場LV → 排出率・費用）

酒場の効果表は **LV1〜LV10 を全レベル列挙**しており、解決規則は `tech_base.md` §2.1 に従う（**酒場LVと一致する行を引くだけ**。しきい値検索・補間を行わない。LV0 は該当行なし）。
採用した行から次の2つを引く。

| 引くもの | 正となるファイル |
|---------|----------------|
| レアリティ別排出率 | `characters/CHARACTERS_OVERVIEW.md` §4.1 の該当LV列 |
| スカウト費用（ゴールド） | `economy.md` §2.9 酒場表の該当行 |

- スカウト可能レアリティが同じLVでも排出率は必ず向上する（据え置きのLVを作らない。`tech_base.md` §2.1）
- 排出率・費用を実装へハードコードしない（不変条件「データ駆動」）

## 3. 抽選アルゴリズム

**レアリティ → キャラクター**の2段階で抽選し、乱数を**必ずこの順で2回**消費する（`tech_rng.md` §3 の消費順序固定）。

### 3.1 レアリティ抽選（累積確率）

1. 排出率は**整数パーセント**のままマスターから引き、コモン → アンコモン → レア → エピック → レジェンダリーの**表の行順**に累積する
2. 一様乱数 `r`（`[0,1)`）を1つ引き、`r × 100 < 累積パーセント` を満たす**最初の**レアリティを採用する
3. 「-」（未開放のレアリティ）は**0%**として扱い、累積を進めない

- 判定を `r < p` に統一する規約（`tech_rng.md` §1）に従うため、0% のレアリティは決して選ばれない
- 確率を小数へ変換してから累積しない（浮動小数の加算誤差で最終累積が 100 未満になり、最後のレアリティが外れる経路を作らないため）
- 採用行の排出率の**合計が100でない**場合はマスターデータ不正として例外を送出する（`tech_rng.md` §5 #6 と同じ扱い）。合計が100であれば最終累積は必ず 100 となり、`r × 100 < 100` は常に真になるので「どのレアリティにも当たらない」経路は存在しない

### 3.2 キャラクター抽選（離散一様）

1. プール20体（`characters/` のタイプ別ファイル §3）から、3.1 で決めたレアリティの候補を抽出する（各レアリティ4体・タイプ均等）
2. 候補を**マスターIDの昇順**に並べ、`[0, 候補数)` の離散一様乱数で1体を採る
3. 候補が0体ならマスターデータ不正として例外を送出する

- 並び順をIDの昇順に固定するのは、同一シードで同一の結果を再現できるようにするため（`tech_rng.md` §3）
- タイプによる重み付けは行わない（同レアリティ内は均等確率）

## 4. 処理フロー（`POST /api/base/scout`）

入口条件: 認証済みであること。リクエストボディは持たない。

1. プレイヤーの `players` 行を**行ロック**して取得する（ゴールド消費の競合を防ぐ。`tech_base.md` §3 手順2 と同じ方式）
2. 酒場の現在LVを取得する（`facilities` に行が無ければ LV0）
3. 現在LV が **0** → `400 BASE_NOT_BUILT`（状態は変更せず、**乱数も消費しない**）
4. §2 で採用しきい値行を決め、排出率とスカウト費用を引く
5. 所持ゴールドが費用に満たない → `400 BASE_INSUFFICIENT_GOLD`（状態は変更せず、**乱数も消費しない**）
6. §3 の抽選でマスターキャラを1体決める
7. 同一 `master_id` のキャラを既に所持しているかを判定する（重複判定）
8. 所持ゴールドから費用を引く
9. §5 のとおり `characters` へ1行追加する（**重複でも行を作る**）
10. 手順8〜9を1トランザクションでコミットする。途中で失敗した場合は全件ロールバックする

出口条件: ゴールド減算とキャラ1行追加が**ともに成立**しているか、**いずれも起きていない**かのどちらか。

- 検証（手順3・5）は**すべて抽選と消費の前**に行う。抽選後に失敗する経路を持たない（乱数を消費したのに獲得できない状態を作らない）
- 重複でもキャラ行を作るのは、限界突破が「同一キャラ1体」を素材に取るため（`master/character.md` §8。スカウトの重複規則は `characters/CHARACTERS_OVERVIEW.md` §4）。[tech_party.md §2](tech_party.md) の「既所持なら付与しない」は**塔クリア報酬のみ**の規則であり、スカウトには適用しない
- 追加したキャラをパーティへ自動編入しない（控えとして加入。`tech_party.md` §2 手順3 と同じ）
- キャラクターの所持数に上限は設けない（倉庫の所持枠はアイテムのみが対象。`tech_base.md` §2.3）

## 5. 加入時のキャラクター生成

| 列 | 設定する値 |
|----|-----------|
| `master_id`・`name`・`type`・`rarity` | プール（`characters/` のタイプ別ファイル §3）の定義値をそのまま入れる |
| `level`・`exp`・`skill_points`・`limit_break` | LV1・0・0・0（習得スキルなし・装備なし） |
| `base_atk`・`base_def`・`base_spd`・`max_hp` | `master/character.md` §1.2 の**タイプ別 LV1 基礎値をそのまま**入れる |
| `hp` | `max_hp` と同値 |

- 基礎値へ**レアリティ倍率を掛けない**。倍率と限界突破ボーナスは読み取り時に実効値（[tech_data/game_state.md §1.1.2](../basic/tech_data/game_state.md) の `effectiveAtk` 等）として算出する。保存値に含めると二重適用になる
- 加入時LVが1である点は `characters/CHARACTERS_OVERVIEW.md` §3 の確定入手キャラと同じ（**仮置き**。調整は [balance_backlog.md](../../backlog/balance_backlog.md) B-8）

## 6. API

| 項目 | 内容 |
|------|------|
| リクエスト | ボディなし |
| 成功 | `200`。`character`（追加したキャラ）・`isDuplicate`・`canLimitBreak`・`gold`（更新後）を返す |
| 失敗 | `400 BASE_NOT_BUILT` / `400 BASE_INSUFFICIENT_GOLD`（`tech_base.md` §6）。形式は [tech_error_handling.md](../basic/tech_error_handling.md)「統一エラーレスポンス形式」 |

- 新規と重複で**レスポンスの形を変えない**（`isDuplicate` で区別する）。フロントは1つの型で受け取り、表示だけを分ける
- `canLimitBreak` は「重複であり、かつ既所持の同一キャラに突破回数が上限未満のものが1体以上ある」ときだけ `true`。限界突破そのものは `POST /api/character/limit-break`（別途）で行い、本APIでは実行しない

## 7. 分岐一覧（単体テスト観点）

| # | 分岐点 | 条件 | 期待する振る舞い |
|---|-------|------|----------------|
| 1 | 施設行の有無 | `facilities` に酒場の行がある | その行のLVを現在LVとする |
| 2 | 施設行の有無 | `facilities` に酒場の行が無い | 現在LVを0とみなす |
| 3 | 酒場LV | LV1以上 | 排出設定の解決へ進む |
| 4 | 酒場LV | LV0（未建設） | `400 BASE_NOT_BUILT`。乱数を消費せず状態を変更しない |
| 5 | 効果表の解決 | 酒場LVと一致する行が表にある | その行の排出率・費用を採用する |
| 6 | 効果表の解決 | 酒場LVと一致する行が表に無い | マスターデータ不正として例外を送出する |
| 7 | ゴールド | 所持ゴールドが費用を上回る | 抽選へ進む |
| 8 | ゴールド | 所持ゴールドが費用とちょうど同じ | 抽選へ進む（境界は実行可） |
| 9 | ゴールド | 所持ゴールドが費用に満たない | `400 BASE_INSUFFICIENT_GOLD`。乱数を消費せず状態を変更しない |
| 10 | 排出率の整合 | 採用行の排出率の合計が100 | 抽選する |
| 11 | 排出率の整合 | 採用行の排出率の合計が100でない | マスターデータ不正として例外を送出する |
| 12 | レアリティ抽選 | 乱数が先頭レアリティの累積未満 | 先頭のレアリティを採用する |
| 13 | レアリティ抽選 | 乱数が中間の累積境界の直前 | 手前側のレアリティを採用する |
| 14 | レアリティ抽選 | 乱数が中間の累積境界ちょうど | 次のレアリティを採用する（`r < 累積` のため境界は次側） |
| 15 | レアリティ抽選 | 乱数が取り得る最大値 | 最後のレアリティを採用する |
| 16 | レアリティ抽選 | 排出率が0%のレアリティ | 決して採用しない |
| 17 | キャラ抽選 | 該当レアリティの候補が1体以上 | ID昇順の並びから離散一様で1体を採る |
| 18 | キャラ抽選 | 該当レアリティの候補が0体 | マスターデータ不正として例外を送出する |
| 19 | 乱数消費 | 抽選に到達した | レアリティ → キャラの順に必ず2回消費する |
| 20 | 乱数消費 | 検証で弾かれた（未建設・ゴールド不足） | 乱数を1回も消費しない |
| 21 | 重複判定 | 同一マスターIDの所持が無い | 新規として扱う |
| 22 | 重複判定 | 同一マスターIDを1体所持している | 重複として扱う（キャラ行は新規と同様に作る） |
| 23 | 重複判定 | 同一マスターIDを2体以上所持している | 重複として扱う（体数で振る舞いを変えない） |
| 24 | 限界突破の可否 | 重複で、既所持の同一キャラに突破回数が上限未満のものがある | 素材として使用可（`canLimitBreak` を真）と返す |
| 25 | 限界突破の可否 | 重複だが、既所持の同一キャラがすべて突破回数の上限に達している | 使用不可（`canLimitBreak` を偽）と返す |
| 26 | 限界突破の可否 | 新規 | 使用不可（`canLimitBreak` を偽）と返す |
| 27 | パーティ | キャラを追加した | パーティは変更しない（控えに加入） |
| 28 | トランザクション | ゴールド減算とキャラ追加がともに成功 | コミットし更新後の値を返す |
| 29 | トランザクション | ゴールド減算とキャラ追加の途中で失敗 | 全件ロールバックし状態を変更しない |

> WARN許容 #27: 追加後の無条件処理で、対になる条件を持たないため1行（追加しない経路では編成に触れる余地がない）。`tech_party.md` §2 #4 と同じ扱い。
