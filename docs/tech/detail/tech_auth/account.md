## 9. 3操作に共通する規約

| 項目 | 規約 |
|------|------|
| 認証の要否 | register・login は認証不要。**logout は `Authorization: Bearer <access_token>` が必須**（`tech_api/common.md` §5.0 の認証不要リストに logout は無い） |
| パスワードハッシュ | bcrypt（`BCryptPasswordEncoder`・strength 12）。値の正は §1 |
| リフレッシュトークン | 48バイトの乱数を Base64URL（パディングなし）で表した生値をクライアントへ返し、DBには SHA-256（16進小文字）だけを保存する。ゲスト作成（§8.2 手順7）・refresh と同じ方式 |
| 有効期限 | アクセス30分・リフレッシュ30日（§1）。いずれも現在時刻からの相対で決める |
| 現在時刻 | 1リクエストにつき同一の時刻源から1回だけ取得した UTC 値を使う（テストで固定するため） |
| バリデーション違反 | 422 `VALIDATION_ERROR`（Bean Validation。対応表は [exception.md](../../../process/coding_standards_backend/exception.md)） |
| エラー応答 | `{"error": {"code", "message", "requestId"}}`。コードは AUTH_ 一覧から選び、本工程で新設しない |
| ログ | メールはマスクして出す（`tech_logging.md`「ログフォーマット」）。パスワードとトークン生値は出力しない |

## 10. アカウント登録（`POST /api/auth/register`）

入口条件: 認証不要。ボディ `{ email, password }`。
出口条件: users 1行・プレイヤー初期状態（§8.2 手順2〜6）・確認トークン1行・リフレッシュトークン1行が単一トランザクションで永続化され、トークンペアと `user` を 200 で返す（応答例は §5）。

1. ボディを検証する。`email` は必須・メール形式・255文字以内、`password` は必須・8文字以上（§1「パスワード要件」）。違反は 422 を返し、以降を実行しない
2. `email` で `users` を検索する。行があれば 409 `AUTH_EMAIL_TAKEN` を返し、何も作らない（相手がゲスト・Google連携のみのアカウントでも同じ）
3. パスワードを bcrypt でハッシュ化する
4. ユーザーを作成する（`user_<UUID4>`、`is_guest = false`、`email_verified = false`、`display_name` は列の既定値、`created_at`・`last_login_at` は現在時刻、`google_id` は NULL）
5. §8.2 の手順2〜6 を同じ順序で実行し、プレイヤー初期状態を作る（内部の分岐は §8.3 が持ち、本書では再掲しない）
6. 確認トークンを1件作成する（`purpose = verify_email`、`expires_at` は現在時刻 + 24時間、`used = false`）。生値のハッシュだけを保存する
7. トークンペアを発行する（§9）
8. 手順3〜7 を単一トランザクションでコミットする
9. コミット後に確認メールの送信を要求する。**送信はトランザクションの外**で行い、成否を応答へ反映しない（失敗は WARN ログだけを残す）。送信手段（SMTP設定・本文・再送）は verify-email の詳細設計で定める

パスワード確認欄はフロントだけで照合し、APIは受け取らない（[ui/onboarding.md](../../../design/systems/ui/onboarding.md)「登録タブ」）。

## 11. 分岐一覧（アカウント登録）

| # | 分岐点 | 条件 | 期待する振る舞い |
|---|-------|------|----------------|
| 1 | メール形式 | メールアドレスとして妥当な形式 | 手順2へ進む |
| 2 | メール形式 | `@` を欠く等で形式が不正 | 422 `VALIDATION_ERROR` を返し、ユーザーを作らない |
| 3 | メール長 | 255文字以内 | 手順2へ進む |
| 4 | メール長 | 256文字以上 | 422 `VALIDATION_ERROR` を返す |
| 5 | パスワード長 | 8文字以上 | 手順3へ進む |
| 6 | パスワード長 | 7文字以下（空文字を含む） | 422 `VALIDATION_ERROR` を返す |
| 7 | メール重複 | 同じ `email` を持つ行が無い | 登録を続行する |
| 8 | メール重複 | 同じ `email` を持つ行が既にある | 409 `AUTH_EMAIL_TAKEN` を返し、何も作らない |
| 9 | メール重複 | 手順2の通過後、挿入時に `uq_users_email` 違反が起きる（同時登録） | 全体をロールバックし 409 `AUTH_EMAIL_TAKEN` を返す |
| 10 | 登録トランザクション | 手順3〜7 がすべて成功 | コミットし、トークンペアと `user` を 200 で返す |
| 11 | 登録トランザクション | 手順3〜7 の途中で失敗（初期化の失敗・DBエラー） | 全体をロールバックし、ユーザー・プレイヤー・確認トークン・リフレッシュトークンのいずれも残さない |
| 12 | 確認メール送信 | 送信に成功 | 応答を変えない |
| 13 | 確認メール送信 | 送信に失敗 | WARN ログを残し、登録は成功として 200 を返す（確認トークンの行は消さない） |

## 12. ログイン（`POST /api/auth/login`）

入口条件: 認証不要。ボディ `{ email, password }`。
出口条件: `last_login_at` を更新し、リフレッシュトークンを1件追加して、トークンペアを 200 で返す。

1. ボディを検証する。`email` は必須・メール形式、`password` は必須。**登録時の「8文字以上」はログインでは課さない**（要件変更より前に作られたアカウントを締め出さないため）。違反は 422 を返す
2. `email` で `users` を検索する。行が無ければ 401 `AUTH_INVALID_CREDENTIALS`
3. `password_hash` が NULL なら、bcrypt 照合を行わず 401 `AUTH_INVALID_CREDENTIALS`（Google連携のみのアカウント）
4. bcrypt で照合する。不一致は 401 `AUTH_INVALID_CREDENTIALS`
5. `email_verified` の値でログインを止めない（§3「未確認状態でもログイン・プレイは可能」）
6. `last_login_at` を現在時刻へ更新する
7. トークンペアを発行する（§9）。**既存のリフレッシュトークンは失効させない**（複数端末の同時ログインを許容する。失効はログアウトと refresh のローテーションだけが行う）

手順2〜4 はいずれも同じコードとメッセージを返し、メールとパスワードのどちらが誤りかを区別させない。ゲストは `email` が NULL のため手順2の検索に一致しない。

## 14. ログアウト（`POST /api/auth/logout`）

入口条件: `Authorization: Bearer <access_token>` が必須。ボディ `{ refreshToken }`。
出口条件: 対象のリフレッシュトークンが `revoked = true` になり、`{"status": "ok"}` を 200 で返す。

1. アクセストークンを検証してユーザーを特定する（全エンドポイント共通の認証処理。失敗時のコードは AUTH_ 一覧）
2. ボディの `refreshToken` を検証する（必須）。違反は 422 を返す
3. 生値の SHA-256 で `refresh_tokens` を検索する。行が無ければ 401 `AUTH_REFRESH_INVALID`
4. 行の `user_id` が手順1のユーザーと異なれば 401 `AUTH_REFRESH_INVALID`（他人のトークンを失効させない）
5. 既に `revoked = true` なら更新せず 200 を返す。**§4の再利用検知（ユーザーの全トークン失効）はログアウトでは行わない** — 二重ログアウトは再送信や複数タブで起きる正常操作であり、全端末の切断は過剰なため
6. 期限切れのトークンでも `revoked = true` へ更新する（期限切れと失効は両立する）
7. 更新をコミットし `{"status": "ok"}` を返す

フロント側の破棄手順（アクセストークン・リフレッシュトークン・ゲストID）は §3「ログアウト」が正。

## 15. 分岐一覧（ログアウト）

| # | 分岐点 | 条件 | 期待する振る舞い |
|---|-------|------|----------------|
| 1 | アクセストークン | 有効なトークンを提示 | 手順2へ進む |
| 2 | アクセストークン | 欠落・形式不正・期限切れ・署名不正 | AUTH_ 一覧に従い 401 を返し、リフレッシュトークンを変更しない |
| 3 | リフレッシュトークン指定 | ボディに `refreshToken` がある | 手順3へ進む |
| 4 | リフレッシュトークン指定 | 未指定または空文字 | 422 `VALIDATION_ERROR` を返す |
| 5 | トークンの存在 | ハッシュが一致する行がある | 手順4へ進む |
| 6 | トークンの存在 | 一致する行が無い | 401 `AUTH_REFRESH_INVALID` を返す |
| 7 | トークンの持ち主 | 認証ユーザー自身のトークン | 手順5へ進む |
| 8 | トークンの持ち主 | 別ユーザーのトークン | 401 `AUTH_REFRESH_INVALID` を返し、対象を失効させない |
| 9 | 失効状態 | `revoked` が false | `true` へ更新して 200 を返す |
| 10 | 失効状態 | `revoked` が既に true | 更新せず 200 を返す（冪等）。ユーザーの他トークンも失効させない |
| 11 | 有効期限 | `expires_at` が現在時刻より後 | 失効させて 200 を返す |
| 12 | 有効期限 | `expires_at` が現在時刻以前 | 期限内と同じく失効させて 200 を返す |
