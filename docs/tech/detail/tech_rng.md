# AFK GAME — 乱数設計

> 技術仕様の索引は [tech_spec.md](../tech_spec.md)。戦闘処理は [tech_battle.md](tech_battle.md)、丸め規約は [tech_numeric.md](tech_numeric.md)、tick制御は [tech_tick.md](tech_tick.md)。
> 戦闘結果はサーバー権威で確定するため、乱数の扱いは **再現性**（バグ調査）と **テスト容易性**（C1網羅100%）の両立が要件となる。

## 1. 乱数の一覧

| # | 用途 | 分布 | 判定 | 定義元 |
|---|------|------|------|-------|
| 1 | ダメージ分散 | 一様 `[-0.1, 0.1)` | `ATK × (1 + r)` | `tech_battle.md` §3.1 |
| 2 | クリティカル | 一様 `[0,1)` | `r < crit_rate` | tech_battle §3.1 |
| 3 | 通常攻撃のターゲット | 離散一様 | 生存者から1体 | tech_battle §3.3 |
| 4 | 挑発 | 一様 `[0,1)` | 累積確率比較 | tech_battle §3.1.3 |
| 5 | 麻痺による行動不能 | 一様 `[0,1)` | `r < 0.3` | tech_battle §3.1 |
| 6 | 状態異常の付与 | 一様 `[0,1)` | `r < 付与率` | [master_data.md §9](../../data/master_data.md) |
| 7 | エンカウント抽選 | 重み付き | `weight` に比例 | tech_battle §3.2 |
| 8 | 敵の出現数 | 離散一様 | min〜max | tech_battle §3.2 |
| 9 | 装備ドロップ判定 | 一様 `[0,1)` | `r < drop_rate` | [master/equipment.md](../../data/master/equipment.md) |
| 10 | 装備レアリティ（ドロップ） | 順次独立判定 | レジェンダリー→アンコモンの順に `r < 補正後確率` | [systems/equipment.md](../../design/systems/equipment.md) |
| 11 | 装備のステータス種別・値 | 離散一様 / 一様 | — | master/equipment.md |
| 12 | HP吸収の付与 | 一様 `[0,1)` | `r < 0.10` | master/equipment.md |
| 13 | アイテムドロップ | 一様 `[0,1)` | `r < rate` | [tech_data.md §1.2](../basic/tech_data.md) |
| 14 | 酒場スカウト | 累積確率 | レアリティ順 | CHARACTERS_OVERVIEW §4.1 |
| 15 | 装備製作（鍛冶屋・ランダム製作） | 離散一様 | ベース → 付与数 → ステータス種 の順 | [tech_forge/craft.md §4.1](tech_forge/craft.md) |

**境界の統一規約**: 確率判定はすべて **`r < p`** とする（`r <= p` は使わない）。これにより `p = 0` は決して発生せず、`p = 1` は必ず発生する。

## 2. RNGの扱い

| 項目 | 仕様 |
|------|------|
| 実体 | `java.util.Random` の**インスタンス**を1つ生成し、tick処理の入口から引数（DIではなくメソッド引数）で受け渡す |
| 静的・共有インスタンスの直接参照 | **禁止**（テストでのシード固定がプロセス全体に波及し、並行リクエスト間で干渉するため） |
| 生成単位 | 1リクエスト（1回の `/api/battle/tick`）につき1インスタンス |
| シード | 通常は未指定（`new Random()` の既定エントロピー）。調査時のみ環境変数 `BATTLE_RNG_SEED` で固定できる |
| 永続化 | RNGの内部状態はDBに保存しない（リクエスト間で持ち越さない） |
| 適用範囲 | 戦闘・ドロップ・装備生成・スカウトを含む全サービスが同一インスタンスを受け取る（乱数源を1本化する） |

- インスタンス注入により、単体テストは `new Random(42)` を渡すだけで完全に決定的になる
- 特定分岐の網羅には、`nextDouble()` 等の戻り値を列で与えるスタブ（テストダブル）を用いる
- **言語を跨いだ再現性は保証しない**。`java.util.Random` は線形合同法であり、Python の Mersenne Twister（旧実装）とはアルゴリズムが異なるため、同一シードでも生成される乱数列は一致しない

## 3. 再現性の範囲

| 対象 | 再現性 | 理由 |
|------|-------|------|
| 同一プロセス（JVM）・同一シード・同一入力 | **完全に再現する** | 消費順序を固定しているため |
| Python実装（移行前）との再現性 | **保証しない** | 乱数アルゴリズムが異なるため、同一シードでも結果は一致しない。シード固定テストの期待値は Java 側で再生成する |
| 本番の戦闘結果の事後再現 | 再現しない | シードを保存しないため。調査は戦闘ログ（`tech_data.md` §1.3）で行う |
| ロールバック後の再計算 | 結果は変わる | クライアント未返却の区間のため差異は観測されない（`tech_tick.md` §4） |

**消費順序の固定**: 乱数は §1 の番号順ではなく、`tech_battle.md` §3.1 の**ターン処理フローの記述順**で消費する。分岐によって消費数が変わる場合も「消費しない分岐では消費しない」を守り、数合わせのダミー消費は行わない。

## 4. 乱数を使わない領域

| 領域 | 方式 | 定義元 |
|------|------|-------|
| オフライン簡略計算（101tick以上） | 期待値による確定計算 | [tech_offline.md §4.1](tech_offline.md) |
| 同SPD時の行動順 | キャラID昇順（固定タイブレーク） | tech_battle §3.1 |
| 同条件ターゲットの決定 | キャラID昇順 | tech_battle §3.1 |
| 簡略計算での全滅判定 | 確定判定 | tech_offline §4 |

- 「正規シミュレーション（乱数あり）」と「簡略計算（期待値）」の境界は100tick（`FAST_CALC_THRESHOLD`）。同じ状態でも計算方式が変われば結果が変わることを仕様として許容する

## 5. 分岐一覧（単体テスト観点）

| # | 観点 | テスト方法 |
|---|------|-----------|
| 1 | 確率0%の事象が発生しない | `p=0` で1,000回試行し発生0件 |
| 2 | 確率100%の事象が必ず発生する | `p=1` で必ず発生 |
| 3 | クリティカル発生／非発生の両分岐 | `r` を `crit_rate` の直前・直後に固定 |
| 4 | ダメージ分散の上下限 | `r = -0.1` / `r = 0.0999…` |
| 5 | 重み付き抽選で各要素が選ばれる | 累積境界の直前・直後の値を与える |
| 6 | 重み合計が0のエンカウントプール | マスターデータ不正として例外を送出 |
| 7 | 生存者0体でのターゲット選択 | 呼び出されないこと（呼ばれたら例外） |
| 8 | 並行リクエストでの乱数干渉 | 2インスタンスを別シードで同時実行し結果が独立すること |
| 9 | 生存者ありのターゲット抽選（#7 の正常系） | 候補に生存者と戦闘不能者を混ぜ、`nextInt(生存者数)` を1回だけ消費して生存者から1体を返すこと |
