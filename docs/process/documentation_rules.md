# AFK GAME — ドキュメント規約

> 本書は AFK GAME の Markdown ドキュメント（要件定義〜詳細設計の成果物）の記述規約を定める。
> プロジェクト概要は [README.md](../../README.md)、工程定義は [development_process.md](development_process.md) を参照。

| 分冊 | 担当節 |

## 1. 目的

AIエージェント（Claude Code）と人間が共同で開発するため、ドキュメントは「人が読める」だけでなく **「AIが1回の読み込みで理解できる」** 必要がある。

- **コンテキスト効率**: 巨大ファイルは全文読込でコンテキストを圧迫し、他の必要情報を押し出す
- **参照精度**: 1ファイル1テーマなら、必要な箇所だけを正確に参照できる
- **編集の安全性**: 巨大ファイルの部分編集は前後の文脈欠落により矛盾を生みやすい
- **レビュー効率**: ファイルが小さいほど変更の影響範囲が明確になる

→ **「1ファイル = 1テーマ = 1回の読み込みで完結」** を原則とする。

## 2. 適用範囲

- 対象: リポジトリ内の全 `.md` ファイル
- 除外: `node_modules/`、`docs/reviews/`、`docs/changelog.md`（いずれも追記型アーカイブ。通常の作業では読み込まない）
- ただし `docs/reviews/` は文字数ではなく**件数**でローテーションする（[§9](documentation_rules/reviews.md)）

## 3. 文字数上限

文字数は **UTF-8の文字数**（バイト数ではない）で数える。

| 区分 | 対象 | 推奨 | 上限 | 根拠 |
|------|------|------|------|------|
| **A. 常時読込** | `CLAUDE.md` | 2,500 | **3,000** | 全セッション・全ターンで読み込まれるため最も厳格 |
| **B. 索引** | `README.md`、`**/*_OVERVIEW.md` | 4,000 | **6,000** | 目次として全体を見渡す。詳細は持たない |
| **C. 仕様・設計・データ** | `docs/**`（設計図 `docs/diagrams/**` を含む） | 6,000 | **8,000** | 1テーマを1回の読み込みで完結できる粒度 |
| **D. エージェント定義** | `.claude/**`（スクリプト・フックを含む全体） | 4,000 | **5,000** | スキル起動時に読み込まれる |
| **除外** | `docs/reviews/**`、`docs/changelog.md`、`node_modules/**` | — | — | 追記型アーカイブ（§5.1・[§9](documentation_rules/reviews.md)） |

### 3.1 上限を緩和する例外

| 対象 | 倍率 | 理由 |
|------|------|------|
| `docs/process/coding_standards_backend.md` と同名ディレクトリ配下 | **×1.5**（区分C 12,000字・H2 3,000字・H3 1,500字） | 準拠元（TERASOLUNA 開発ガイドライン）の章立てに沿って「規約 + ガイドラインとの差分」を1テーマへ書き切る必要がある。これ以上割ると「どの規約がどの分冊か」の探索コストが上限の効果を上回る |

例外は `check_doc_size.py` の `RELAXED_PREFIXES` / `RELAXED_FACTOR` が持つ。**増やすときは本表と同時に更新する**。

### 上限8,000字の根拠

本プロジェクトで既に「1エンティティ = 1ファイル」に分割済みの `docs/data/towers/`（1,915〜7,808字）・`docs/data/skills/`（1,916〜3,906字）は、**全ファイルが8,000字未満**に収まっている。一方、未分割の `game_spec.md`（35,042字）・`tech_spec.md`（27,052字）は上限の3〜4倍。
適切に分割された「1テーマ」の自然なサイズが8,000字であることを、本リポジトリの実績が示している。

## 4. セクション粒度

| 対象 | 上限 | 超過時の対処 |
|------|------|-------------|
| H2（`##`）セクション | 2,000字 | H3へ分割、またはセクションごと子ファイルへ切り出す |
| H3（`###`）セクション | 1,000字 | 表への置き換え、または記述の圧縮 |

- 1ファイルの H2 は **7個以内**（多すぎる場合は複数テーマの混在を疑う）
- 見出し階層は **H3まで**。H4が必要になったら子ファイルへ分割する
- H2・H3の上限にも §3.1 の緩和倍率が効く（緩和対象は H2 3,000字・H3 1,500字）
- Mermaid図1枚で構成されるセクション（`class_diagram/`・`er_diagram/` 等）は分割しても可読性が上がらないため2,000字超を許容し、`--sections` の WARN として扱う

## 5. 記述スタイル

文字数を増やさないための記述ルール。

- **表を優先**: 列挙的な情報（数値・パラメータ・API一覧）は散文ではなく表で書く
- **1行1事実**: 1つの箇条書きに複数の事実を詰め込まない
- **重複禁止**: 同じ数値・仕様を複数ファイルに書かない。正となるファイルを1つ決め、他はリンクする。正の宣言は [spec_ownership.md](spec_ownership.md) の対応表へ登録する（`check_docs.py --owner` が逸脱を検出する）
- **前置き禁止**: 「〜について説明します」等の導入文を書かない
- **コード例は最小限**: 完全なコードではなく、構造が分かる最小の抜粋にする
- **変更履歴を各ファイルに書かない**: [changelog.md](../changelog.md) へ集約する（§5.1）
- **未作成ファイルへリンクしない**: 別タスクへ切り出した成果物は Markdown リンクではなく `パス` のコード表記で書く（`check_docs.py --links` がリンク切れで落ちる）。作成タスクで索引登録とセットにリンク化する
- **ソース内のパス参照は手で直す**: `check_docs.py` は Markdown しか走査しない。ドキュメントを移動・改名したら `backend/**/*.java` の Javadoc 内パスも grep して同じ変更で直す

### 5.1 変更履歴は1ファイルへ集約する

**個々のドキュメントに変更履歴セクションを置かない。** 改稿時は `changelog.md` の先頭（最新日付ブロック）へ `| ファイル | 内容 |` を1行追記する。

理由 — 変更履歴は**本文が増えなくても単調増加する**唯一の要素であり、文字数予算を静かに食い潰す。

| | 移行前 | 移行後 |
|---|-------|-------|
| `tech_spec.md` | 4,191字（履歴 **47%**） | 2,219字 |
| `game_spec.md` | 4,619字（履歴 **39%**） | 2,824字 |
| `CLAUDE.md` | 2,987字（上限3,000の**残99.6%消費**） | 2,520字 |

索引ファイルほど本文が短く、かつ§6の「履歴は親に集約」で子の履歴まで集まるため、**履歴が本文を上回る**状態に陥っていた。集約先の `changelog.md` は上限対象外（§2）とし、通常の作業では読み込まない。完全な履歴は Git（`git log -- <path>`）が持つため、changelog は人間向けの一覧に徹する。

## 6. 分割パターン

### 6.1 ハブ&スポーク（推奨・本プロジェクトの標準形）

親を索引にし、詳細を子ファイル（区分C）へ移す。**索引 `X.md` と子ディレクトリ `X/` は兄弟に置く**（[§10](documentation_rules/directories.md)）。

```
docs/tech/detail/
├── tech_forge.md        # 索引: 鍛冶屋の共通ルール・分冊リンク表
└── tech_forge/          # 子: 1テーマ = 1ファイル
    ├── enhance.md
    ├── craft.md
    └── disassemble.md
```

索引を `X/` の**中**に置かないのは、分割の前後で索引のパスを変えないため。`X.md` が育って分割に至っても `X.md` は動かず、外部（他の仕様書・`.claude/**`・Javadoc）からの参照が生き残る。内側方式は分割の瞬間に `X.md` → `X/X_OVERVIEW.md` の移動が必ず起き、最も参照の多いファイルを動かすことになる。

`docs/data/{towers,skills}/` は索引が内側（`*_OVERVIEW.md`）の旧形。揃えるには区分Bの判定（§3）と `check_doc_size.py` を同時に変える必要があり未着手。

### 6.2 サブシステム分割

機能単位で切り出す。例: `game_spec.md` の §2.x（キャラクター・戦闘・装備…）を1機能1ファイルへ。

### 6.3 レイヤー分割

同一テーマを抽象度で分ける。例: `tech_spec.md` → データ設計 / API設計 / アーキテクチャ方針。

### 分割時の必須事項

1. 親ファイルに子ファイルへの**リンク表**を残す（リンク切れ = 情報の喪失）
2. 親から移した内容は親から**削除**する（重複させない）
3. **節番号は維持**する（`§2.4` を子ファイル側でも `2.4` のまま使う）。既存のリンク・アンカー・レビュー指摘の参照が生き残る
4. **変更履歴は親にも子にも置かない**（§5.1）。分割した旨は `changelog.md` へ1行記録する
5. 子ファイルのヘッダに **親へのリンク**と担当節を明記する
6. [docs/INDEX.md](../INDEX.md) と、`.claude/project/**` の対象ファイル一覧を更新する
7. リンク切れがないことを確認する（相対パスは移動先を基準に張り直す）
8. `docs/tech/**` の子ファイルは、テスト側の分岐マーカーを**親ディレクトリ名つき**にする（`分岐: tech_forge/craft.md §10 #1`）。`check_branch_list.py` は層ディレクトリ（`basic`/`detail`/`nonfunctional`）だけを落とした名前で照合する

### 6.4 ファイル名の付け方

**`親_子.md` は使わない**（親子か対等かが名前から判別できない）。判定は**子のヘッダが親を索引と宣言しているか**で行う。

| 関係 | ヘッダの書き方 | 形 | 例 |
|------|--------------|----|----|
| 親子 | 「親: X.md」「X.md の子ファイル」「索引側が正」 | `X.md` + `X/子.md` | `tech_api.md` + `tech_api/common.md` |
| 対等 | 相互に「〜が正」と参照し合うだけ | 共通接頭辞を持たない別名（索引は上流） | `tech_structure.md`（§2〜§3）と `tech_backend.md`（§4）。索引は `tech_spec.md` |

## 7. 判定と超過時の運用サイクル

```bash
python scripts/check_doc_size.py          # 判定（未登録の上限超過・変更履歴があれば exit 1）
python scripts/check_doc_size.py --list   # 全ファイルの文字数一覧
python scripts/check_doc_size.py --sections  # H2セクションの文字数も表示
python scripts/check_docs.py              # リンク・索引到達性・曖昧語・正の逸脱・決定先送り・台帳存否（違反は exit 1）
```

- **検出は都度**: 新規作成・改稿時に両方実行する。`doc-review`・`diagrams-review` の判定項目にも含める
- **修正は一括**: 超過をその場で圧縮しない。台帳へ溜め、横並びで圧縮か分割かを判断してまとめて是正する

| 検出 | 対応 |
|------|------|
| 新規超過（区分B・C） | スクリプトの `KNOWN_OVERSIZED`（台帳）へ**是正方針を1行添えて登録**し作業を継続する。登録済みは WARN（exit 0） |
| 新規超過（区分A・D） | **同一セッション内に是正**（台帳登録不可。作業を中断せずタスクの区切りで、移管を優先して行う）。毎ターン・スキル起動ごとに読み込まれ、放置コストが読込回数に比例するため |
| 変更履歴セクションの復活 | **即時修正**（1行移動で済む。§5.1。スクリプトが `## 変更履歴` 等の見出しを検出する） |
| 残量WARN（上限の90%超） | 対応不要。次の追記で超過し得る早期警戒であり、一括是正時の分割候補 |

- **是正で情報を消さない**（全区分共通）: ①子ファイルへの移管・分割（§6）②表化・重複排除（§5）の順で行い、固有の事実は削らない。やむを得ず削る場合は削除内容を `changelog.md` の1行へ明記する
- **一括是正**: 台帳を入力とする専用タスクとして工程の区切りに実施する（`fix-specs` の対象外。分割は §6 の手順に従い、解消した行は台帳から削除する）
- **締切**: Phase完了ゲート時点で台帳が空であること（工程は跨いでよいが Phase は跨がない）
