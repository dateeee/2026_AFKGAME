# 要件定義（工程1）

**目的**: 「何を作るか」を、後工程が設計判断で迷わない粒度まで確定する。実装方式は決めない（それは基本設計）。

## 0. 最初に読む

| 順 | ファイル | 内容 |
|----|---------|------|
| 1 | `.claude/project/profile.md` | 技術スタック・ディレクトリ・不変条件・コスト規律 |
| 2 | `.claude/project/requirements.md` | 成果物の配置・参照順・固有の観点・確定後の反映先 |

以降「プロファイル」はこの2ファイルを指す。**プロファイルに書かれた読み込み範囲を守る**（全文読み込みをしない）。

## 1. スコープの特定

確定する対象（機能・カテゴリ・Phase・個別項目）を特定する。示されていない場合は未確定項目の一覧を提示して選んでもらう。**一覧表示の時点では仕様書を読まない。**

## 2. 現状把握

プロファイルの参照順に従い、**該当セクションのみ**読む。

1. 項目の文面から関連する仕様書を推定する
2. Grep で見出し・キーワードを検索して行番号を特定する
3. Read の offset/limit で該当セクション周辺のみ読む

確定済み仕様から生じる**制約**を整理する。プロファイルの不変条件に抵触する案は、この時点で除外する。

## 3. 対話による確定

項目を1つずつ（密接に関連するものはグループで）提示する。

| 要素 | 内容 |
|------|------|
| 背景 | なぜ未確定か、なぜ確定が必要か、どの仕様に影響するか |
| 制約 | 確定済み仕様から生じる制約条件 |
| 提案 | 案A（推奨）／案B／案C。各案の内容・メリット・デメリット |
| 推奨理由 | ジャンル慣習・バランス・実装複雑度を踏まえた判断 |

- **必ず推奨案を明示する**。選択肢を並べるだけにしない
- 実装難易度が高い案は、その旨を伝えたうえでシンプルな代替案も出す
- 既存仕様と矛盾する場合は明示してユーザーの判断を仰ぐ
- 数値バランスは**仮置きでも確定**し、実装後の実測で調整する前提で進める
- ユーザーが「後回し」「保留」とした項目はスキップする

## 4. 仕様書への反映

反映前に確認を取る（「この内容で仕様書に反映してよいですか？」）。承認後、プロファイルの「確定後の反映先」に従って反映する。

| # | 作業 |
|---|------|
| 1 | 関連仕様書へ確定内容を追記・更新する。既存の文体・フォーマットに合わせ、**複数ファイルはまとめて更新**して整合を保つ |
| 2 | 数値・計算式・分岐条件は**一意に読める**表現で書く（「適宜」「おおよそ」を使わない） |
| 3 | 未確定の数値には「仮置き」と明記する |
| 4 | 未確定管理ファイルの該当項目を**削除**する（チェック済みで残さない） |
| 5 | 変更履歴はプロファイルが指定する集約先へ追記する |

**同じ値を複数ファイルに書かない。**正となるファイルを1つ決め、他はリンクする。

## 5. 整合性チェック（工程内で必ず行う）

反映した内容が**要件定義の成果物どうしで矛盾していないか**を、この工程の中で確認する。
横断レビュー（`doc-review`）へ丸投げしない。ここで潰せる矛盾を残したままゲートへ渡さない。

### 5.1 機械的に検証する（目視しない）

スクラッチパッドに使い捨てスクリプトを書き、出力だけを取り込む。プロファイルの「整合性チェック」表に検証項目がある場合はそれに従う。

| 対象 | 検証内容 |
|------|---------|
| リンク | 今回追加・変更した相対リンクの参照先が実在するか |
| 未確定の取りこぼし | 「TBD」「未定」「後日検討」等が本文に残り、未確定管理ファイルに未登録でないか |
| 数値の重複 | 今回書いた数値が他ファイルにも書かれていないか（正が1つに定まっているか） |
| 用語 | 今回使ったID・名称が用語集の表記と一致するか |
| 規約 | 文字数上限チェックが通るか |

### 5.2 読んで確認する（今回の変更範囲のみ）

| # | 観点 | 判定 |
|---|------|------|
| 1 | 自己整合 | 確定内容が、同じ成果物内の既存記述と矛盾しないか |
| 2 | 相互整合 | 確定内容が、関連する他の要件定義成果物と矛盾しないか |
| 3 | 不変条件 | プロファイルの不変条件に抵触していないか |
| 4 | 段階整合 | 機能の割り当て（Phase・リリース単位）が全記述で一致しているか |
| 5 | 派生影響 | 確定によって**新たに未確定になった項目**がないか。あれば未確定管理ファイルへ登録する |
| 6 | 前提の明示 | 言及だけされて詳細が未定義のまま残った機能がないか |

**プロファイルの「固有の観点」表も必ず適用する。**

### 5.3 矛盾が見つかったら

| 状況 | 対応 |
|------|------|
| 今回の確定内容が誤っている | §3 に戻ってユーザーに確認し、確定し直す |
| 既存記述が古い | 既存側を更新する。影響範囲を完了報告に明記する |
| どちらが正か判断できない | **勝手に決めない**。ユーザーに提示して判断を仰ぐ |

## 6. 完了報告

| 項目 | 内容 |
|------|------|
| 確定した項目 | 項目名と確定内容（1行ずつ） |
| 反映先 | 更新したファイルと該当セクション |
| 整合性チェック | §5 の結果。検出した矛盾と、その解消内容 |
| 残件 | 未確定のまま残った項目と、その理由 |
| 次の一手 | 残件がある場合は「続きは再実行してください」と案内する |

## 7. 完了基準

プロファイルの完了基準に加え、以下を満たすこと。

- 対象項目がすべて解消され、仕様書へ反映されている
- **§5 の整合性チェックで検出した矛盾がすべて解消されている**（判断保留はユーザー確認済み）
- 数値のみ未定の項目は、実装をブロックしないよう別ファイルへ退避してある
- ドキュメント規約チェックが通る

## 8. 次工程

1. 仕様確定ゲート: `doc-review` スキル → 指摘を `fix-specs` スキルで反映
2. `basic-design` スキルへ引き継ぐ

**ゲートスキルは自動起動しない。**完了報告で次に実行すべきスキル名を提示して終了する。

## 注意事項

- **実装方式を決めない**。API設計・DB設計・画面構成は基本設計の担当
- 1回の実行で扱う項目数の上限はプロファイルに従う。超える場合は再実行を案内して終了する
- ユーザーが選んでいない案を「決まったこと」として仕様書に書かない
