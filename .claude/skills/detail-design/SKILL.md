# 詳細設計（工程3）

**目的**: 対象機能を「仕様書だけで一意に実装できる」粒度まで具体化する。あわせて**分岐一覧**を作り、後続のテストとC1網羅の導出元にする。

## 0. 最初に読む

| 順 | ファイル | 内容 |
|----|---------|------|
| 1 | `.claude/project/profile.md` | 技術スタック・ディレクトリ・不変条件・コスト規律 |
| 2 | `.claude/project/detail-design.md` | 成果物・参照順・固有の観点・分岐一覧の記法 |

**プロファイルに書かれた読み込み範囲を守る**（該当セクションのみ読む）。

## 1. スコープの特定

詳細化する対象（機能・処理・Phase）を特定し、影響する成果物をプロファイルの成果物表から洗い出す。

## 2. 入力の確認

基本設計の成果物から、対象の骨格を**該当セクションのみ**読む。

| 確認項目 | 内容 |
|---------|------|
| API | 入出力の構造と型 |
| データ | 参照・更新するエンティティと属性 |
| 横断規約 | 乱数・数値/丸め・状態遷移の既定ルール |
| 既存の詳細設計 | 同種の処理が既にあれば、その記述粒度と用語に揃える |

骨格が未確定なら `basic-design` スキルでの確定を先に提案する。

## 3. 処理を詳細化する

| 領域 | 決めること |
|------|----------|
| 処理フロー | 手順を順序づけて書く。入口条件と出口条件を明示する |
| 計算式 | 演算子・優先順位・**丸め方向と桁**まで書く |
| 分岐条件 | 比較演算子（`<` か `<=` か）を明示する |
| 境界の挙動 | 上限・下限・ゼロ・空・未登録・未知IDのときどうなるか |
| 乱数 | 何を抽選するか、シードの決まり方、確率の適用順 |
| 状態 | 処理前後で状態がどう変わるか。失敗時にどこまで巻き戻すか |
| 数値 | マスターデータの具体値。未確定なら**「仮置き」と明記**する |

**曖昧語を書かない。**「適宜」「おおよそ」「必要に応じて」が残っていたら詳細化が足りていない。

## 4. 分岐一覧を作る（本工程の必須成果物）

各処理仕様に分岐一覧を記載する。**これが唯一の導出元**であり、後続工程はここから機械的にテストを作る。

記法はプロファイルの「分岐一覧」節に従う。共通ルール:

| # | ルール |
|---|-------|
| 1 | **条件は真偽の両方**を書く（片側だけでは分岐網羅に届かない） |
| 2 | ループは「0周・1周・2周以上」を分ける |
| 3 | 例外経路（未知ID・未登録・権限なし・外部失敗）を漏らさない |
| 4 | 「残量がある / 尽きた」のように**仕様上の意味**で書く。実装表現（`if x > 0`）で書かない |
| 5 | 1行1観点。複数の分岐を1行にまとめない |

## 5. 整合性チェック（工程内で必ず行う）

詳細設計は**数値・式・分岐**が複数ファイルに散るため、この工程の中で突き合わせる。`doc-review` へ丸投げしない。

### 5.1 機械的に検証する（目視しない）

スクラッチパッドに使い捨てスクリプトを書き、出力だけを取り込む。

| 対象 | 検証内容 |
|------|---------|
| 数値の重複 | 同じパラメータが複数ファイルに書かれていないか。書かれている場合は値が一致するか |
| ID・名称 | 参照しているIDがマスターデータ側に実在するか。逆に定義だけで未参照のIDがないか |
| 合計値 | 確率・重み・配分の合計が想定値（100%等）になっているか |
| リンク | 今回変更した相対リンクの参照先が実在するか |
| 曖昧語 | 「適宜」「おおよそ」「TBD」「未定」が本文に残っていないか（grep） |
| 規約 | 文字数上限チェックが通るか |

### 5.2 読んで確認する（今回の変更範囲のみ）

| # | 観点 | 判定 |
|---|------|------|
| 1 | 上流整合 | 基本設計の入出力・データ構造で、この処理が成立するか |
| 2 | 一意な実装可能性 | 仕様書だけで**一意に**実装できるか。読み手によって解釈が割れる箇所がないか |
| 3 | 丸めの明示 | 除算・乗算の結果に丸め方向と桁が書かれているか |
| 4 | 境界の網羅 | 上限・下限・ゼロ・空・未登録の挙動がすべて定義されているか |
| 5 | 横断規約の適用 | 乱数・数値/丸め・状態遷移が横断規約と矛盾していないか |
| 6 | 不変条件 | プロファイルの不変条件に抵触していないか |
| 7 | 仮置きの明示 | 未確定の数値に「仮置き」と明記され、調整待ち管理へ登録されているか |

**プロファイルの「固有の観点」表も必ず適用する。**

### 5.3 分岐一覧の自己検証（最重要）

分岐一覧は後続工程の唯一の入力なので、**処理フローと1対1で突き合わせる**。

| # | 確認 | 不足していたら |
|---|------|--------------|
| 1 | 処理フローに書いた条件分岐が、すべて一覧に載っているか | 一覧に追加する |
| 2 | 各条件に**真・偽の両方**の行があるか | 欠けている側を追加する |
| 3 | ループに 0周・1周・2周以上 の行があるか | 追加する |
| 4 | 例外経路（未知ID・未登録・失敗）の行があるか | 追加する |
| 5 | 一覧の行が、処理フローのどこにも対応しない | 処理フローの記述漏れを疑う。どちらが正か確認して揃える |
| 6 | 期待する振る舞いが「〜する」と**一意に**書けているか | 曖昧なら処理フロー側の詳細化不足 |

### 5.4 矛盾が見つかったら

| 状況 | 対応 |
|------|------|
| 数値が複数ファイルで食い違う | 正となるファイルを1つ決め、他はリンクに置き換える |
| 基本設計では実現できない処理になっている | §3 に戻る。骨格の変更が必要なら `basic-design` スキルを提案する |
| どちらの値が正か判断できない | **勝手に決めない**。ユーザーに提示して判断を仰ぐ |

## 6. 完了報告

| 項目 | 内容 |
|------|------|
| 詳細化した処理 | 処理名と、確定した式・分岐 |
| 更新した成果物 | ファイルと該当セクション |
| 分岐一覧 | 処理ごとの分岐件数 |
| 整合性チェック | §5 の結果。検出した矛盾と、その解消内容 |
| 仮置き | 「仮置き」と明記した数値と、その調整タイミング |

## 7. 完了基準

プロファイルの完了基準に加え、以下を満たすこと。

- 対象機能の数値・計算式・分岐条件が仕様書から一意に実装できる
- **各処理仕様に分岐一覧があり、§5.3 の自己検証を通過している**
- §5 の整合性チェックで検出した矛盾がすべて解消されている（判断保留はユーザー確認済み）
- ドキュメント規約チェックが通る

## 8. 次工程

1. 仕様確定ゲート: `doc-review` スキル
2. `test-list` スキルへ引き継ぐ（分岐一覧を失敗するテストへ落とす）

**ゲートスキルは自動起動しない。**完了報告で次に実行すべきスキル名を提示して終了する。

## 注意事項

- **実装コードを書かない**。それは製造工程の担当
- 数値をコードにハードコードさせる書き方をしない（データ駆動で設計する）
- 後続工程で分岐一覧に無い分岐が見つかった場合は、**本工程に戻って一覧を更新**してからテスト・実装を直す
