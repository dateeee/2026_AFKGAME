# テストリスト作成（工程4）

**目的**: 詳細設計の**分岐一覧**を1観点1テストへ展開し、**実装前に失敗するテスト**として置く。ここで作ったテストが製造工程の唯一の完了判定になる。

## 0. 最初に読む

| 順 | ファイル | 内容 |
|----|---------|------|
| 1 | `.claude/project/profile.md` | 技術スタック・ディレクトリ・不変条件・コスト規律 |
| 2 | `.claude/project/test-list.md` | 成果物・対象範囲・入力・フィクスチャ・記述規約・固有の観点 |

**プロファイルに書かれた読み込み範囲を守る**（該当セクションのみ読む）。

## 1. スコープの特定

対象モジュールを特定し、プロファイルの「対象と適用範囲」表で**TDD適用対象か**を判定する。
適用外の領域（型チェックや結合テストで検証する範囲）なら、その旨を伝えて対象から外す。

対象が示されていない場合は、プロファイルの「入力」表が指す分岐一覧から**まだテストへ展開していない候補を提示して選んでもらう**。
**選ばれるまでテストを書き始めない。**

## 2. 入力の確認（分岐一覧）

**分岐一覧が唯一の入力**。プロファイルの「入力」表に従い、該当セクションのみ読む。

| 状況 | 対応 |
|------|------|
| 分岐一覧がある | 各行をそのままテスト1件へ対応づける |
| 分岐一覧が無い | **テストを書き始めない**。`detail-design` スキルでの作成を提案して止める |
| 分岐一覧が粗い | 不足分を列挙してユーザーへ提示し、詳細設計へ追記してから進める |

**分岐一覧に無いテストを勝手に足さない。** 必要だと気づいたら詳細設計へ戻す。

## 3. テストを書く

テストを書き始める前に [references/patterns.md](references/patterns.md)（一般的な実装パターン）を読む。プロジェクト固有の実例はプロファイルが指すファイル。

| # | ルール |
|---|-------|
| 1 | 分岐一覧の1行 = 1テスト。対応が追えるようテスト名へ**分岐の意味**を書く |
| 2 | 分岐は「真/偽」でなく**仕様上の意味**で表現する（テスト名がそのまま設計の説明になる） |
| 3 | 境界値・等価クラスはパラメータ化にまとめ、各ケースへ意図のコメントを付ける |
| 4 | 外部要因（乱数・時刻・外部I/O）は**必ず固定**する。固定しないと分岐を選べない |
| 5 | 期待値は**直書き**する。実装を呼んだ結果を期待値にしない |
| 6 | 1テスト1観点。複数の分岐を1つのテストに詰め込まない |

さらにプロファイルの「記述規約」表に従う。

## 4. Red を確認する

対象のテストを実行し、以下2点を満たすこと。

- 全件が **FAIL または ERROR** になる
- **落ち方が期待どおり**（未実装なら `ImportError` / `AttributeError`、実装済みなら `AssertionError`。想定外の `TypeError` はテスト側のバグ）

**1件でも最初から PASS する場合**、そのテストは分岐を検証できていない（アサーションが弱い／既存挙動をなぞっているだけ）。書き直す。

## 5. 工程内検証（必ず行う）

分岐一覧との対応漏れは、後工程では**カバレッジ不足として初めて表面化する**。この工程の中で潰す。

### 5.1 機械的に検証する（目視しない）

| 対象 | 検証内容 |
|------|---------|
| 件数の対応 | 分岐一覧の行数と、収集されたテスト件数が対応するか |
| 実行結果 | 全件 FAIL / ERROR か。PASS が混じっていないか |
| 命名の重複 | 同名のテスト関数が上書きされていないか |
| 実装の混入 | 本工程の差分にプロダクトコードが含まれていないか（`git status` / `git diff --name-only`） |

### 5.2 読んで確認する（今回追加した範囲のみ）

| # | 観点 | 判定 |
|---|------|------|
| 1 | 一覧との対応 | 分岐一覧の全行にテストがあるか。対応表を作って埋まっているか確認する |
| 2 | 両側の網羅 | 各条件に**真・偽の両方**のテストがあるか |
| 3 | ループ | 0周・1周・2周以上が分かれているか |
| 4 | 例外経路 | 未知ID・未登録・失敗のテストがあるか |
| 5 | 外部要因の固定 | 乱数・時刻が固定され、実行のたびに結果が変わらないか |
| 6 | 期待値の独立 | 期待値が実装を参照して作られていないか |
| 7 | テストの独立性 | 実行順やテスト間の共有状態に依存していないか |

**プロファイルの「固有の観点」表も必ず適用する。**

### 5.3 過不足が見つかったら

| 状況 | 対応 |
|------|------|
| 一覧にあるがテストが無い | テストを追加する |
| テストがあるが一覧に無い | **詳細設計へ戻して一覧に追記**する。一覧を更新しないまま残さない |
| 一覧の記述では期待値が決まらない | 詳細設計の詳細化不足。`detail-design` スキルへ差し戻す |
| 最初から PASS してしまう | アサーションを見直す。それでも通るなら既に実装済み。対象範囲を見直す |

## 6. 完了報告

| 項目 | 内容 |
|------|------|
| 追加したテスト | ファイルと件数 |
| 分岐一覧との対応 | どの分岐をどのテストで押さえたか |
| Red の結果 | 全件失敗の実行結果と、落ち方 |
| 差し戻した項目 | 分岐一覧に不足していた分岐 |

## 7. 完了基準

プロファイルの完了基準に加え、以下を満たすこと。

- 分岐一覧の全項目にテストが対応している
- 全件が**期待どおりに失敗する**（Red）
- プロダクトコードを1行も書いていない
- §5 の工程内検証で検出した過不足がすべて解消されている

## 8. 次工程

`dev` スキルへ引き継ぐ（Red → Green → Refactor を1テストずつ回す）。
**次工程は自動起動しない。**完了報告で次に実行すべきスキル名を提示して終了する。

## 注意事項

- **実装を書かない**。テストを通したくなっても製造工程の担当
- テストが通らないときに**期待値のほうを書き換えない**
- 既に網羅済みの実装に対する遡及整備・カバレッジ補完は `unit-test` スキルの担当
