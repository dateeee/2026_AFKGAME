# 単体テスト（工程6）

**目的**: 実装済みコードの**C1（分岐網羅）を測定し、100%まで補完する**。行網羅（C0）100%では不十分。
テストリスト工程のテストだけでは C1 に届かないことがある（分岐一覧の漏れ）。ここで検出して**上流へ戻す**。

## 0. 最初に読む

| 順 | ファイル | 内容 |
|----|---------|------|
| 1 | `.claude/project/profile.md` | 技術スタック・ディレクトリ・不変条件・コスト規律 |
| 2 | `.claude/project/unit-test.md` | 対象・配置・コマンド・固有の分岐観点・除外規則 |

テストの書き方（記述規約・フィクスチャ・実装パターン）は `test-list` 側の資産を使う。ここでは重複させない。

## 1. 対象を決めて現状を測る

プロファイルの「コマンド」表に従って測定する。対象を絞れる場合は絞って回す（全体測定は時間がかかる）。
対象が示されていない場合は、測定結果から**未達分岐が残るモジュールを候補として提示し**、選んでもらってから補完に入る。

**この工程の入口は「実装が存在する」こと。** 実装が無い新規機能は `test-list` スキルの担当。
カバレッジ計測が未設定のプロジェクトでは、先に導入の可否をユーザーへ確認する（設定・コマンドはプロファイルへ追記する）。

## 2. 未達分岐を特定する

レポートの読み方と構文別の観点は [references/c1_checklist.md](references/c1_checklist.md)。**補完に入る前に必ず読む。**

| 表記 | 意味 |
|------|------|
| `35-40` | その行が一度も実行されていない（C0未達） |
| `181->189` | 181 → 189 の**分岐だけ**が未実行（C1未達） |
| `263->233` | 後方ジャンプ = ループが**再び回る**分岐が未実行 |
| `429->exit` | その行から**関数を抜ける**分岐が未実行 |

未達が多いときは HTML レポート（部分分岐が色分けされる）で原因を特定する。

## 3. 未達分岐を潰す

1件ずつ、**その分岐を通す最小の入力**を持つテストを足す。

| # | ルール |
|---|-------|
| 1 | 観点は「真/偽」でなく**仕様上の意味**で言語化する |
| 2 | カバレッジのためだけのテストを書かない。**期待する振る舞い**を検証する |
| 3 | 既存テストのアサーションを増やして済ませない。1テスト1観点を保つ |
| 4 | 補完で見つけた分岐は、詳細設計の**分岐一覧へ逆反映**する |

**プロファイルの「固有の分岐観点」表を必ず適用する。**

### 潰せない分岐が残ったら

| 状況 | 対応 |
|------|------|
| 通常経路で作れない（外部I/O失敗・DB制約違反） | モックで例外を強制して通す |
| どう入力しても到達しない | **実装側のデッドコードを疑う**。仕様の抜けか不要コードのことが多い |
| 仕様が未確定で期待値を決められない | 勝手に決めない。ユーザーへ提示して判断を仰ぐ |
| どうしても通せない | プロファイルの除外規則に従い、**理由コメント必須**で除外する |

**カバレッジを通すためだけの除外指定は禁止。**

## 4. 工程内検証（必ず行う）

### 4.1 機械的に検証する（目視しない）

| 対象 | 検証内容 |
|------|---------|
| カバレッジ | C1 100% の判定コマンドが exit 0 になるか |
| 部分分岐 | 部分分岐の残件数がゼロか |
| 全体実行 | 対象を絞らずに全テストを流して全PASSか（絞った測定で見落とす退行を防ぐ） |
| 除外指定 | 除外指定の件数と、それぞれに理由コメントがあるか |
| 実装の混入 | 本工程の差分にプロダクトコードが含まれていないか（`git diff --name-only`） |

### 4.2 読んで確認する（今回追加した範囲のみ）

| # | 観点 | 判定 |
|---|------|------|
| 1 | 検証の実質 | 追加したテストが**振る舞い**を検証しているか。分岐を通すだけになっていないか |
| 2 | 期待値の根拠 | 期待値が仕様から導かれているか。実装の出力をそのまま写していないか |
| 3 | 上流への反映 | 補完した分岐が分岐一覧へ反映されているか |
| 4 | 疑義の記録 | 検出した実装の疑義（仕様乖離・デッドコード）が記録されているか |
| 5 | 独立性 | 実行順やテスト間の共有状態に依存していないか |

### 4.3 期待値が仕様と食い違ったら

**実装の出力に合わせてテストを書かない。** どちらが正かを確定してから直す。

| 状況 | 対応 |
|------|------|
| 実装が誤り | 疑義として記録し、修正するか否かをユーザーへ確認する |
| 仕様が誤り・不足 | `detail-design` スキルへ差し戻す |
| 判断できない | ユーザーに提示して判断を仰ぐ |

## 5. 完了報告

| 項目 | 内容 |
|------|------|
| 追加・修正したテスト | ファイルと件数 |
| カバレッジ | 対象の **C1 前後の数値** |
| 逆反映 | 分岐一覧へ追記した分岐 |
| 除外 | 除外指定した箇所と理由（あれば） |
| 疑義 | 検出した実装の不具合・仕様の疑義と、その記録先 |

## 6. 完了基準

プロファイルの完了基準に加え、以下を満たすこと。

- 全テスト PASS かつ **C1カバレッジ100%**
- 補完した分岐が詳細設計の分岐一覧へ反映されている
- 除外指定にすべて理由コメントがある
- 検出した疑義が記録されている

## 7. 次工程

`integration-test` スキルへ引き継ぐ。
**次工程は自動起動しない。**完了報告で次に実行すべきスキル名を提示して終了する。

## 注意事項

- **実装を直さない**。疑義は記録し、修正の要否はユーザーの判断を仰ぐ
- 到達不能な分岐を見つけたら、除外の前に**まず削除できないか**を検討する
- 製造で機能を追加・変更したら、**同一変更内で100%を維持**する（後回しにしない）
