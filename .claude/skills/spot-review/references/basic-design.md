# 基本設計のレビュー観点（一般）

> 工程2「基本設計（ハイレベル設計）」の成果物（システム構造・API設計・データモデル・画面構成・非機能の実現方式）に当てる**プロジェクト非依存**の観点。
> 固有の対象ファイル・上乗せ観点は `.claude/project/review/spot.md`。使い方は [SKILL.md](../SKILL.md) §2。

**この工程の問いは「要件を満たす骨格になっているか」**。計算式・数値の具体化は工程3の担当。
設計図（Mermaid等）との整合は `diagrams-review` の担当なので、ここでは扱わない。

## 1. 観点表

| 分類 | # | 観点 | 典型的な兆候 |
|------|---|------|------------|
| 追跡 | 1 | **全要件がどこかの設計要素に割り当て**られているか | 要件にある機能に対応する設計が無い |
| 追跡 | 2 | 逆に、**対応する要件が無い設計要素**が無いか | 誰も求めていない拡張点が設計に入っている |
| 追跡 | 3 | 設計判断の**根拠と却下した代替案**が残っているか | 結論だけで、後から覆される |
| 構造 | 4 | レイヤ・コンポーネントの**責務が重複せず**分離されているか | 同じ判定が2箇所の責務に書かれている |
| 構造 | 5 | 依存の向きが**一方向**か（循環依存が無いか） | 下位層が上位層の型を参照する |
| 構造 | 6 | 分割の粒度が妥当か（1コンポーネントの責務が多すぎ / 少なすぎ） | 「共通」「ユーティリティ」に何でも入る |
| 構造 | 7 | 状態の**持ち主が1つ**に決まっているか | 同じ状態をクライアントとサーバーの両方が権威として持つ |
| インタフェース | 8 | API の**命名・粒度・HTTPメソッドと状態コードの意味づけ**が統一されているか | 同種の操作が別の動詞・別のコードを返す |
| インタフェース | 9 | **冪等性**・再送時の挙動が定義されているか | 同じリクエストの二重送信で二重に処理される |
| インタフェース | 10 | ページング・ソート・フィルタの規約が統一されているか | エンドポイントごとにパラメータ名が違う |
| インタフェース | 11 | **エラー応答の形式とコード体系**が統一されているか | 一部だけ独自形式・生の例外メッセージ |
| インタフェース | 12 | 互換性の方針（バージョニング・任意項目の追加ルール）があるか | 破壊的変更の扱いが未定義 |
| データ | 13 | 主キー・一意制約・外部キー・NULL可否・型と桁が決まっているか | 「ID」だけで型・生成方式が未定 |
| データ | 14 | 正規化 / 非正規化の**選択に根拠**があるか | 重複保持の同期タイミングが未定義 |
| データ | 15 | 導出値（集計・キャッシュ列）の**更新契機**が決まっているか | いつ再計算されるか読めない |
| データ | 16 | 検索・一覧の**アクセスパターンに対する索引方針**があるか | 全件走査が前提になっている |
| 画面 | 17 | 全画面に**到達経路**があり、戻る・キャンセルの経路が定義されているか | 遷移先だけあり戻り先が無い画面 |
| 画面 | 18 | **初期表示・空状態・読み込み中・エラー時**の表示が決まっているか | 正常データがある場合しか定義が無い |
| 画面 | 19 | 画面が必要とするデータと API の応答が**過不足なく対応**するか | 画面に出す項目が応答に無い |
| 非機能 | 20 | 認証・認可の**方式と適用範囲**が決まっているか | 「認証する」だけで、保護対象の一覧が無い |
| 非機能 | 21 | **トランザクション境界**と同時実行制御（ロック・楽観排他）の方針があるか | 複数更新の原子性が未定義 |
| 非機能 | 22 | 外部依存の**失敗時の振る舞い**（タイムアウト・リトライ・縮退）が決まっているか | 成功前提の設計 |
| 非機能 | 23 | ログ・監査・監視の出力方針（レベル・相関ID・機微情報の除外）があるか | 何を残すか未定義 |
| 非機能 | 24 | 性能目標に対する**実現手段**が示されているか | 目標値だけで手段が無い |
| 非機能 | 25 | 移行・初期データ投入・ロールバック手順があるか | 初回リリースしか想定していない |

## 2. 見落とされやすいもの

| # | 内容 |
|---|------|
| 1 | **削除・無効化の設計**。作成と更新は設計されるが、削除時の関連データ・参照整合が抜ける |
| 2 | **境界をまたぐ型の一致**。API の型・必須性が、データモデルと画面のどちらとも微妙にずれる |
| 3 | **時刻とタイムゾーン**。保存する型（時点か日付か）と表示の基準が未定義 |
| 4 | **一覧と詳細の不整合**。同じ概念を返す2つの応答で項目名・粒度が違う |
| 5 | **アーキテクチャ不変条件の侵食**。個別最適な設計が、全体の前提（権威の所在・層分離）を崩す |

## 3. 機械的に検証できる項目

| 対象 | 検証内容 |
|------|---------|
| 型・スキーマ | 設計書の項目定義とデータ定義の両側を抽出して差分を取る |
| エンドポイント一覧 | 設計書のAPI一覧と実装の対応（欠落・余剰）を数え上げる |
| 参照整合 | 外部キー・参照先エンティティが定義済みか |
| 画面到達性 | 遷移定義から到達不能な画面・出口の無い画面を列挙する |
| 相対リンク・節番号 | 参照先が実在するか |
