# 製造のレビュー観点（一般）

> 工程5「製造」の成果物（実装コード）に当てる**プロジェクト非依存**の観点。言語・フレームワークに依存する規約は
> `.claude/project/review/spot.md` の上乗せ観点と、プロジェクトのコーディング規約が正。使い方は [SKILL.md](../SKILL.md) §2。

**この工程の問いは「設計どおりに、壊れずに動くか」**。設計そのものの是非は工程2・3へ差し戻す。

## 1. 観点表

| 分類 | # | 観点 | 典型的な兆候 |
|------|---|------|------------|
| 正しさ | 1 | **設計書の式・定数・分岐条件と実装が一致**するか | 係数が設計書と違う、丸めの位置が違う |
| 正しさ | 2 | 境界条件（off-by-one・`>=` と `>`・ループ端）が正しいか | 最後の1件が処理されない |
| 正しさ | 3 | null / 空 / 未設定の扱いが設計どおりか | 空リストで例外、null が既定値に化ける |
| 正しさ | 4 | 型変換・桁あふれ・整数除算の切り捨てが意図どおりか | 整数割り算で小数が消える |
| 正しさ | 5 | 条件式の論理（否定・複合条件・短絡）が意図どおりか | ド・モルガンの取り違え |
| 正しさ | 6 | 同じ入力で**同じ結果**になるか（暗黙の状態依存が無いか） | 呼び出し順で結果が変わる |
| エラー処理 | 7 | 例外を**握り潰して**いないか（捕捉して何もしない） | 空の catch、ログだけで処理継続 |
| エラー処理 | 8 | 捕捉の粒度が適切か（広すぎる捕捉が想定外の不具合を隠さないか） | すべての例外を1つにまとめて握る |
| エラー処理 | 9 | 失敗時に**リソースが解放**されるか（接続・ファイル・ロック） | 例外経路でクローズされない |
| エラー処理 | 10 | **トランザクション境界**と巻き戻し条件が設計どおりか | 例外時に一部だけ確定する |
| エラー処理 | 11 | エラー応答・エラーコードが統一形式か | 一部だけ独自形式を返す |
| 構造 | 12 | **レイヤの責務**を越えていないか（上位層にロジックが漏れていないか） | 入出力層に業務判定が書かれる |
| 構造 | 13 | 依存の向きが設計どおりか（循環依存が無いか） | 下位が上位を参照する |
| 構造 | 14 | 既存の共通処理・ユーティリティの**再利用漏れ**が無いか | 同じ変換処理が3箇所に複製されている |
| 構造 | 15 | 重複コードが無いか。ある場合、意図的な重複か | コピーの片方だけ修正されている |
| 構造 | 16 | 関数・クラスの責務が単一か、引数が多すぎないか | 1メソッドで取得・判定・保存・通知を行う |
| セキュリティ | 17 | 入力**バリデーションの位置と網羅**（境界で検証しているか） | 内部呼び出しだけ検証を飛ばす |
| セキュリティ | 18 | 認証・**認可チェックの漏れ**（保護対象の全経路にあるか） | 一覧は保護され詳細は素通り |
| セキュリティ | 19 | インジェクション対策（SQL・コマンド・パス・テンプレート）が効いているか | 文字列連結でクエリを組む |
| セキュリティ | 20 | **機微情報**がログ・エラー応答・URLへ出ていないか | パスワード・トークンをそのまま記録 |
| セキュリティ | 21 | 秘密情報が**設定から注入**されているか（ハードコードでないか） | 鍵がソースに埋め込まれている |
| 並行性 | 22 | 共有可変状態への同時アクセスが保護されているか | 使い回しのインスタンスに可変フィールド |
| 並行性 | 23 | ロックの取得順序が一定か（デッドロックしないか） | 経路によって取得順が逆転する |
| 性能 | 24 | ループ内での問い合わせ（N+1）・全件取得が無いか | 1件ずつ取得して結合する |
| 性能 | 25 | 計算量が入力規模に対して妥当か。不要な再計算が無いか | 毎回ソートし直す |
| 可読性 | 26 | **マジックナンバー・ハードコード**が無いか（設計上の定数を直書きしていないか） | 数値が式の中に裸で現れる |
| 可読性 | 27 | 命名が役割を表しているか（型名・単位を含む値の命名） | `data` `tmp` `flag` |
| 可読性 | 28 | コメントが「何を」ではなく**「なぜ」**を説明しているか | コードの逐語訳コメント |
| 保守 | 29 | デッドコード・未使用の定義・到達不能分岐が残っていないか | 呼び出し元の無い公開メソッド |
| 保守 | 30 | TODO・仮実装に**解消条件と担当工程**が書かれているか | 理由なしの TODO |
| 保守 | 31 | 公開インタフェースの**後方互換**を壊していないか | 既存呼び出し元を確認せず引数を変更 |

## 2. 見落とされやすいもの

| # | 内容 |
|---|------|
| 1 | **設計書との数値の食い違い**。実装が正しく見えても、係数・上限が設計と1つずれている |
| 2 | **例外経路のテスト不在**。正常系だけ動作確認され、失敗時の状態が誰も見ていない |
| 3 | **暗黙のグローバル状態**。時刻・乱数・環境変数を直接読み、注入されていない |
| 4 | **修正の巻き添え**。1箇所の修正が、同じ処理を共有する別機能の挙動を変える |
| 5 | **アーキテクチャ不変条件の侵食**。プロジェクトが宣言した前提（権威の所在・層分離・データ駆動）を破る近道 |
| 6 | **ログの過不足**。失敗時に原因を特定できる情報が無い / 逆に大量出力で埋もれる |

## 3. 機械的に検証できる項目

| 対象 | 検証内容 |
|------|---------|
| 規約 | 静的解析・規約チェッカーの出力をそのまま取り込む（同じ項目を目視で重ねて探さない） |
| ビルド・型 | コンパイル・型チェックの結果を根拠に使う（目視で型整合を判断しない） |
| テスト | テスト実行結果（成功・失敗・スキップ件数）を取り込む |
| 未使用 | 未参照の定義・到達不能コードを解析器で列挙する |
| 依存の向き | パッケージ間参照を抽出し、循環・逆流を検出する |
| 定数の重複 | 設計書の数値と実装の定数を抽出して突き合わせる |
