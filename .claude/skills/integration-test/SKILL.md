# 結合テスト（工程7）

**目的**: **基本設計**（API設計・画面遷移・データ構造）どおりにコンポーネントが連結して動くことを、通しのシナリオで検証する。Phase完了ゲートの判定材料になる。

## 0. 最初に読む

| 順 | ファイル | 内容 |
|----|---------|------|
| 1 | `.claude/project/profile.md` | 技術スタック・ディレクトリ・不変条件・コスト規律 |
| 2 | `.claude/project/integration-test.md` | レイヤー構成・配置・シナリオ導出元・必須シナリオ・固有の観点 |

**プロファイルに書かれた読み込み範囲を守る**（該当セクションのみ読む）。

## 1. スコープの特定

対象（Phase・機能）を特定し、プロファイルの必須シナリオ表から**今回検証するシナリオ**を選ぶ。
テスト基盤が未整備の場合は、先に導入の可否をユーザーへ確認する（導入手順はプロファイルへ追記する）。

## 2. シナリオを設計する

シナリオはプロファイルの「導出元」から作る。**単体テストの分岐一覧から作らない。**

| 観点 | 内容 |
|------|------|
| 起点と終点 | どの状態から始め、どの状態になれば成功か |
| 経路 | 通過するエンドポイント・画面と、その順序 |
| 状態の引き継ぎ | 前段の結果が後段の入力として正しく渡るか |
| 永続化 | 処理後にデータが保存され、再取得しても保たれるか |
| 異常系 | 途中で失敗したときに、どこまで巻き戻り、何が表示されるか |

**分岐の網羅を狙わない。** 結合テストが見るのは「連結が成立するか」であり、条件分岐の網羅は単体テストの担当。
1シナリオが長くなりすぎる場合は、意味のある単位で切って独立に実行できるようにする。

## 3. テストを書く

| # | ルール |
|---|-------|
| 1 | 1シナリオ1テスト。テスト名に**シナリオの意味**を書く |
| 2 | 各ステップの後で**中間状態を検証**する。最後の結果だけ見ない |
| 3 | テスト間で状態を共有しない。毎回クリーンな状態から始める |
| 4 | 待ち時間は固定秒数のスリープでなく、**条件待ち**にする（不安定化の主因） |
| 5 | 外部要因（乱数・時刻）は、シナリオの成否に影響する範囲だけ固定する |
| 6 | セレクタ・エンドポイントは実装の詳細に密着させすぎない |

配置と記述規約はプロファイルに従う。

## 4. 実行と原因の切り分け

失敗したとき、**どの工程の問題か**を切り分けてから直す。

| 症状 | 疑う場所 | 対応 |
|------|---------|------|
| 単体テストは通るが連結で失敗 | 基本設計（API・データ構造の不一致） | 設計側の齟齬を特定し `basic-design` へ差し戻す |
| 期待した画面へ到達しない | 画面遷移設計 | 遷移図と実装を突き合わせる |
| 値は返るが内容が仕様と違う | 詳細設計・実装 | 単体テストの不足を疑い、分岐一覧へ戻す |
| 実行のたびに結果が変わる | テスト側 | 待ち方・共有状態・外部要因の固定を見直す |

**テストを通すために期待値を緩めない。**

## 5. 工程内検証（必ず行う）

### 5.1 機械的に検証する（目視しない）

| 対象 | 検証内容 |
|------|---------|
| シナリオの網羅 | プロファイルの必須シナリオ表の全行にテストがあるか |
| 実行結果 | 対象レイヤーが全PASSか |
| 安定性 | 同じテストを複数回実行して結果が変わらないか |
| 経路の網羅 | 設計上のエンドポイント・画面のうち、どれもシナリオに現れないものが無いか |

### 5.2 読んで確認する（今回の範囲のみ）

| # | 観点 | 判定 |
|---|------|------|
| 1 | 上流整合 | 検証しているのが**基本設計**の内容か（分岐の網羅にすり替わっていないか） |
| 2 | 中間検証 | 各ステップで状態を確認しているか。最終結果だけで判定していないか |
| 3 | 異常系 | 失敗経路のシナリオがあるか |
| 4 | 独立性 | 実行順に依存していないか |
| 5 | 不変条件 | `profile.md` §5 の不変条件が実際に守られているか |
| 6 | 永続 | 再取得・再ログイン後も状態が保たれるか |

**プロファイルの「固有の観点」表も必ず適用する。**

### 5.3 仕様との乖離が見つかったら

| 状況 | 対応 |
|------|------|
| 実装が仕様と違う | 乖離として記録し、「仕様書を実装に合わせる」か「実装を修正する」かを判断する |
| 仕様書どうしが食い違う | `doc-review` スキルへ回す。ここで勝手に決めない |
| 設計自体が成立しない | `basic-design` スキルへ差し戻す |

判断できないものは**勝手に決めない**。ユーザーに提示して判断を仰ぐ。

## 6. 完了報告

| 項目 | 内容 |
|------|------|
| 実行したシナリオ | シナリオ名とレイヤー、PASS / FAIL |
| 追加したテスト | ファイルと件数 |
| 工程内検証 | §5 の結果 |
| 検出した乖離 | 仕様と実装の差異と、その扱い（記録先） |

## 7. 完了基準

プロファイルの完了基準に加え、以下を満たすこと。

- 対象範囲の必須シナリオが全PASS
- 検出した乖離がすべて記録され、対応方針が決まっている
- 繰り返し実行しても結果が安定している

## 8. 次工程

Phase完了ゲート（`full-review` スキル）へ引き継ぐ。
**ゲートスキルは自動起動しない。**完了報告で次に実行すべきスキル名を提示して終了する。

## 注意事項

- 単体テストで見るべき分岐をここで網羅しようとしない（実行時間が破綻する）
- 不安定なテストを `skip` で黙らせない。原因を特定して直す
- 実装を直したくなったら、まず**どの工程の成果物が誤っているか**を確定させてから戻る
