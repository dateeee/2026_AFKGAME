# 製造（工程5）

**目的**: テストリスト工程で用意した**失敗するテストを1件ずつ Green にする**実装を書く。仕様に無い機能を足さず、テストが要求する以上を作り込まない。

## 0. 最初に読む

| 順 | ファイル | 内容 |
|----|---------|------|
| 1 | `.claude/project/profile.md` | 技術スタック・ディレクトリ・不変条件・コスト規律 |
| 2 | `.claude/project/dev.md` | 成果物と実装順・参照先・TDD適用範囲・固有の観点・動作確認 |

**プロファイルに書かれた読み込み範囲を守る**（該当セクションのみ読む）。

## 1. スコープの特定

実装対象を特定する。示されていない場合は、プロファイルの参照先から対象候補を提示して選んでもらう。

## 2. 入力の確認

| 確認項目 | 無かった場合 |
|---------|------------|
| 失敗するテスト（テストリスト） | `test-list` スキルでの作成を提案し、**製造に入らない** |
| 分岐一覧 | `detail-design` スキルへ差し戻す |
| 未確定仕様 | 対象に未確定が含まれるならユーザーへ通知し、確定を先にするか確認する |

仕様はプロファイルの「参照先」表の順に、**該当セクションのみ**読む。

## 3. 既存コードの確認

命名規則・ディレクトリ構造・import規約・再利用できる既存部品を把握し、**既存パターンに揃える**。新しい流儀を持ち込まない。

## 4. 実装計画の提示

実装前に計画を提示し、ユーザーの確認を得る。

```
## 実装計画: <機能名>

### 対象範囲
- （Phase / 機能 / 対象テスト）

### 仕様の要約
- （仕様書から読み取った要件）

### 変更するファイル
| ファイル | 操作 | 内容 |

### 満たすテスト
- （Green にする対象テストの列挙。これ以外は作らない）

### 注意点
- （制約・依存関係・既存コードとの兼ね合い）
```

## 5. 実装の実行

プロファイルの実装順に従う。TDD の適用範囲もプロファイルの表で判定する。

| 手順 | 内容 |
|------|------|
| Red | 対象テスト1件が**失敗している**ことを確認する |
| Green | **最小の実装**で通す。先回りして未テストの機能を作らない |
| Refactor | テストを保ったまま整理する。この段階で振る舞いを変えない |

これを**1テストずつ**回す。まとめて実装してから一括で通さない。

| # | 禁止 |
|---|------|
| 1 | テストを通すために**期待値のほうを書き換える** |
| 2 | 分岐一覧に無い分岐を、詳細設計を更新せずに実装する |
| 3 | テストが無い機能を先に作り込む |
| 4 | 数値を実装へ直接埋め込む（データとして持つ） |

TDD非適用の範囲は、実装後に型チェック・結合テストで検証する（プロファイルの適用範囲表を参照）。

## 6. 工程内検証（必ず行う）

### 6.1 機械的に検証する（目視しない）

コマンドはプロファイルの「動作確認」表。

| 対象 | 検証内容 |
|------|---------|
| テスト | 全件 PASS（Green）か |
| 型 | 型チェックが通るか |
| 構文・起動 | エントリポイントが読み込めるか |
| 差分の範囲 | 計画外のファイルを触っていないか（`git status` / `git diff --name-only`） |
| 数値の埋め込み | 実装に書いた数値が、データ側に対応を持つか |

### 6.2 読んで確認する（今回の差分のみ）

| # | 観点 | 判定 |
|---|------|------|
| 1 | 仕様との一致 | 実装した振る舞いが仕様の記述どおりか |
| 2 | 過剰実装 | テスト・仕様が求めていない機能を作っていないか |
| 3 | 最小性 | Green のために書いた分岐が、いずれかのテストで到達されるか |
| 4 | 層の責務 | ロジックが所定の層に集約され、上位層へ漏れていないか |
| 5 | 既存パターン | 命名・配置・import が既存と揃っているか |
| 6 | 不変条件 | `profile.md` §5 に抵触していないか |
| 7 | エラー処理 | 例外・エラー応答の形式が既存と統一されているか |

**プロファイルの「固有の観点」表も必ず適用する。**

### 6.3 テストが通らないとき

| 状況 | 対応 |
|------|------|
| 実装が誤り | 実装を直す |
| テストの期待値が誤り | **テストを直す前に詳細設計へ戻る**。分岐一覧を正してからテストを直す |
| 分岐一覧に無い分岐が必要 | 詳細設計へ追記 → テスト追加 → 実装 の順で進める |
| 仕様が曖昧で判断できない | **勝手に決めない**。ユーザーへ提示して判断を仰ぐ |

## 7. 完了報告

| 項目 | 内容 |
|------|------|
| 変更したファイル | 層ごとの表（新規 / 修正） |
| テスト結果 | 全件 PASS の実行結果 |
| 工程内検証 | §6 の結果 |
| 上流へ戻した項目 | 詳細設計へ追記した分岐・修正したテスト |
| 未実装 | 意図的に作らなかったもの（別Phase・別機能） |

## 8. 完了基準

プロファイルの完了基準に加え、以下を満たすこと。

- テストリスト工程の全テストが PASS（Green）
- §6 の機械的検証がすべて通る
- 仕様に無い機能を実装していない

## 9. 次工程

1. 製造完了ゲート: プロファイルの次工程表が指すコードレビュー系スキル
2. `unit-test` スキルへ引き継ぐ（C1網羅の測定と補完）

**ゲートスキルは自動起動しない。**完了報告で次に実行すべきスキル名を提示して終了する。

## 注意事項

- 仕様書に記載されていない機能を追加しない
- 対象範囲より後のPhaseの機能は実装しない（将来拡張を考慮した設計は可）
- リファクタは Green を保ったまま行う。振る舞いの変更と混ぜない
