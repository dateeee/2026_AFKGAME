# レビュー指摘の反映（fix-specs）

仕様書レビューの指摘に従って**仕様書を修正する**。新たなレビューは行わない。

## 0. 最初に読む

| 順 | ファイル | 内容 |
|----|---------|------|
| 1 | `.claude/project/profile.md` | ディレクトリ・不変条件（§5）・ドキュメント規約（§7）・コスト規律 |
| 2 | `.claude/project/review-docs.md` §6 | 対象レポート・修正ルール・変更履歴の追記先・サブエージェント制限 |
| 3 | `.claude/references/review-format.md` | レポートの見出し構造・ISSUE表の項目定義（解析の契約） |

## 1. 対象レポートの特定

引数にパスがあればそれを使う。無ければプロファイル §6 が指す保存先から、**ファイル名タイムスタンプが最新**のレポートを選ぶ。
引数で ISSUE 番号・カテゴリ・重要度が指定された場合は、**その範囲の指摘のみ**を修正対象とする。

| 状況 | 対応 |
|------|------|
| 引数のパスが実在しない | エラーとして報告し、保存先直下の候補一覧を提示して終了する |
| レポートが1件も無い | 修正対象なし。先行レビュー（`doc-review` スキル）の実行を提案して終了する |
| 最新レポートが「指摘なし」 | 修正不要と報告して終了する |

## 2. 指摘の解析

レポートの「指摘一覧」から各 `ISSUE-NNN` を読む。項目の定義は review-format.md の ISSUE表を正とする（カテゴリ・重要度・関連ファイル・該当箇所・検出可能工程・問題・修正案）。

## 3. 修正の実行

プロファイル §6 の修正ルールに従う。加えて共通ルール:

| # | ルール |
|---|-------|
| 1 | **重要度「高」から**着手する |
| 2 | 修正前に該当箇所を必ず読み、**レビュー時点から内容が変わっていないか**確認する |
| 3 | 関連する全ファイルを**まとめて**修正し、整合を保つ |
| 4 | 既存の文体・フォーマットに合わせる。表記法・リンク記法を壊さない |
| 5 | 修正対象は**該当セクションのみ**読む（全文読み込み禁止） |
| 6 | **同じファイルの組に2件以上の指摘がある場合**、指摘行のピンポイント修正で終えない。該当トピックについて両ファイルを突き合わせ、**どちらが正か（記述の境界）を確定**してから直す（小出しの矛盾が次のレビューで再発するのを防ぐ） |

## 4. スキップの判断

以下は修正せず、理由を報告する。

| 状況 | 理由 |
|------|------|
| 修正案が不明確 | どう直すべきか判断できない |
| 設計方針に反する | profile.md §5 の不変条件に抵触する |
| 既に解消済み | レビュー時点から仕様が更新されている |
| 大きな構造変更が必要 | 自動修正の範囲を超える |

**元の意図を損なう恐れがある場合はスキップする**（勝手に解釈して書き換えない）。

## 5. 修正後の検証

| 対象 | 検証内容 |
|------|---------|
| 規約 | ドキュメント規約チェックが exit 0 か（profile.md §4 のコマンド） |
| リンク | 追加・変更した相対リンクの参照先が実在するか（常設スクリプトがあれば実行する） |
| 新たな矛盾 | 修正によって他ファイルとの食い違いが生じていないか |

「新たな矛盾」の確認を**修正した本人の再読だけで済ませない**（自己検証は盲点をそのまま通す）。
修正ファイルを列挙した**別コンテキストのサブエージェント**に検証させる（上限・モデルはプロファイルに従う）。

## 6. 報告

```markdown
## 修正報告

### 修正済み
| ISSUE | タイトル | 修正内容の要約 | 修正ファイル |

### スキップ（修正不要 / 不可）
| ISSUE | タイトル | スキップ理由 |
```

変更履歴は**各仕様書に書かない**。profile.md §7 が指す集約ファイルの先頭へ追記する。

## 注意事項

- サブエージェントは「多数ファイルにまたがる機械的修正」と「修正後の検証」（§5）のみ（プロファイル §6 の上限・モデル指定を厳守）
- 修正後に再レビューを自動起動しない。必要ならスキル名を提示して終了する
