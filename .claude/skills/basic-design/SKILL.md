# 基本設計（工程2）

**目的**: 要件を、詳細設計が数値とアルゴリズムを埋められる骨格まで落とす。計算式の中身は決めない（それは詳細設計）。

## 0. 最初に読む

| 順 | ファイル | 内容 |
|----|---------|------|
| 1 | `.claude/project/profile.md` | 技術スタック・ディレクトリ・不変条件・コスト規律 |
| 2 | `.claude/project/basic-design.md` | 成果物・設計図の一覧・参照順・固有の観点・機械検証の方法 |

**プロファイルに書かれた読み込み範囲を守る**（索引構成の成果物は、索引で担当ファイルを特定してから必要な子だけ読む）。

## 1. スコープの特定

設計対象（機能・サブシステム・Phase）を特定し、影響する成果物をプロファイルの成果物表から洗い出す。

## 2. 入力の確認

要件定義の成果物から、設計対象の要件を**該当セクションのみ**読む。

| 確認項目 | 内容 |
|---------|------|
| 機能要件 | 何ができる必要があるか |
| 非機能要件 | 性能・容量・セキュリティ・可用性の**要求値** |
| 運用要件 | 監視・バックアップ・変更管理 |
| 未確定仕様 | 設計に影響する未確定項目が残っていないか |

未確定仕様が設計をブロックする場合は、`requirements` スキルでの確定を先に提案する。

## 3. 設計する

以下を確定する。既存の設計・実装があれば、そのパターンを踏襲する。

| 領域 | 決めること |
|------|----------|
| アーキテクチャ | 層構成、依存方向、責務の境界 |
| データ | エンティティ、属性、型、リレーション、永続化方式 |
| API | エンドポイント一覧、メソッド、リクエスト/レスポンス構造、共通仕様（エラー形式・認証） |
| 画面 | 画面一覧、遷移条件、各画面の構成要素 |
| 横断 | ログ、認証、エラーハンドリングの方針 |
| 非機能の実現方式 | 要求値ごとに「どう実現するか」を1つずつ対応づける |

**非機能・運用要件は、要求値と実現方式を1対1で対応づける。**対応先のない要求値を残さない。

## 4. 設計図を更新する

プロファイルの設計図一覧に従い、変更が及ぶ図を更新する。

- 図とテキスト仕様の**両方**を更新する（片方だけ直さない）
- 索引 + 子ファイル構成の図は、索引のリンク表を維持する
- 図が上限を超えたら、既存の構成と同じ形で図単位に切り出す

**新しい仕様ファイルを追加した場合**は、追加と同時に次の3点を行う（後続レビューの指摘源になりやすい）。

1. 索引（README 等、プロファイルが指す索引）へ登録する
2. 既存ファイルと記述が重なるトピックは、**どちらが正か**を両ファイルに明記する
3. 正の宣言をプロジェクトの正の所在マップ（プロファイル参照）へ登録する

## 5. 整合性チェック（工程内で必ず行う）

基本設計は**テキスト仕様・設計図・上流の要件**の3者が食い違いやすい。この工程の中で突き合わせ、`diagrams-review` へ丸投げしない。

### 5.1 機械的に検証する（目視しない）

スクラッチパッドに使い捨てスクリプトを書き、出力だけを取り込む。検証項目はプロファイルの「機械検証」表に従う。

| 対象 | 検証内容 |
|------|---------|
| 図の構文 | コードフェンスの閉じ、ブロック開始と終了キーワードの対応 |
| 図の参照整合 | エンティティ定義から属性を抽出し、リレーション両端の実在を確認する |
| リンク | 索引から子ファイルへのリンク、および今回変更した相対リンクが実在するか |
| 命名の突き合わせ | エンドポイント名・テーブル名・画面名を図とテキストの双方から抽出して差分を取る |
| 規約 | 文字数上限チェックが通るか |

### 5.2 読んで確認する（今回の変更範囲のみ）

| # | 観点 | 判定 |
|---|------|------|
| 1 | 上流整合 | 設計が要件定義の機能要件を満たしているか。要件にない機能を勝手に足していないか |
| 2 | 図↔テキスト | 設計図の内容が対応するテキスト仕様と一致するか（**両方を更新したか**） |
| 3 | 図↔図 | 設計図どうしで矛盾がないか（データ構造と画面遷移、画面遷移と呼び出しフロー等） |
| 4 | 網羅 | 追加したエンドポイント・エンティティ・画面が、関係するすべての成果物に反映されているか |
| 5 | 非機能の対応 | 非機能・運用要件の**すべて**に実現方式が対応づいているか。対応先のない要求値がないか |
| 6 | 不変条件 | プロファイルの不変条件に抵触していないか |
| 7 | 実装との乖離 | 既存の実装があるのに設計だけ変えていないか。変えた場合、乖離を記録したか |

**プロファイルの「固有の観点」表も必ず適用する。**

### 5.3 矛盾が見つかったら

| 状況 | 対応 |
|------|------|
| 図とテキストの片方だけ古い | 新しい側に揃える。どちらが新しいか不明なら要件定義まで遡って判断する |
| 要件を満たせない設計になっている | §3 に戻って設計し直す。要件側の変更が必要なら `requirements` スキルを提案する |
| 図どうしが矛盾する | 正となる図を決めて他を揃える。決められない場合はユーザーに提示する |

## 6. 完了報告

| 項目 | 内容 |
|------|------|
| 更新した成果物 | ファイルと該当セクション |
| 更新した設計図 | 図の名前と変更点 |
| 非機能の対応表 | 要求値 → 実現方式の対応（新規・変更分） |
| 整合性チェック | §5 の結果。検出した矛盾と、その解消内容 |
| 未対応 | 設計しきれなかった項目と理由 |

## 7. 完了基準

プロファイルの完了基準に加え、以下を満たすこと。

- **§5 の整合性チェックで検出した矛盾がすべて解消されている**（判断保留はユーザー確認済み）
- 非機能・運用要件のすべてに実現方式が対応づいている
- 図の構文検証が通り、索引のリンクが揃っている
- ドキュメント規約チェックが通る

## 8. 次工程

1. 設計整合・仕様確定ゲート: `diagrams-review` スキルと `doc-review` スキルを続けて実行し、**両レポートの指摘を1回の修正パスに統合**して反映する（レビューごとに修正を分けると「修正→再レビュー」のループが倍になる）
2. `detail-design` スキルへ引き継ぐ

**ゲートスキルは自動起動しない。**完了報告で次に実行すべきスキル名を提示して終了する。

## 注意事項

- **計算式の中身・具体的な数値を決めない**。詳細設計の担当
- プロファイルの不変条件（アーキテクチャ上の前提）を破る設計をしない
- 既存の実装があるのに設計だけ変える場合、乖離が生まれることを報告に明記する
- 図とテキストで同じ情報を二重管理しない。正となる側を決めて他は参照にする
