# 工程プロファイル テンプレート

`.claude/skills/**` は**プロジェクト非依存の一般手順**、`.claude/project/**` は**そのプロジェクト固有の値**を持つ。
新しいプロジェクトへ持ち出すときは `.claude/skills/` と `.claude/references/` をそのままコピーし、**本テンプレートに沿って `.claude/project/` だけを書き直す**。

## 使い方

1. `.claude/skills/` `.claude/references/` `.claude/scripts/` をコピーする（無改造）
2. `.claude/project/profile.md` を新プロジェクトの値で書く（全スキルが最初に読む）
3. 工程ごとに `.claude/project/<スキル名>.md` を下記スキーマで書く
4. `.claude/project/INDEX.md` の対応表を更新する

**スキル名とプロファイル名は1対1で揃える**（`skills/unit-test/` ↔ `project/unit-test.md`）。スキルは固有値を持たず、常に対応するプロファイルを読んでから作業する。
例外はレビュー系で、**共通1件 + 領域別の分冊**（`project/review.md` + `project/review/<領域>.md`）とし、各スキルは「共通 + 自分の分冊」だけを読む（下記スキーマ）。

## 記述の原則

| 原則 | 内容 |
|------|------|
| 値のみ書く | 「なぜそうするか」は一般スキル側。プロファイルは**パス・数値・名称・観点**だけを持つ |
| 表を優先 | 散文で書かない。列挙は必ず表にする |
| 重複禁止 | 同じ値を複数プロファイルに書かない。`profile.md` に置いて参照する |
| 実在確認 | パス・コマンドは実在するものだけ書く。将来の予定は「未整備」と明記する |
| 上限5,000字 | `.claude/**` は区分D。超えたら観点を絞るか子ファイルへ分割する |

## スキーマ: `profile.md`（プロジェクト共通・全スキルが読む）

```markdown
# <プロジェクト名> — プロジェクトプロファイル

## 1. 基本情報
| 項目 | 値 |          ← 種別 / 構成 / 対象プラットフォーム / 開発段階

## 2. ディレクトリ
| パス | 内容 |        ← バックエンド・フロントエンド・仕様書・テストの実配置

## 3. 技術スタック
| 層 | 技術 | 規約 |    ← バージョンと「守るべき書き方」を1行で

## 4. 常用コマンド
| 目的 | コマンド |      ← 型チェック / テスト / 起動 / 規約チェック

## 5. アーキテクチャ不変条件
- 破ってはいけない設計上の前提（サーバー権威・シングルプレイ等）

## 6. 工程 ↔ スキル ↔ プロファイル 対応表
| 工程 | スキル | プロファイル |
```

## スキーマ: `<スキル名>.md`（工程ごと）

```markdown
# <工程名> — プロジェクト固有プロファイル

> 一般手順は [.claude/skills/<スキル名>/SKILL.md](...) を参照。本書は固有の値のみを持つ。

## 1. 成果物
| 成果物 | パス | 役割 |
                            ← この工程で作る/更新するファイル。索引構成なら索引と子を分けて書く

## 2. 参照先（読む順）
| 順 | 参照先 | 読む範囲 |
                            ← 「該当セクションのみ」等、読む範囲を必ず書く（全文読込を防ぐ）

## 3. 固有の観点
| # | 観点 | 判定基準 |
                            ← 一般手順では出てこない、このプロジェクトでだけ必要なチェック

## 4. 完了基準
- 一般スキルの完了基準に**上乗せ**する固有条件のみ書く

## 5. 次工程
| 次にやること | 手段 |
                            ← 呼ぶスキル名を明記する
```

## スキーマ: レビュー系プロファイル（共通 + 分冊）

レビュースキルは共通手順（[.claude/references/review-procedure.md](../references/review-procedure.md)）を使うため、プロファイルは以下を追加で持つ。**1スキル1分冊**とし、スキル間で同じ値を書かない。

```markdown
# review.md（共通・全レビュースキルが読む）
## 1. 共通パラメータ  | 項目 | 値 |
       ← 保存先の命名 / ローテーション / 準備スクリプト / 該当箇所の示し方 / 担当範囲。
         references 側はこれらを持たず本節を参照する
## 2. 重要度の共通軸  | 重要度 | 基準 |    ← 分冊はこれを具体化する（齟齬は分冊が勝つ）
## 3. 分冊            | スキル | 分冊 | 持つ節 |

# review/<領域>.md（スキルごと）
## 0. レビューパラメータ  | 項目 | 値 | + 準備コマンド
       ← 保存先ディレクトリ / タイトル / カテゴリのみ（共通側の再掲禁止）
## 1. 対象ファイル / 差分モードの照合先  ← 全量モードの分担もここへ
## 2. 観点                | 分類 | # | 観点 |
## 3. 重要度の基準        | 重要度 | 基準 |
```

## スキーマ: SKILL.md frontmatter（新スキル追加時のみ）

既存スキルは無改造でコピーする。新スキルを足すときは以下の規約に従う。

| フィールド | 必須 | 規約 |
|-----------|------|------|
| `name` | ○ | スキルのディレクトリ名と一致させる |
| `description` | ○ | 「何をするか」＋トリガー句の例＋「固有値はプロファイルから読み込む」を書く（自動起動の判定に使われる） |
| `argument-hint` | ○ | `/` 起動時の補完に出す引数ヒント（例: `"[full \| 追加観点]"`）。YAMLの誤解釈を避けるため引用符で囲む |
| `model` | 任意 | 機械的作業が主のスキルのみ `sonnet`（例: `fix-specs`） |

- 本文に固有の値を書かない。「0. 最初に読む」で対応プロファイルを指す
- **スキル→プロファイルの参照は「ファイル名 + 見出し名」で書く**（例: `requirements.md` §4 未確定仕様の確定）。§番号だけの参照・見出し名を伴わない表参照は、改番や表名変更で握手が切れるため禁止
- スキル専用の資料は `skills/<スキル名>/references/` に置く（複数スキル共有のみ `.claude/references/`）
- 「注意事項」は Gotchas として運用し、実運用で観測した失敗パターンを随時追記して育てる
- `description` には**特定の言語・フレームワーク名を書かない**（トリガー判定は意味マッチで機能する）。スタック名は本 `project/` 側に置く

**一般層に残す固有前提の範囲**: テスト系スキル（`test-list` `unit-test`）の一般例は **JUnit 5 / JaCoCo 前提**で書かれている（`@Tag`・`@ParameterizedTest`・分岐カバレッジの読み方など）。他のスタックへ持ち出す場合は、スキル本体ではなく `skills/<スキル名>/references/` の資料を差し替える。

## 規約: スクリプトの配置

判定・採番・雛形生成・一括置換など**決定的に決まる手順は LLM の手作業にせず**スクリプトへ寄せる。

| 置き場所 | 用途 | 回帰テスト |
|---------|------|----------|
| `.claude/scripts/` | 複数スキルが共有するもの（例: `review_prep.py` — レビュー系5スキルのモード判定・差分特定・採番・雛形生成） | `.claude/scripts/tests/` |
| `.claude/skills/<スキル名>/scripts/` | そのスキル専用のもの | 同ディレクトリの `tests/` |
| `.claude/hooks/` | フック本体（stdin の JSON を受けて判定するもの） | `.claude/hooks/tests/` |
| `<リポジトリ>/scripts/` | プロジェクト固有の検証（`.claude/` の外。パス・対象を内蔵してよい） | `<リポジトリ>/scripts/tests/` |

- 判定ロジックを持つスクリプトには `<配置先>/tests/` へ pytest を置き、`python -m pytest <配置先>/tests -q` で回す。プロダクト側のテスト設定（カバレッジ閾値等）と混ざらないよう**別ルートで回す**
- テストは**緑パス + 変異テスト**（検出対象を1項目ずつ壊して検出されることを確認）をセットにする。緑パスだけでは「何も検出しない実装」が通ってしまう
- `tests/conftest.py` で `sys.path` へ親ディレクトリを足し、通常の import 経路で読む（`importlib` の直読みは `sys.modules` 未登録で dataclass の型解決が落ちる）
- `.claude/` 配下のスクリプトは**プロジェクト非依存**にする。保存先・対象パス・タイトル等の固有値は**すべて引数で受け取り**、呼び出し側（スキル + プロファイル）が渡す
- 出力は `KEY  値` 形式など**そのまま取り込める形**にする。LLM に再計算させない
- 許可プロンプトを省くには `.claude/settings.json` の `permissions.allow` へ `Bash(python .claude/scripts/*)` を追加する（SKILL.md の `allowed-tools` は「そのスキルが使えるツールの制限」であり、書くと列挙外のツールが使えなくなる。許可の追加用途には使わない）

## チェックリスト（新プロジェクト立ち上げ時）

- [ ] `profile.md` の全項目が実在する値で埋まっている
- [ ] 工程プロファイルがスキル数と一致している（各工程に最低1つ）
- [ ] 対応表（`INDEX.md`）にプロファイル未作成のスキルがない
- [ ] 一般スキル側にプロジェクト固有の名称・パスが残っていない
- [ ] 全ファイルが文字数上限内である
