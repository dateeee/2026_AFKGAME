## 2. 開始プロンプトの定型（5要素）

```
/<工程スキル> <Phase・対象>: <作業内容を1行>
完了条件: <コミット・Red確認・C1 100% など>
参照: <ファイル1〜2点>（起点。追加はここから索引経由で）
前提: <直前の状態1行・コミットID>
```

設計の経緯と敵対的検証は [logs/session_start_prompt_design_2026-08-06.md](../../logs/session_start_prompt_design_2026-08-06.md)。

### 2.1 「参照」「前提」「完了条件」の裏取り

引き継ぎに書く前提は、**書くターンで実在を確認する**。裏の取れていない前提は次セッションの着手を止める。

| # | 対象 | ルール |
|---|------|-------|
| 1 | 参照するセクション | **「〜の正」と書く参照は、そのセクションの実在を書くターンで確認する**（分岐一覧なら `python scripts/check_branch_list.py`、それ以外は Grep で見出しを引く）。無いものを指すと、次セッションが着手前に前工程へ差し戻す往復になる |
| 2 | 外部ツール・ランタイム・ミドルウェア（JDK・Maven・docker・DBサーバー等） | **書くターンで実際に実行し、コマンドと結果を根拠にする**。根拠なしに「確認済み」と書かない |
| 3 | 同上 | **新しいシェルで再現するかまで確認する**。導入直後は PATH がユーザー環境変数へ未反映で、次セッションの新規シェルからは見えないことがある。PATH 依存ならフルパスを書く |
| 4 | 同上 | 不在なら、代替手段まで含めて「前提」に明記する。**不在のまま完了条件へ書かない**（着手後に判明すると中断になる） |

## 3. 使いどころの制限

- `/clear` 後の**新セッション冒頭専用**。セッション途中の別タスク開始には使わない（[profile.md](profile.md) §6 規律6: 工程の区切りで /clear）
- 委譲先の工程スキル ↔ プロファイル対応は [INDEX.md](INDEX.md) の対応表を使う

## 4. 引き継ぎ更新時のチェック

引き継ぎは **worktree の統合後に main で1回だけ**書き換える（worktree の中では触らない ＝ `next_session.md` §0 ルール4）。

**書き換える前に** `python scripts/check_doc_size.py --sections docs/backlog/next_session.md` を実行する。
台帳（`KNOWN_OVERSIZED`）に本ファイルの行があれば、**その是正方針を先に実施してから**書く
（書いた後で超過に気づくと、移設・H2分割・節番号の繰り下げが後追いになる）。

あわせて main で `git status --short` を確認する。
未コミットの書きかけ（別タスクへ切り出した成果物・試行の残骸）が残る場合は、
そのパスと状態を §1 の「次回」へ明記するか、破棄してから終える。

**引き継ぎに書かれていない未コミットファイルは次セッションの着手を止める**
（`??` の正体をユーザーに確認するまで作業を開始できない）。

再帰削除（`__pycache__`・移行後の残骸ディレクトリ等）を「統合後」へ残す場合は、
**承認が要る前提でユーザーへ提示する**（権限分類器に拒否されるため、書き置くだけでは実施されない）。
