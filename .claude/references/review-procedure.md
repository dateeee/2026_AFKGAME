# レビュー共通手順（一般）

レビュー系スキル（`doc-review` `diagrams-review` `backend-review` `frontend-review` `full-review` `spot-review`）が共通で従う手順。
**プロジェクト固有の対象ファイル・観点・パラメータは、各スキルが指定するプロファイルに置く。**本書には固有の値を書かない。

## 1. コスト規律

| # | 規律 |
|---|------|
| 1 | **デフォルトは差分レビュー**。全量は引数に `full` がある場合、または過去レポートが1件もない場合のみ |
| 2 | **複数サブエージェントへの分担は全量モードのみ**。差分モードは分担せず、メインコンテキストまたは規律7の1体委譲で完結させる |
| 3 | サブエージェントには**担当ファイルのみを列挙**し、「列挙外は読まない」「戻り値は指摘のみ・原文引用は1〜3行」を明示する。モデルは `sonnet` を指定する |
| 4 | **機械的に検証できる項目はLLMで目視しない**。スクラッチパッドに使い捨てスクリプトを書いて検証し、その出力だけを取り込む |
| 5 | 照合先は**該当セクション・該当ファイルのみ**読む（全文読み込み禁止） |
| 6 | 索引 + 個別ファイル構成では、変更されたのが子ファイルなら**その子と照合先のセクションだけ**読む（索引の全文読み込みは不要） |
| 7 | レビューは機械的な照合が主体。モードを問わず、**レビュー全体を `sonnet` のサブエージェント1体へ委譲してよい**（担当ファイルを列挙し、戻り値は指摘のみと明示する） |

## 2. 準備（モード判定・差分特定・採番）

**手作業で判定しない。** 準備スクリプトを実行し、出力をそのまま取り込む。

```bash
python .claude/scripts/review_prep.py --dir <保存先> --paths <対象パス...> \
    [--full] [--title <タイトル>] [--categories "<カテゴリ>"] [--init]
```

- `--dir` `--title` `--categories` はプロファイル §0「レビューパラメータ」の値、`--paths` は自スキルの対象パス
- 引数に `full` があるときだけ `--full` を付ける。`--init` は雛形ファイルを先に作る場合のみ

| 出力キー | 使い方 |
|---------|-------|
| `MODE` | 差分 / 全量。全量は `--full` 指定時とレポートが1件も無いときのみ |
| `BASE` | 差分の基点コミット（前回レポートに記録された HEAD SHA）。括弧内に根拠が出る |
| `CHANGED` | 変更ファイル数と一覧。**0件ならレビューを実行しない**（§3-3） |
| `ISSUE_START` | 今回の先頭 ISSUE 番号。ここから連番で振る |
| `REPORT_PATH` | レポートの保存先（§8） |
| `MODE_LINE` | レポート冒頭へそのまま貼るモード行（§8） |

`BASE` が「タイムスタンプで代替」と出た場合、前回レポートが HEAD SHA 記録前の形式か基点コミットが失われている。差分範囲が前後しうるため、境界付近の指摘は慎重に扱う。

## 3. 差分モードの対象特定

`CHANGED` の一覧を起点に、以下を加えて対象を確定する。

1. 変更ファイルごとに、プロファイルの「差分モードの照合先」表を引いて照合先を加える
2. **前回レビューで指摘に挙がったファイルとその照合相手**は、今回変更が無くても対象に加え、指摘があったトピックは**ペア全体**を照合する（修正は指摘行の周辺に新たな矛盾を持ち込みやすい）
3. **変更ファイルが存在しない場合はレビューを実行しない**。「前回レビュー以降、変更なし」と報告して終了する（レポートファイルを作成しない）
4. **依頼のスコープが `CHANGED` より狭い場合、スコープ外と判断したファイルは差分の中身を調べずに除外する**。除外した範囲と理由をレポート冒頭に1段落で記す（対象外ファイルの差分ステータスを追っても結論は変わらない）

## 4. 全量モードの分担

プロファイルの「全量モードの分担」表に従ってサブエージェントへ割り当てる。各エージェントのプロンプトには以下を必ず含める。

- 担当ファイルの**完全な列挙**
- 「列挙されたファイル以外は読まないこと」
- 「戻り値は指摘のみ。原文引用は問題箇所の1〜3行に留めること」
- 適用する観点（プロファイルの該当行）

## 5. 機械的検証

**プロジェクトの常設検証スクリプト（プロファイルの常用コマンド表）を先に実行し、出力をそのまま取り込む。**
使い捨てスクリプトは常設で賄えない検証にのみ書く。同種の使い捨てを繰り返し書いているなら、常設スクリプトへの昇格を報告で提案する。

使い捨てスクリプトの実行は次の2点を守る（どちらも失敗が再発しやすい）。

| # | 手順 |
|---|------|
| 1 | シェルのヒアドキュメントへ直接流し込まず、**スクラッチパッドへファイルとして書いてから実行する**（ヒアドキュメントはエスケープが落ちて構文エラーになる） |
| 2 | 出力に非ASCII文字を含む場合は、**標準出力のエンコーディングを明示して実行する**（実行環境の既定が UTF-8 でないとエンコードエラーで落ちる） |

以下は目視せず、スクリプトで検証して出力だけを取り込む。

| 対象 | 検証内容 |
|------|---------|
| リンク | 相対リンクの参照先が実在するか |
| 文字数上限 | 規約チェックスクリプトの出力をそのまま取り込む |
| 構造化データ | 重み合計・ID重複・参照整合など数え上げで判定できるもの |
| 型・スキーマ | 両側の定義を抽出して差分を取る |
| 図の構文 | フェンスの閉じ、ブロック開始と `end` の対応 |

既存の型チェック・テストコマンドがある場合は、その実行結果を根拠に使う（目視で型整合を判断しない）。

## 6. 指摘の書き方

| # | ルール |
|---|-------|
| 1 | 「〜の可能性がある」ではなく「AではXと記載されているがBではYとなっている」と、該当箇所を引用して明示する |
| 2 | 該当箇所はセクション番号または行番号で示す |
| 3 | 修正案は、修正適用スキルがそのまま実行できる粒度で書く |
| 4 | 重要度（高/中/低）はプロファイルの基準表に従う |
| 5 | 自分の担当範囲外の問題は指摘せず、担当スキル名を添えて言及に留める |
| 6 | 問題がない場合は「指摘なし」と明記する |
| 7 | 修正案に「既存テスト・既存呼び出しへの影響なし」と書くときは、**その根拠（アノテーション・設定・呼び出し箇所の実在）を Grep で確かめてから書く**。未確認の影響評価は修正適用時に覆る |

## 7. 担当範囲の切り分け

自分の担当範囲外の問題は指摘として立てず、担当スキル名を添えた言及に留める。**同じ問題を複数のレビューで重複計上しない。**

| 問題の所在 | 担当スキル |
|----------|----------|
| 仕様書間の矛盾のみ | `doc-review` |
| 設計図が絡む乖離（図↔仕様、図↔コード、図↔図） | `diagrams-review` |
| バックエンドのコード品質のみ | `backend-review` |
| フロントエンドのコード品質のみ | `frontend-review` |
| 仕様↔コード、フロント↔バックにまたがる | `full-review` |

境界が曖昧な指摘は、**より広い範囲を担当するスキル**へ寄せる（コード品質より統合整合性を優先する）。
`spot-review` は担当範囲ではなく**起動タイミング**で分かれる（ゲート外で対象を指定して行う単発レビュー）。上表のいずれかが担当する対象を扱うため、直近の定型レビューと**重複計上しない**こと。
**設計図が絡む照合は、図↔仕様・図↔コード・図↔図のいずれも `diagrams-review` が担当する**（他スキルのプロファイルは図を照合先に持たない）。
Phase完了ゲート等で図の再確認が必要な場合は、統合レビューと併せて `diagrams-review` を併走させる。

## 8. 出力と報告

1. [review-format.md](review-format.md) の形式で、§2 の `REPORT_PATH` へ保存する（`--init` を付けていれば雛形が作成済み。指摘を埋める）
2. タイトル直下へ §2 の `MODE_LINE` を**そのまま**置く。ここに含まれる `HEAD: <SHA>` が次回レビューの差分基点になるため、手で書き換えない
3. プロファイル §0 の**ローテーションコマンド**を実行し、ディレクトリ直下を上限件数に保つ（超過分はアーカイブへ移動。削除はしない）
4. 保存したファイルパスと、モード・指摘件数（重要度別）をユーザーへ報告する
5. 各指摘の「検出可能工程」（review-format.md）を集計し、同じ工程内検証・スクリプトに指摘が偏っている場合は、その検証・プロファイルの改善案を報告に含める（プロセスへの還元）
6. 指摘の反映が必要な場合は、対応する修正適用スキル名を提示して終了する（**自動で起動しない**）
