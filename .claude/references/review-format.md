# レビュー結果 共通出力形式

レビュー系スキル（`doc-review` `backend-review` `frontend-review` `diagrams-review` `full-review`）共通の出力形式。
各スキルのプロファイルで定義される **保存先・レポートタイトル・カテゴリ一覧・重要度基準** を以下のテンプレートに当てはめる。
`fix-specs` スキルがこの形式を解析するため、見出し構造・ISSUE表の項目名を変更しないこと。

## 保存先

`docs/reviews/{スキル名}/YYYY-MM-DD_HHMMSS.md`（YYYY-MM-DD_HHMMSS は現在日時。ディレクトリがなければ作成する）

- **スキル名ごとにディレクトリを分け、ファイル名は日時のみ**とする。種別はディレクトリ名が示すため、ファイル名に繰り返さない
- 保存後に `python scripts/rotate_reviews.py --apply` を実行する。ディレクトリ直下は最新10件に保たれ、超過分は `archive/` へ移動する（**削除はしない**）
- 過去レポートは追記型アーカイブとして残す。**通常の作業では読み込まない**（読むのは差分モードの起点となる最新1件のみ）

## フォーマット

```markdown
# {レポートタイトル} — YYYY-MM-DD HH:MM:SS

## サマリー

| カテゴリ | 件数 |
|---------|------|
| {カテゴリ1} | N件 |
| {カテゴリ2} | N件 |
| 合計 | N件 |

---

## 指摘一覧

### ISSUE-NNN: [問題の短いタイトル]

| 項目 | 値 |
|------|-----|
| カテゴリ | {カテゴリ一覧のいずれか} |
| 重要度 | 高 / 中 / 低 |
| 関連ファイル | path/to/file1, path/to/file2 |
| 該当箇所 | file1 セクションX.X または 行N〜M |
| 検出可能工程 | {この問題を最も早く検出できた工程内検証・常設スクリプト。なければ「本レビュー」} |

**問題の説明:**
具体的にどのような問題があるか。原文・コード片を引用して示す。

**修正案:**
どのファイルのどの部分をどのように修正すべきか、具体的に記述する。
修正が必要なファイルごとに箇条書きで示す。

---

（以降、ISSUE番号を連番で続ける）
```

## 共通ルール

- **ISSUE番号は保存先ディレクトリ内で一意**にする。直下の全レポートで使われた最大番号を**次の100の位へ切り上げた番号**から採番する（例: 最大が ISSUE-507 → 今回は ISSUE-601 から。最新レポートが「指摘なし」でも過去レポートまで遡る。番号を持つレポートが無ければ 001 から）。レポートごとに 001 へリセットしない — 修正コミット・解消確認が番号で追跡されるため
- **検出可能工程**には、この問題を最も早く検出できた工程内検証（例: `詳細設計 §5.3`）または常設スクリプト（例: `scripts/check_docs.py --reach`）を書く。該当がなければ「本レビュー」。同じ工程・検証に指摘が偏る場合、その検証の改善が次の再発防止策になる（レビュー手順 §8）
- 指摘は具体的に記述すること。「〜の可能性がある」ではなく「AではXと記載されているがBではYとなっている」のように、該当箇所を引用して明示する
- 重要度（高/中/低）の判定基準は各コマンド側の定義に従う
- 問題がない場合は「指摘なし」と明記する
- レビュー完了後、保存したファイルパスをユーザーに報告する
