# フロントエンドコーディング規約 — 層の責務

> 親: [coding-standards-frontend.md](../coding-standards-frontend.md)。本書は同 **§2** を担当する。
> 記述は §3 [writing.md](writing.md)、状態と API は §4 [state-api.md](state-api.md)。正はプロジェクト側のコーディング規約ドキュメント。

## 2. 層の責務（越えたら指摘）

| 層 | 書いてよいこと | 書いてはいけないこと |
|----|--------------|-------------------|
| 画面（views） | 配置、画面固有ロジック、ストア・composable の利用 | 色・寸法の判断、API 直接呼び出し、生 `fetch` |
| UI プリミティブ | 見た目と操作の挙動（props / emits で完結） | 業務知識、ストア・API・ルーターへの依存 |
| アプリシェル | ヘッダ・ナビ・スクロール境界・全画面共通の帯 | 個別画面の業務ロジック |
| composable | リアクティブなロジック（タイマー・初期化・逐次制御） | 画面を跨いで残る状態の保持（ストアの仕事） |
| ストア | 画面を跨ぐ状態、API 呼び出し（action 内）、loading / error | ゲームルールの計算（サーバー権威）、他ストアの state 書き換え |
| API クライアント層 | 生 `fetch`、共通処理（認証・エラー変換・リトライ）、エンドポイント関数 | 表示ロジック |
| utils | フレームワーク非依存の純粋関数 | リアクティブ値の受け渡し、状態の保持 |

**呼び出し可否**。

| # | 規約 |
|---|------|
| 1 | 依存は 画面 → 部品 / ストア / composable → API 層 → 型 の一方向。逆流・循環を作らない |
| 2 | **サーバー通信はストアの action か composable を経由**。画面・部品から API 層を直接 import しない |
| 3 | 生 `fetch` を書けるのは API クライアント層のみ |
| 4 | `provide` / `inject` を使わない（状態はストア、親子は props / emits）。採用は正の側の改訂が先 |
| 5 | 他ストアの参照は action・関数の中で取得する（トップレベルで確立しない）。ストア ↔ composable の相互参照は関数単位の import で片方向に倒す |

**ルーティング**。ルート定義は1ファイルに集約し、画面は遅延ロード（`() => import(...)`）で登録する。認証などの横断判定は `beforeEach` ガード1箇所に置き、各画面で判定しない。遷移は `name` 指定（`path` 直書きしない）。
