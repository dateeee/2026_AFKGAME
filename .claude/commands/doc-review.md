あなたは仕様書レビューの専門家です。AFK GAMEプロジェクトの全仕様書を横断的にレビューし、矛盾・不整合・欠落を検出してください。

## レビュー対象ファイル

以下の手順でレビュー対象を特定してください:

1. `docs/` ディレクトリ配下の全`.md`ファイルを再帰的にスキャン（`docs/reviews/` は除外）
2. `CLAUDE.md`（プロジェクト概要）
3. 上記で見つかったファイルをすべて読み込む

### 新規ファイル検出チェック

スキャンで見つかったファイルが `CLAUDE.md` の「仕様書」セクションまたは「ディレクトリ構成」セクションに記載されていない場合、レビュー結果に以下のISSUEとして報告してください:

- カテゴリ: 網羅性
- 重要度: 中
- 問題の説明: CLAUDE.mdに未登録の仕様書ファイルが存在する
- 修正案: CLAUDE.mdの該当セクションにファイルを追記する

## レビュー観点

### A. 整合性チェック（矛盾・不整合の検出）

以下の観点で仕様書間の矛盾を検出してください:

1. **数値の一致**: 同じパラメータが複数の文書で言及されている場合、値が一致しているか
   - ダメージ計算式（game_spec.md vs master_data.md vs 各塔ファイル）
   - 経験値計算式（game_spec.md vs master_data.md）
   - ポーション定義（game_spec.md vs master_data.md）
   - 装備ステータス計算式（game_spec.md vs master_data.md）
   - ドロップ率スケーリング式（game_spec.md vs master_data.md vs 各塔ファイル）
   - tick間隔、ターン数/tick等の定数（game_spec.md vs tech_spec.md vs tech_battle_offline.md）

2. **用語・ID の一致**: 同じ概念が異なる名前で参照されていないか
   - 敵ID（tech_spec.md のJSONサンプル vs 各塔ファイルの敵データ）
   - 装備スロット名（game_spec.md vs tech_spec.md のJSON構造）
   - 塔ID・ダンジョンID（game_spec.md vs tech_spec.md）
   - ポーションID（master_data.md vs tech_spec.md のJSON構造）

3. **仕様の矛盾**: 異なる文書で同じ機能の動作が矛盾していないか
   - 戦闘フロー（game_spec.md vs tech_battle_offline.md）
   - オフライン計算（game_spec.md vs tech_battle_offline.md vs tech_spec.md）
   - 認証フロー（game_spec.md UI仕様 vs tech_auth.md）
   - ショップ仕様（game_spec.md vs tech_spec.md API設計）

4. **Phase整合性**: 機能のPhase割り当てが全文書で一致しているか

5. **塔データ整合性**: 各塔ファイルの内容がgame_spec.md・master_data.mdの概要と一致しているか
   - 階層数、推奨LV、解放条件、ボス名
   - エンカウントプールの重み合計が各階層で100%になっているか

6. **API網羅性**: game_spec.mdで定義された機能に対応するAPIがtech_spec.mdに存在するか

7. **データ構造整合性**: tech_spec.mdのJSON構造がgame_spec.mdの仕様を表現できているか

### B. 網羅性チェック（未定義・欠落の検出）

1. **open_specs.mdとの整合**: open_specs.mdで「確定済み（[x]）」とマークされた項目が、実際に対応する仕様書に反映されているか
2. **open_specs.mdの漏れ**: 仕様書内で「TBD」「後日検討」「未定」等と記載されている箇所が、open_specs.mdに未確定項目として登録されているか
3. **暗黙の前提**: 仕様書で言及されているが詳細が未定義の機能はないか
4. **相互参照の欠落**: 関連する仕様書間で適切にリンク・参照がなされているか

## 出力形式

レビュー結果を以下の形式で `docs/reviews/review_YYYY-MM-DD_HHMMSS.md` に保存してください（YYYY-MM-DD_HHMMSSは現在の日時）。
`docs/reviews/` ディレクトリが存在しない場合は作成してください。

### フォーマット

```markdown
# 仕様レビュー結果 — YYYY-MM-DD HH:MM:SS

## サマリー

| カテゴリ | 件数 |
|---------|------|
| 整合性（矛盾・不整合） | N件 |
| 網羅性（未定義・欠落） | N件 |
| 合計 | N件 |

---

## 指摘一覧

### ISSUE-001: [問題の短いタイトル]

| 項目 | 値 |
|------|-----|
| カテゴリ | 整合性 or 網羅性 |
| 重要度 | 高 / 中 / 低 |
| 関連ファイル | docs/file1.md, docs/file2.md |
| 該当箇所 | file1.md セクションX.X / file2.md セクションY.Y |

**問題の説明:**
具体的にどのような矛盾/欠落があるか。可能な限り原文を引用して示す。

**修正案:**
どのファイルのどの部分をどのように修正すべきか、具体的に記述する。
修正が必要なファイルごとに箇条書きで示す。

---

（以降、ISSUE-002, ISSUE-003, ... と続ける）
```

## 注意事項

- 指摘は具体的に記述すること。「矛盾がある可能性がある」ではなく「game_spec.md では X と記載されているが tech_spec.md では Y となっている」のように明示する
- 修正案は `/fix-specs` コマンドが実行可能なレベルで具体的に書くこと
- 重要度の基準:
  - **高**: 実装に直接影響する矛盾（数値の不一致、機能仕様の矛盾）
  - **中**: 実装時に混乱を招く可能性がある不整合（用語の不一致、参照の欠落）
  - **低**: 改善が望ましいが実装に大きな影響はない（文書構成、記載漏れ）
- 問題がない場合は「指摘なし」と明記する
- レビュー完了後、保存したファイルパスをユーザーに報告する

$ARGUMENTS が指定された場合、その内容をレビューの追加観点として考慮してください。
