## 2. 敵対的検証の結果

### 2-1. 記録は信頼できるか → 概ね信頼できる（穴は3点）
- (session_id, model) の重複0件、`input+output+cache_read+cache_creation == total` が全行成立、backfill と stop の二重計上0件を独立再計算で確認。stop 記録は同一セッション行を削除→書き直す upsert で、累積の二重計上はない。
- Stop 未発火で終わったセッションも `--all` backfill が補完する設計のため、恒久的な漏れは「最終 backfill 実行後に強制終了したセッション」のみ。
- **新たに見つかった穴**: (1) backfill は現在の cwd の slug しか走査せず、**worktree 等の別ディレクトリで実行したセッションは拾えない**（08-08以降 worktree 並列運用を開始しており、実消費は CSV より大きい可能性）。(2) 重複排除キーが `message.id or uuid` で両欠落時に過少計上。(3) cache_creation の TTL 別内訳が残らず、コスト幅 ×1.25〜2.0 は原理的に縮小できない。

### 2-2. コスト試算は妥当か → 妥当（ただしスナップショット）
単価・係数は claude-api 公式値と一致。CSV は稼働中に追記されるため、数値は 08-12 時点のスナップショット（全期間 $1,600〜1,770）。

### 2-3. 日次コスト急増（08-08〜）は効率悪化か → **総量増加が主因。ただし「効率改善」も否定**
- 当初主張「コスト/コミットは $4.7→$3.2 に改善」は**反証された**: 08-08以降の worktree 運用でマージコミット37件（backfill期0件）・5行以下の微小コミット49件（同2件）が分母を約1.4倍水増ししており、実質コミットで再計算すると **$4.62 → $4.57/コミットで横ばい**。変更行数基準では悪化の可能性すらある（ノイズ大）。
- 一方、実質コミット/日 17.4→52.5（3.0倍）に対しコスト/日 $80→$240（3.0倍）と比例しており、「急増は作業量の増加で説明できる（浪費の急増ではない）」は支持された。
- 結論: **単位あたりコストは削減計画後も下がっていない**。総量が3倍になったので請求も3倍になった、が実態。

## 3. 節約の観点 — 推奨アクション（確度・効果順）

1. **⑤（帰属できるログ）を最優先で実装する**【確度: 高 / 他施策の前提】— タスク帰属が7割超不能な現状では、施策の効果測定がすべて今回のような推定になる。`cost_usd` 列追加とやり取り単位の deltas 記録だけで足りる。あわせて worktree セッションを backfill が拾えない穴（§2-1）を修正する。
2. **②を機械的に強制する**【確度: 高 / 効果: 大】— Opus+Fable で99%超。仮に消費の2〜3割を Sonnet（単価0.6倍）へ移せば $15〜25/日規模の削減。規律は存在するが実態が伴っていないため、スキル側でサブエージェント `model: sonnet` を既定にする等、人の判断に依存しない形にする。
3. **1呼び出しコンテキストの抑制**【確度: 中〜高】— コストの6割は cache_read で、その源はコンテキスト長×呼び出し回数。平均147k/呼は前回(133k)より悪化しており、200k超セッションの棚卸し（何を持ち込んでいるか）と context-mode 運用の実効性検証が必要。目標例: 加重中央値 120k。
4. **Fable 5 の使用基準を明確化**【確度: 中】— 日次期コストの15%（$181）。Opus 5 の2倍単価に見合うタスクか、セッション開始時のモデル選択を意識的に行う。
5. **効率KPIは「実質コミット」で測る**【確度: 高 / 計測規律】— マージ・微小コミット込みのコミット数は worktree 運用で約1.4倍水増しされる。§2-3 の教訓として、今後の効果測定は5行超の非マージコミット、または行数ベースで行う。

## 4. 対応記録（2026-08-12 同日実装）

§3 の推奨 1（⑤帰属ログ）と 3（コンテキスト抑制）に対応した。

- **⑤実装済み**（`scripts/log_token_usage.py` 改修、テスト77件）: (a) やり取り単位の差分を `logs/token_usage_deltas.csv` へ追記し直前プロンプトへ帰属、(b) 両CSVへ `cost_usd` 列（cache write は1時間TTLの×2.0で計上）、(c) コンテキスト12万/18万tok・呼び出し100回で `/clear` を促す systemMessage 警告（計画①-2）、(d) worktree 起動でも main の logs/ へ記録し `--all` が全 worktree slug を走査。
- **worktree 記録漏れの回収**: `--all` 再実行で6セッション・$19 を新規取り込み（§2-1 の穴が実在した）。全190行の cost_usd 化後の総額は **$1,808**（×2.0換算）。
- **棚卸し結果（平均180k超/呼の21セッション中、transcript 残存12件を解析)**:
  - 初回コンテキストは**全セッション一律 42〜44k**（常駐分=システムプロンプト+ツール+スキル一覧等）。最終は286〜397k、成長は0.8〜1.3k tok/呼。
  - 成長のうちツール結果は**約2〜3割のみ**（最大は Read、12セッション計で≈44万tok。ctx_execute系は≈17万tokと小さい）。残り約7割は会話自体の蓄積（応答本文・思考・Edit/Write のツール入力）。
  - 含意: (a) 最有効打はセッション長の抑制で、解析12件すべてが215〜507呼と警告閾値(100回)の2〜5倍まで走っていた → 新警告が直接効く。(b) 常駐44kは全呼び出しの cache_read に乗り、日次期間だけで約$200相当 → **計画③-3（未使用プラグイン・コネクタの無効化）が未実施のまま**で、削減余地が残る。(c) Read は節読み（offset/limit）徹底の対象。
- **未対応の残り**: ⑤-3 `report_token_usage.py`（週次レビュー）、③-3 プラグイン棚卸し（`/plugins` とコネクタ設定からのユーザー操作が必要）、②の機械的強制。
