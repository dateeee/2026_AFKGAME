# セッション開始プロンプトの設計と実現の仕組み（2026-08-06）

ベース: [token_reduction_plan_2026-08-06.md](token_reduction_plan_2026-08-06.md) §1-1。
運用ルール「1セッション = 1工程 or 1タスク。『次の作業を進めて』で別タスクを始めない（/clear → 新プロンプトで開始）」を実際に回すには、**新セッションの最初の1通に何を書くか**と、**それを毎回低コストで用意する仕組み**が必要になる。本書はその検討結果と敵対的検証の記録。

## 1. 開始プロンプトに書く内容

### 1-1. 必要な要素（5点）

| # | 要素 | 目的 |
|---|------|------|
| 1 | **工程スキル名**（`/dev` `/test-list` 等） | 自動起動の推測に頼らず起動先を確定する |
| 2 | **対象**（Phase・機能・API名） | タスクの特定。探索的な状況把握を不要にする |
| 3 | **完了条件**（コミット・Red確認・C1 100% 等） | セッションの終端を明確にし、続投を防ぐ |
| 4 | **参照の起点**（索引 or 個別ファイル 最大2点） | 最初に読むファイルを指定し、持ち込み量を抑える |
| 5 | **前提**（直前の状態を1行。対応コミットID推奨） | 「前回何をしたか」の再調査（git log 探索）を省く |

### 1-2. 定型テンプレート

```
/<工程スキル> <Phase・対象>: <作業内容を1行>
完了条件: <...>
参照: <ファイル1〜2点>（起点。追加はここから索引経由で）
前提: <直前の状態1行・コミットID>
```

記入例（Phase 3 お知らせAPIでの例示）:

```
/test-list Phase 3 お知らせAPI: GET /api/notice/list の分岐一覧をテストリストへ展開
完了条件: 失敗するテスト一式（Red）を確認してコミット
参照: docs/tech/basic/tech_api.md §3.7（起点。追加はここから索引経由で）
前提: 詳細設計・分岐一覧は確定済み（コミット 1fe9e07）
```

悪い例: 「作業を継続して」「次の作業を進めて」「Phase 3 の続きをやって」——タスクが特定されず、状況把握のための探索読み（git log・仕様書スキャン）で数万トークンを消費し、誤ったタスクを選ぶ余地もある。

### 1-3. ユーザーが実際に送るもの

**このテンプレートを毎回手書きするのは非現実的**（要素5点を正確に思い出すコストが高い）。そこで「完成形のプロンプトを前セッションの終わりにエージェントが書き残し、ユーザーは貼り付けるだけ」にする。→ §2 の仕組み。

## 2. 仕組みの候補比較

| 案 | 内容 | 利点 | 難点 | 判定 |
|----|------|------|------|------|
| A | **引き継ぎファイル + コピペ**: `docs/backlog/next_session.md` の先頭に次回開始プロンプトの完成形を置き、ユーザーが新セッションへ貼り付ける | 常駐コストゼロ。ユーザーが内容を目視してから開始できる | 更新漏れで陳腐化する。ファイルを開く一手間 | **採用（即時）** |
| B | **`/next` スキル**: キュー先頭のプロンプトを読み、対応する工程スキルへ委譲 | 入力が5文字。タスク特定はファイル側が担うため 1-1 の趣旨は満たす | スキル一覧に1行常駐（全呼び出しの cache に乗る）。③-3 の常駐削減直後に逆行 | **条件付き採用**（案Aで2週間運用し、コピペが定着しない場合のみ実装） |
| C | **SessionStart フックで自動注入**: 引き継ぎファイルを毎セッション冒頭に注入 | プロンプトは一言で済む | 引き継ぎ不要なセッション（質問・調査・別作業）にも毎回課金。③の方針と正面衝突 | **却下** |
| D | **現状維持**: git log + development_process から次工程を都度導出 | 仕組み不要 | 導出のための探索読みが毎回発生。①の狙い（持ち込み削減）に反する。並行テーマがあると誤選択 | **却下** |

## 3. 推奨案の詳細設計（案A + Stopフック拡張）

### 3-1. `docs/backlog/next_session.md`（新設）

```markdown
# 次回セッションの開始プロンプト

> 使い方: 新セッションの最初のメッセージとして「次回」のコードブロックを貼り付ける。
> 更新: セッション終了（コミット）前に、次のタスクへ書き換える。完了行は残さない。

最終更新: <日付> / 対応コミット: <ID>

## 次回（コピペ用）

<定型テンプレートの完成形1件>

## 候補キュー（最大5行・優先順）

| 優先 | タスク | 工程スキル |
|------|-------|-----------|
```

- 役割は**ポインタ専用**。Phase 進捗・仕様の実体は書かない（正は README / development_process / 各仕様書。[docs/process/spec_ownership.md](../docs/process/spec_ownership.md) へ役割を1行宣言する）
- 次タスクをエージェントが確定できない場合、「次回」ブロックは `（ユーザー判断待ち — 候補キューから選択）` とし、ユーザーが候補行を選んでテンプレートへ流し込む

### 3-2. Stop フック拡張（`stop-commit.sh`）

コミット指示の手順へ1行追加する（リマインドのみ・強制しない）:

> 4. docs/backlog/next_session.md の「次回」ブロックを次のタスクへ更新したか確認する（タスク完了時のみ）

Stop フックは毎セッション末に必ず走るため、**更新漏れを機械的に検知する場所として最も確実**。フック本体のロジック追加は不要（メッセージ1行のみ）。

### 3-3. 運用ルールへの但し書き（①-1 の表を反映する際に追記）

- 「新セッションの開始は `docs/backlog/next_session.md` の定型プロンプト貼り付けで行う」を1セッションの単位の行へ補足
- 禁止フレーズ「次の作業を進めて」の趣旨は「**タスクを特定しない開始**の禁止」であることを明記（引き継ぎファイルがタスクを特定していれば `/next`（案B導入時）は趣旨に反しない）

### 3-4. 開始側の防御（陳腐化対策）

開始プロンプト（テンプレート）を受けたエージェントの最初の動作に「`前提:` のコミットIDと git log 最新数件を突合し、**プロンプトの作業が完了済みに見える場合は開始せずユーザーへ確認する**」を含める（工程スキル共通の手順としてではなく、next_session.md のヘッダー注記に1行で記載。スキル改修を要しない）。

## 4. 敵対的検証（自己レビュー）

設計 v1 に対して12の攻撃を行い、成立した攻撃は設計へ反映した（§2〜3 は反映後の姿）。

| # | 攻撃 | 判定 | 設計への反映 |
|---|------|------|------------|
| 1 | ルール①-1 は「次の作業を進めて」を禁止しているのに、`/next`（実質同義）を推奨するのは自己矛盾 | 部分成立 | 禁止の趣旨を「タスク未特定の開始の禁止」と明文化（§3-3）。案Bは趣旨を満たすが、矛盾に見える文言リスクも考慮し条件付き採用へ格下げ |
| 2 | 引き継ぎファイルは更新漏れ・手動作業後に陳腐化し、誤ったタスクを開始させる | 成立 | Stopフックのリマインド（§3-2）+ 対応コミットID欄 + 開始時のgit log突合で開始前に検知（§3-4） |
| 3 | 仕組み自体が常駐トークンを増やし、③-3（常駐棚卸し）と逆行する | 成立 | 案C（SessionStart注入）を却下。案B（スキル1行常駐）を条件付きへ。案Aは呼んだ時だけのコストで中立 |
| 4 | next_session.md が README の開発状況・development_process・open_specs と「正の重複」（規約4違反）を起こす | 部分成立 | ポインタ専用と明記し、spec_ownership へ役割宣言を追加（§3-1） |
| 5 | docs/ 配下に置くと check_docs の曖昧語・決定先送り検査がプロンプト文言に誤反応し、追記で8,000字上限にも近づく | 部分成立 | キュー最大5行・完了行削除で肥大化を防止。誤反応が出たら実装時に check_docs の除外設定で対処（logs/ 退避は リンク検査対象外になるため次善） |
| 6 | Stopフックのメッセージ肥大は毎セッション末の表示コストを増やす | 不成立 | 追加は1行のみ。フックはユーザー表示中心で、増分は無視できる |
| 7 | 定型が200字級では毎回書けず、形骸化する | 不成立（対処済み） | 手書きは例外時のみ。通常は前セッションが完成形を書き残す（§1-3） |
| 8 | 実装とドキュメント整備が並行すると「次回」1件では選べない | 成立 | 「次回」1件 + 候補キュー最大5行の2段構成。確定できない場合は「ユーザー判断待ち」と書く（§3-1） |
| 9 | `/next` スキルを作る場合、`.claude/skills/` はプロジェクト非依存の規約があり、ファイルパスをハードコードできない | 成立（案B採用時のみ） | 案B実装時はパスを profile 側に置く。実装手順（§5）に記載 |
| 10 | git log + development_process で次工程は導出できるから仕組み不要では | 不成立 | 導出のための探索読みが毎セッション発生し①の狙いに反する。導出誤り（並行テーマ）のリスクも残る（案Dの却下理由） |
| 11 | 反映先の profile.md は残り5字で、但し書きを追記できない | 成立 | §1-1 運用ルール全体の恒久化（①-1 反映）時に profile §6 の分割を先行させる。本書の範囲では profile を触らない（§5 の順序に明記） |
| 12 | 「参照: これ以外は読まない」は実務で守れず、必要ファイルが足りないと作業不能になる | 成立 | 文言を「起点。追加はここから索引経由で」に変更（§1-2）。規律4の運用手順（索引→該当のみ）と整合 |

**検証で設計が変わった点の要約**: 案Cの却下・案Bの条件付き化（攻撃1・3）、コミットID突合による陳腐化検知（攻撃2）、2段構成キュー（攻撃8）、「読まない」→「起点」への文言修正（攻撃12)、profile 分割を前提条件に組み込み（攻撃11）。
