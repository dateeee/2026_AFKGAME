# トークン消費量の敵対的検証と削減策（2026-08-05）

対象データ: `logs/token_usage.csv`（42行 = 35セッション × モデル別、backfill 37行 + stop/clear 5行）
突き合わせ対象: git履歴（全91コミット、2026-08-01〜05に87件）、リポジトリ成果物、`scripts/log_token_usage.py` の計上ロジック。

## 1. 集計サマリ

| 総トークン（CSV合計） | 5億303万 |
| 内訳 | cache_read 97.0% / cache_creation 2.3% / output 0.72% / input 0.007% |

## 2. 敵対的検証の結果

### 2-1. 記録自体は信頼できるか → 概ね信頼できる
- 二重計上なし: `message.id` で応答を重複排除、backfill と stop で同一セッションの重複記録なし（検証済み）。
- サブエージェント分も合算されており、集計漏れの方向の誤りは小さい。
- **ただしカバレッジに穴**: backfill はディスク上に残る transcript のみが対象。2026-03 の初期作業（4コミット）分は含まれていない可能性が高く、実際の累計はCSVより大きい。

### 2-2. 「5億トークン」という数字は妥当な指標か → **指標として不適切**
- 97%は cache_read で、単価は入力の1/10。エージェントは毎呼び出しで全コンテキストを再読するため、**総トークンは「呼び出し回数 × コンテキスト長」でほぼ機械的に膨らむ**。生トークン合計をKPIにすると実態を50倍近く過大に見せる。
- 妥当性判断はコスト加重（約$462〜512）で行うべき。

### 2-3. タスクへの帰属は正しいか → **弱い**
- `task` 列は「セッション最初の実質プロンプト」であり、セッションが長引くほど嘘になる。例: `/reload-skills` ラベルのセッションが335呼び出し・5,700万トークン（実体はその後の別作業）。`(不明)` も4セッション・6,700万トークン。
- 現状のCSVでは「どの工程が高いか」を正確には語れない。タスク別の議論は参考値に留まる。

### 2-4. 消費量そのものは妥当か → **約半分は構造的、残りに明確な削減余地**
妥当と言える部分:
- output 364万トークン vs リポジトリの全テキスト成果物 約70万トークン相当 = **5.2倍**。thinking・レビューレポート・対話応答・書き直しを含むため、レビュー重視のプロセスとしては正常範囲。
- cache_creation 比率2.3%はキャッシュが正常に効いている証拠。

妥当でない部分（反証が成立した点）:
1. **セッションの長期化**: 2,000万トークン超の8セッションだけで全体の68%。呼び出し回数中央値50回に対し、上位セッションは200〜349回。1呼び出し平均コンテキストが27〜34万トークンに達したセッションがあり、CLAUDE.md自身が定める「工程の区切りで /clear」が守られていない。cache_read コスト$269の過半はここから出ている。
2. **モデル選択の規律違反**: profile §6 は「機械的作業は sonnet」と定めるが、実績は Opus/Fable がコストの97%、Sonnet はわずか3.4%。
3. **直近の単価上昇**: 8/5 の stop 記録はすべて Fable 5（$10/$50 = Opus 5 の2倍）。単価の高いモデルで長セッション運用を続けると悪化が加速する。

**結論: 「妥当」とは言えない。総量の桁はエージェント動作の構造上避けられないが、コストの過半を占める cache_read はセッション運用の改善だけで大きく削れる。**

## 3. 削減策（確度が高い順）

### ① セッションを短く区切る — /clear 運用の徹底【確度: 高 / 効果: 最大】
- 根拠: cache_read コスト（全体の58%）は「呼び出し回数 × その時点のコンテキスト長」に比例。長セッション後半は毎回27〜34万トークンを再読しており、同じ作業を2セッションに分ければ後半のコンテキストはほぼ半減する。
- アクション: 工程・タスクの区切りで必ず /clear（既にCLAUDE.mdの規定。「作業を継続して」「次の作業を進めて」で1セッションを引き延ばす運用をやめる）。レビュー→修正適用の別セッション分離も徹底。
- 期待効果: cache_read の3〜4割減 ≒ **全体コスト2割前後の削減**。

### ② モデル階層の使い分けを実態に合わせて強制する【確度: 高】
- 根拠: 単価差が確定的（Sonnet 5 は Opus 5 の0.6倍、Fable 5 の0.3倍）。現状 Sonnet 比率3.4%は profile §6 の方針と乖離。
- アクション: 機械的作業（差分整形、一覧生成、テンプレ適用、カバレッジ穴埋め等）のサブエージェントは `model: sonnet` を必須化。メインセッションも定型工程は Opus、Fable は判断が重い工程に限定。
- 期待効果: 対象作業の単価40〜70%減。全体では1〜2割規模。

### ③ コンテキストへの持ち込み量を減らす【確度: 中〜高】
- 根拠: docsは1ファイル8,000字以下に分割済みなのに、1呼び出し平均コンテキスト中央値が10.8万トークン。差分はツール出力の蓄積・ファイル全読み・常駐定義（スキル/MCP）が占める。
- アクション: (a) 集計・検索・大きな出力の処理は context-mode（ctx_execute 系）で行い、生バイトを会話に入れない。(b) 仕様書は索引→必要セクションのみ読む運用を維持・徹底。(c) 使っていないMCPサーバー・スキルの常駐を整理する。
- 期待効果: 呼び出しあたりコンテキストの1〜3割減（cache_read/write 両方に効く）。

### ④ 出力（thinking含む）の抑制 — effort と差分レビューの活用【確度: 中】
- 根拠: output はコストの24%（$109）。Fable/Opus の thinking は output として課金される。レビュー系は差分モードが既定だが、full 実行や長い経過報告が output を押し上げる。
- アクション: 定型作業は effort を low/medium に落とす。レビューは差分モード厳守、full は Phase 完了ゲートのみ。長い中間報告・重複要約を出させない。
- 期待効果: output の2〜3割減 ≒ 全体5%前後。単体では小さいが確実に効く。

### ⑤ 計測の改善 — 帰属できるログにする【確度: 中 / 他施策の前提】
- 根拠: 現状は task ラベルが不正確（§2-3）で、施策①〜④の効果測定ができない。
- アクション: (a) やり取り単位の記録（Stop移行済み）に「直前のユーザープロンプト」列を追加し、セッション先頭ではなく各時点のタスクを記録。(b) コスト加重列（単価×0.1倍等を適用したUSD換算）を追加し、生トークンではなくコストで監視。(c) 週次で上位セッションを確認するだけの軽い運用にする。
- 期待効果: 直接削減はゼロだが、①〜④の効果検証と再発検知を可能にする。

## 4. 留意事項
- コスト試算は 2026-06 時点キャッシュの一次API単価に基づく概算。cache write の TTL（5分=1.25倍 / 1時間=2倍）で幅を持たせた。
- 20万トークン超のコンテキストで運用したセッションが複数あり、長コンテキスト帯の割増料金が適用されるプランでは実コストがさらに高い可能性がある。
- 2026-03 分の消費は記録外のため、本レポートの数値は「記録が残る範囲の下限」である。
