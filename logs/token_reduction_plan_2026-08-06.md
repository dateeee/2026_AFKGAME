# トークン削減策の具体化 ①③⑤（2026-08-06）

ベース: [token_usage_analysis_2026-08-05.md](token_usage_analysis_2026-08-05.md) §3。
対象は ①セッション分割 / ③持ち込み量削減 / ⑤計測改善 の3件（②モデル選択・④出力抑制は対象外）。

前提数値（分析レポートより）: コスト約$462〜512、うち cache_read 58%。2,000万トークン超の8セッションが全体の68%。呼び出しあたり平均コンテキスト中央値 10.8万トークン、問題セッションは27〜34万。

## ① セッションを短く区切る — /clear 運用の徹底

「規定はあるが守られていない」が問題なので、**運用ルールの数値化**と**機械的な警告**の2本立てにする。

### 1-1. 運用ルール（数値つき）

| ルール | 値 |
|--------|-----|
| 1セッションの単位 | 1工程 or 1タスク。**「作業を継続して」「次の作業を進めて」で別タスクを始めない**（/clear → 新プロンプトで開始） |
| /clear 必須トリガー | コミット完了後 / レビューレポート出力後 / fix-specs 適用完了後 / Phaseゲート通過後 |
| セッション上限の目安 | 呼び出し100回、またはコンテキスト18万トークン到達（下記警告と連動） |
| /compact の許可条件 | 同一タスクの続きを直後に行う場合のみ。レビュー→修正適用は必ず別セッション |

### 1-2. Stop フックでの機械的警告（`scripts/log_token_usage.py` へ追加）

Stop フックは毎やり取り後に走り、transcript を全パースしているため、**追加コストほぼゼロで現在コンテキストを正確に取れる**。

| 項目 | 仕様 |
|------|------|
| 現在コンテキストの算出 | 最後の assistant メッセージの usage から `input + cache_read + cache_creation` を合算 |
| 警告レベル1 | 現在コンテキスト ≥ **12万** or 呼び出し ≥ **100回** → 「工程の区切りで /clear を検討」 |
| 警告レベル2 | 現在コンテキスト ≥ **18万** → 「20万で長コンテキスト割増帯。/clear を強く推奨」 |
| 出力方法 | stdout へ `{"systemMessage": "⚠ コンテキスト18.2万tok / 112回 — /clear を検討..."}` を出力（exit 0）。ユーザー表示のみで**会話コンテキストには乗らない** |

閾値の根拠: 中央値10.8万に対し、問題セッションは27〜34万で推移していた。12万=中央値超過の早期通知、18万=200K割増帯の手前。

### 1-3. 期待効果と検証

cache_read の3〜4割減 ≒ 全体コスト2割前後（分析レポート§3①のまま）。検証は⑤のKPI「呼び出しあたり平均コンテキスト」「呼び出し100回超セッション数」で行う。

## ③ コンテキストへの持ち込み量を減らす

### 3-1. context-mode の運用規律化（profile §6 へ規律7を追記）

追記文言案（[.claude/project/profile.md](../.claude/project/profile.md) §6 の表へ1行）:

> | 7 | 大きな出力（ログ・テスト結果・git履歴・集計・検索）の処理は context-mode（`ctx_batch_execute` / `ctx_execute`）で行い、生出力を会話に持ち込まない。ファイルの分析・要約は `ctx_execute_file`。`Read` の全文読みは Edit 前提のときのみ |

注意: profile §6 改稿時は CLAUDE.md「コスト規律」要約との突合が必要（profile §7 規約6）。

### 3-2. 索引→必要セクション読みの徹底（既存規律4の運用具体化)

| 場面 | 具体的な手順 |
|------|-------------|
| 仕様書参照 | 索引（`tech_spec.md` 等）で担当ファイルを特定 → 該当ファイルのみ読む。大きいファイルは `Read` の offset/limit で節単位 |
| レビュー系スキル | 先に `git diff --name-only` で対象を確定し、対応する個別ファイルのみ読む（差分モード厳守） |
| 再読の禁止 | 同一セッション内で同じファイルを再 Read しない（Edit 失敗時の再確認を除く） |

### 3-3. 常駐プラグイン・MCPの棚卸し【即日実行可・実装不要】

スキル一覧・フック定義はシステムプロンプトに常駐し、**全3,379回の呼び出しすべての cache_read/write に乗っていた**。現状の常駐と処分案:

| 常駐 | 内容 | 処分案 |
|------|------|--------|
| example-skills | algorithmic-art / slack-gif-creator / theme-factory 等12件 | **無効化**（本プロジェクトで未使用） |
| document-skills | xlsx / docx / pptx / pdf 4件 | **無効化**（Office文書を扱う時だけ再有効化） |
| dataviz | チャート作成ガイド | **無効化**（未使用） |
| claude-api | Claude API リファレンス | **無効化**（ゲームにLLM組み込み予定なし） |
| claude.ai コネクタ | Gmail / Calendar / Drive（未認証のまま常駐） | **接続解除**（claude.ai のコネクタ設定から） |
| context-mode | ctx_execute 系 | **残す**（3-1の中核） |

手順: `/plugins` から disable（またはコネクタは claude.ai 設定 / `/mcp`）。効果は呼び出しあたり数千トークン規模だが全呼び出しに比例して効くため、③全体（1〜3割減）の一部を即日で確保できる。

## ⑤ 計測の改善 — 帰属できるログにする

### 5-1. やり取り単位の帰属記録（新規 `logs/token_usage_deltas.csv`）

既存 `token_usage.csv`（セッション累計・上書き型）は互換のまま残し、**差分の追記型CSV**を追加する。Stop フックのたびに「今回の累計 − 前回の累計」を直前のユーザープロンプトへ帰属させる。

| 項目 | 仕様 |
|------|------|
| 列 | `time, session_id, model, prompt, input_d, output_d, cache_read_d, cache_creation_d, calls_d, cost_usd` |
| `prompt` | 直前のユーザープロンプト先頭60字。`<command-name>` はコマンド名（SKIP_COMMANDS 除外）、システム由来（`<`始まり等）はスキップ。既存 `task_label()` を逆順走査に流用 |
| 差分計算 | upsert 前に既存CSVから同 session_id × model の累計を読み、引き算。初回・負値（resume引き継ぎ）は今回累計をそのまま記録 |
| 書き込み | 追記のみ（上書きなし）。既存の上書き型と役割分担 |

これで「/reload-skills ラベルに5,700万トークン」「(不明)に6,700万トークン」のような誤帰属が解消し、工程別・タスク別のコストを語れるようになる。

### 5-2. コスト加重列（両CSVへ `cost_usd` 追加）

スクリプト内に単価表を持ち、行ごとにUSD換算する。

| モデル | input / output（$/MTok） |
|--------|--------------------------|
| claude-opus-5 | 5 / 25 |
| claude-fable-5 | 10 / 50 |
| claude-sonnet-5 | 3 / 15 |
| claude-haiku-4-5 | 1 / 5 |
| 不明モデル | opus-5 単価にフォールバック |

計算式: `cost = (input×p_in + output×p_out + cache_read×p_in×0.1 + cache_creation×p_in×2.0) / 1e6`。cache write 係数は **2.0**（本環境は1時間TTL運用のため。分析レポートの幅1.25〜2.0の上限側）。既存行の `cost_usd` は `--all` 実行時に再計算して埋める。

### 5-3. 週次レビュー（新規 `scripts/report_token_usage.py`）

「週1回・5分・コマンド1発」の軽い運用にする。`python scripts/report_token_usage.py --days 7` で標準出力に20行程度:

- 期間合計コスト（USD）と前週比
- モデル別コストシェア（Sonnet比率の推移確認 = 施策②の検証）
- コスト上位5タスク（deltas の `prompt` 別集計）
- 上位5セッション（コスト / 呼び出し回数 / 平均コンテキスト）
- 閾値超過数（呼び出し100回超・平均コンテキスト15万超のセッション）

### 5-4. 監視KPI（施策①〜④の効果検証に使う）

| KPI | 現状 | 目標 |
|-----|------|------|
| 呼び出しあたり平均コンテキスト（中央値） | 10.8万 | 8万以下 |
| 2,000万トークン超セッションの消費シェア | 68% | 30%以下 |
| 呼び出し100回超のセッション数/週 | 上位で200〜349回 | 0〜1 |
| Sonnet コスト比率 | 3.4% | 20%以上 |
| `(不明)`・誤帰属の消費シェア | 1.3億トークン超 | ほぼ0 |
